# React Adapter Re-render Overhead (Vue/Svelte as Reference Baselines)

**Date:** 2026-07-16
**Status:** Draft — pending user review
**Scope:** `packages/adapters/react/` is the fix target. `packages/adapters/vue/` and `packages/adapters/svelte/` are investigated only as reference points (both already sit at the clean baseline — see Problem) — Phase 1's new test infrastructure still covers Vue (see below, this was already decided before the correction below and remains useful as a contrast tool), but no Vue *fix* is anticipated. A fix to `packages/adapters/react/src/index.ts` is in scope only if root-cause finds a real, fixable adapter-level inefficiency. No changes to `packages/core/`, no changes to `bench/apps/*` demo components unless a root-cause finding specifically implicates demo-only code (see Out of Scope). This is v0.5.0 release-gate item 8 (added after all 7 original items were RESOLVED — see the `project_v050_release_gate` memory).

**Round-1-review correction (significant, changes scope from the originally-approved design):** the draft of this spec cited item 3's *pre-fix* numbers (`React 40 / Vue 30 / Svelte 20`) from an early line in the `project_v050_release_gate` memory, without reading that same memory's own later correction: item 3's final whole-branch review found and fixed a real render-counter reset bug in `bench/apps/vue/src/App.vue` (commit `5fac9ba`) that had inflated Vue's true ~20 up to a published 30. The corrected, currently-published number (independently re-verified against the live `docs/benchmarks/index.md`, "Schema Validation — Re-renders per 20-keystroke sequence (Zod, 10-field form)" table) is **`neutro/form (React) 40`, `neutro/form (Vue) 20`, `neutro/form (Svelte) 20`.** Vue is not anomalous — it already matches Svelte's clean 1:1 baseline. ## Problem

Item 3 of this release cycle (browser-level schema-validate comparison) measured re-render counts across neutro/form's three adapters — React, Vue, Svelte — for the identical engine, same fixture, same 10-field/20-keystroke-into-one-field scenario. The current, correct, published numbers are **neutro/form (React) 40, neutro/form (Vue) 20, neutro/form (Svelte) 20** (see Round-1-review correction above). Vue's and Svelte's counts both match the keystroke count exactly (1 render per keystroke); only React's is anomalous, at exactly 2x. This was recorded at the time as "reflecting each adapter's own subscription granularity, not a neutro-wide constant" and left uninvestigated — item 3's scope was the comparison surface itself, not each adapter's internal behavior.

Investigation for this spec (reading the real demo components directly, not just the aggregate numbers) found a structural picture more specific — and more interesting — than "React subscribes more broadly than Vue/Svelte":

- **The child component in all three frameworks uses an equivalent, genuinely fine-grained per-field subscription.** React's `Field` (`bench/apps/react/src/SchemaValidateNeutro.tsx:15-28`) uses `useSyncExternalStore` wired to `form.subscribeToPath(name, ...)`. Vue's `NeutroField` (`bench/apps/vue/src/NeutroField.vue`) uses the adapter's `useVueFormPath`, itself backed by `subscribeToPath`. Svelte's `NeutroField` (`bench/apps/svelte/src/NeutroField.svelte`) uses `useSvelteFormPath`, likewise per-field. None of the three children is the culprit by itself.
- **The parent components are structurally different, and — counter to the "granularity" framing — the *coarser* parent subscription correlates with the *better* (lower) render count:**
  - React's parent (`SchemaValidateNeutroPage`, same file, lines 30-50) subscribes *specifically* to `field0` via `subscribeToPath('field0', ...)`, to show an error banner for that one field.
  - Vue's parent (`SchemaValidateNeutro.vue:16-17`) subscribes to the **whole form** (`form.subscribe((s) => { state.value = s })`), reading `state.errors.field0` for the same banner.
  - Svelte's parent (`SchemaValidateNeutro.svelte:15-16`) does the same — a **whole-form** `form.subscribe(...)`.
  - Despite React's parent subscription being the *more targeted* of the three (field-specific, not whole-form), React is the one with the 2x render count. Vue and Svelte, with the *coarser* whole-form parent subscription, both land at the clean baseline. This rules out "parent subscribes too broadly" as the mechanism, and points instead at something specific to how each framework's rendering model responds to a parent re-render — most plausibly, **React re-executes every unmemoized child function component whenever its parent re-renders, regardless of whether that child's own props changed, while Vue's and Svelte's compiler-driven fine-grained reactivity does not force child re-execution just because a parent's local reactive state changed.** This is a genuine, testable hypothesis, not yet confirmed — see Design.
  - This hypothesis does **not**, on its own, cleanly explain the *exact* 2x arithmetic (if React's parent re-render cascaded to *all* 10 unmemoized children on every keystroke, the total would be far higher than 40 — closer to 200, matching the render counts TanStack/felte show on this same surface). The real mechanism is more specific than a blanket cascade-to-everyone theory, and Phase 2 exists specifically to nail down what it actually is rather than have this spec assert an unverified explanation.
- Neither app uses `StrictMode` (which would double-invoke renders in dev mode); all three are served from production `vite preview` builds via the existing Playwright bench infra — so it's not a dev-mode artifact.
- Neither React's nor Vue's adapter package (`packages/adapters/react/`, `packages/adapters/vue/`) currently has any component-level test coverage. React's adapter package has **zero tests of any kind** — no test runner references, no `react-dom`/testing-library devDependency. Vue's one existing test (`packages/adapters/vue/test/set-errors.test.ts`) runs the `useVueForm` composable inside a bare `effectScope()`, never mounting a real component tree.

So the real gap this item closes is: **neutro's React adapter has a real, unexplained 2x re-render cost relative to Vue/Svelte for an equivalent scenario, the mechanism has never been isolated (the naive "dual same-path subscriber" and "cascade to all children" theories don't survive contact with the actual demo structure or arithmetic), and neither React's nor Vue's adapter package has ever had component-level test coverage to investigate it with.**

## Design

### Phase 1: New component-level test infrastructure

Neither React's nor Vue's adapter package can currently mount a real component tree and observe render counts. Add that capability to both — React because it's this item's actual fix target, Vue because Vue's known-good structure (whole-form parent, no cascade) is the most useful available contrast for diagnosing React's behavior, and because Vue's adapter package has the same pre-existing test-coverage gap this item is already fixing for React:

- **`packages/adapters/react`**: add `react-dom` and `@testing-library/react` as devDependencies (react itself is already a peerDependency; `@types/react` is already present). New `packages/adapters/react/test/` directory, naming files by concern (e.g. `rerender-repro.test.tsx`) the same way `packages/adapters/vue/test/set-errors.test.ts` names its one existing file — not yet an established multi-file convention, just a sensible default to follow.
- **`packages/adapters/vue`**: add a real DOM-mounting test utility (`@testing-library/vue`, or `@vue/test-utils` if it fits the existing `effectScope`-based test style more naturally — the implementer should pick whichever integrates with the least friction against the existing `set-errors.test.ts` pattern, and document the choice) as a devDependency. Extend `packages/adapters/vue/test/`.
- Both run through the existing root `vitest.config.ts` (which already excludes only `bench/**`/`node_modules/**` and aliases `@neutro/form-core` to source) plus `jsdom` (already a root devDependency, used by other packages already) — no new top-level test runner or config needed. `vue` itself is resolvable today without an explicit devDependency (confirmed by the existing Vue adapter test importing `effectScope` successfully) — the implementer should trace exactly why (workspace hoisting via another package's dependency, e.g. VitePress's own `vue` dependency) and add an explicit `vue` devDependency to `packages/adapters/vue/package.json` if the implicit resolution is fragile, rather than leave it implicit.

### Phase 2: Minimal repro + root-cause

Build two minimal repros — one per framework — each mirroring the *actual structure* found in its respective bench demo (not a synthetic worst case, the real shape confirmed in the Problem section):

- **React repro**: a parent component with a `subscribeToPath('field0', ...)` subscription (matching the real demo's field-specific parent), rendering a list of unmemoized child components, one of which (`field0`) also independently subscribes to `field0` via the adapter's `useFormPath` hook. Count how many times the `field0` child's render function body executes for a sequence of value changes on `field0`.
- **Vue repro**: the same shape, but with the parent's subscription changed to match Vue's real demo (`form.subscribe(...)`, whole-form) rather than React's field-specific one — this is a deliberately *different* parent structure per framework, matching what's actually deployed, not an artificially matched pair. Count the same way.

Use these repros to test concrete hypotheses via `systematic-debugging` discipline — form a hypothesis, test it against the repro, don't guess-and-patch. The Problem section's investigation ruled out the two most obvious theories already (dual same-path parent+child subscription — false, since Vue/Svelte's parents subscribe even *more* broadly and still hit the clean baseline; blanket cascade-to-all-children — arithmetically inconsistent with the observed 2x rather than ~10x). Concrete hypotheses still open:
1. **Memoization-boundary hypothesis**: does wrapping the React child in `React.memo` (or an equivalent bail-out) eliminate the extra render(s), while leaving it unwrapped reproduces them? This tests whether React's lack of an automatic props-unchanged skip (vs. Vue's/Svelte's compiler-driven dependency tracking) is the mechanism, independent of parent subscription granularity.
2. **Partial-cascade hypothesis**: if the cascade theory is real but *not* blanket (i.e., something limits it to exactly field0 rather than all 10 fields), what is that something? Trace `useSyncExternalStore`'s exact re-render-triggering behavior in React 18/19 — does it force a synchronous re-render of *only* the subscribed component when its own snapshot changes (which could explain why `field0`'s own subscription re-renders it once, per keystroke, independent of the parent), and separately, does the parent's own re-render (if it happens at all, and how often) additionally re-invoke `field0`'s child specifically (e.g., because it's first in render order, or because of some other non-obvious React behavior) without touching the other 9? This hypothesis requires literally counting parent re-renders in the repro, not just the child's count, to distinguish "child renders twice from its own subscription firing twice" from "child renders once from its own subscription plus once from a parent cascade."
3. **`useSyncExternalStore` double-notification hypothesis**: does neutro's `notify()` (`packages/core/src/engine.ts`) call a single path's subscribers more than once per `set()` call in some circumstance relevant here (e.g., once for the exact-path notification and again via some ancestor-notification pass)? This would show up as the *same* component's `useSyncExternalStore` callback firing twice per keystroke even with no parent involved at all — testable by mounting *only* the child (no parent) in the repro and counting.

Document whichever hypotheses are confirmed or ruled out, with the repro test as evidence, before proposing any fix. If none of the three above pan out, that's a signal to escalate (more repro variations, or flag to the user) rather than ship a spec-mandated theory that turned out to be wrong.

### Phase 3: Fix (if warranted) + re-verify

- If root-cause finds a genuine, fixable adapter-level inefficiency in `packages/adapters/react/src/index.ts`, fix it, confirm via the Phase 2 repro test (render count drops to the expected value), and re-run the full test suite for both adapter packages plus `packages/core/test/` to confirm no regression. A Vue-side code change is not anticipated (Vue is already at baseline) — if Phase 2's Vue repro somehow surfaces a real Vue-side issue despite the demo-level numbers looking clean, treat that as a genuine, disclosed surprise finding and flag it to the user before fixing, since it wasn't anticipated by this spec.
- Re-run the existing browser-level `bench/suites/browser/schema-validate-rerenders.spec.ts` (already covers all three frameworks, no new browser test needed) to confirm the real, browser-measured `neutro/form (React)` number moved in the expected direction. **Before this re-run, kill any stale Playwright preview servers on ports 4173-4175** (`bench/playwright.config.ts` sets `reuseExistingServer: !process.env.CI`, which silently serves a stale build if a preview server from an earlier run is still bound to those ports locally — this exact failure mode is what produced item 3's original wrong Vue number, per the `project_v050_release_gate` memory's account of commit `5fac9ba`'s verification). If the number moves enough to be worth republishing, regenerate `docs/benchmarks/index.md` per the established pipeline (`bench:merge`/`bench:generate`, copying `latest.json` → `baseline.json` first per the documented local-run convention) and disclose the before/after numbers plainly.
- If root-cause instead shows the gap is inherent to React's own re-render/batching model (not something neutro's adapter code controls or could avoid without a fundamentally different subscription API), document that finding precisely — which mechanism, why it's out of neutro's control, with the repro tests kept as permanent regression coverage proving the *current, understood* behavior — and stop. No fix should be forced where none is warranted; this is an acceptable, honest outcome per this cycle's established standard (matching item 6's "no bug found, mechanism confirmed nesting-agnostic" outcome).

## Expected outcome / hypothesis

Not yet known which of Phase 2's three hypotheses will hold — this is genuinely open, unlike some of this cycle's earlier items where a specific mechanism was already suspected with reasonable confidence. The Round-1 correction above already ruled out the two theories the original draft implicitly leaned on (dual-same-path-subscriber, blanket-cascade), so Phase 2 starts from a narrower, better-evidenced set of live hypotheses rather than the original guess. Two broad possible final outcomes, both real findings either way:
- **If Phase 2 confirms a real, fixable React-adapter inefficiency:** Phase 3 fixes it, `neutro/form (React)`'s re-render count should drop measurably in the browser bench (ideally toward Vue/Svelte's 20), and both adapter packages gain permanent, real component-level test coverage they currently entirely lack (a second, independent value of this item beyond the specific fix).
- **If Phase 2 finds the gap is an inherent React rendering-model cost:** this is disclosed precisely (which exact mechanism, with the repro test as evidence — not hand-waved as "just how React works"), the repro tests still ship as permanent coverage proving both adapters behave as understood, and the finding becomes documentation (likely a note near the schema-validate-rerenders numbers in `docs/benchmarks/index.md`, since the existing "reflecting each adapter's own subscription granularity" language is now known to be an inaccurate simplification per the Problem section) rather than a code change.

## Verification

- Phase 1: `pnpm exec vitest run packages/adapters/react/test/` and `pnpm exec vitest run packages/adapters/vue/test/` — new test files run and pass (initially just proving the repro mounts and renders correctly, before any hypothesis-testing assertions are added).
- Phase 2: repro test(s) assert the confirmed render-count mechanism for both frameworks (e.g., "React child renders N times for M value changes, with/without React.memo"; "Vue child renders N times for M value changes with a whole-form parent subscription, confirming the known-good baseline the React repro is measured against").
- Phase 3 (if a fix lands): repro test(s) updated to assert the corrected render count; `pnpm exec vitest run packages/adapters/` (both packages) and `pnpm exec vitest run packages/core/test/` green; `pnpm --dir bench install` (if new devDependencies require it) then rebuild the React bench app (`pnpm --dir bench run bench:apps:build:react`) and re-run `pnpm --dir bench exec playwright test suites/browser/schema-validate-rerenders.spec.ts` (a single-file invocation, distinct from the repo's own `bench:browser` script which runs the whole `suites/browser` directory — both trigger the same `webServer` auto-start block in `bench/playwright.config.ts`, so either form works; the single-file form just narrows which spec(s) run) — after first killing any process bound to ports 4173-4175 from a prior local run (`lsof -ti:4173,4174,4175 | xargs kill` or equivalent), per the stale-preview-server footgun documented in Phase 3 above — to confirm real browser numbers.
- Full pipeline: `pnpm lint && pnpm exec tsc --noEmit && pnpm build && pnpm test` (per `CLAUDE.md`'s pre-push checklist) regardless of which outcome (fix vs. documented-inherent-cost) this item lands on.

## Out of Scope

- `packages/core/` — this item is about adapter-level render behavior, not the core engine's `notify`/`pathSubscribers` mechanism itself, **unless** Phase 2's hypothesis 3 (`useSyncExternalStore` double-notification) confirms the double-notify originates in `notify()`/`pathSubscribers` itself rather than in React's own rendering response to a single notification — in that case the cause is core-engine-level, not adapter-level, and is a genuine scope-expansion trigger: stop and flag it to the user rather than silently expanding scope, since it would change this item's blast radius significantly (a core-engine bug would affect Vue's and Svelte's adapters too, contradicting their clean baseline numbers — which would itself be a strong signal the double-notify theory is wrong, but must be confirmed empirically, not assumed).
- A Vue-side *fix* — per the Round-1 correction, Vue is not anomalous (matches Svelte's baseline already). Vue's new test infrastructure and repro (Phase 1/2) exist to provide a contrast baseline for diagnosing React, not because Vue itself needs fixing. If Phase 2 unexpectedly surfaces a real Vue-side issue anyway, that's a disclosed surprise finding per Phase 3, not a planned deliverable of this item.
- Solid and Angular adapters — item 3's `schema-validate-rerenders` surface never measured them (no comparable data exists), so there's no signal to investigate for either. A future item, not bundled here.
- `bench/apps/*` demo component changes — the demo components are treated as a faithful, already-correct representation of real per-field-subscription usage for the child components, and real (if structurally different per framework) parent-subscription usage — both confirmed by direct inspection during this spec's own investigation (see Problem section, now covering all three frameworks' actual parent/child structure, not just React/Svelte as the original draft did). If Phase 2 finds a demo itself is structured in a way that doesn't represent realistic adapter usage, that becomes a disclosed finding for the user to weigh, not an in-scope fix.
- Republishing `docs/benchmarks/index.md` unconditionally — only regenerate if Phase 3 lands a real fix with numbers worth updating; a documented-inherent-cost outcome does not, by itself, require a docs page change beyond correcting the now-known-inaccurate "subscription granularity" explanation already published there (matching the "no docs changes unless genuinely noteworthy" default used throughout this cycle for items 5-7, while still fixing a now-identified inaccuracy).
- React Native — no such adapter exists in this codebase; irrelevant to this item.
