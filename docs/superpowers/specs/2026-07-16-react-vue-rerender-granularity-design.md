## Problem

Item 3 of this release cycle (browser-level schema-validate comparison) measured re-render counts across neutro/form's three adapters — React, Vue, Svelte — for the identical engine, same fixture, same 10-field/20-keystroke-into-one-field scenario. The current, correct, published numbers are **neutro/form (React) 40, neutro/form (Vue) 20, neutro/form (Svelte) 20** (see Round-1-review correction above). Vue's and Svelte's counts both match the keystroke count exactly (1 render per keystroke); only React's is anomalous, at exactly 2x. This was recorded at the time as "reflecting each adapter's own subscription granularity, not a neutro-wide constant" and left uninvestigated — item 3's scope was the comparison surface itself, not each adapter's internal behavior.

Investigation for this spec (reading the real demo components directly, not just the aggregate numbers) found a structural picture more specific — and more interesting — than "React subscribes more broadly than Vue/Svelte":

- **The child component in all three frameworks uses an equivalent, genuinely fine-grained per-field subscription — but React's is structured differently from the other two in a way that matters.** React's `Field` (`bench/apps/react/src/SchemaValidateNeutro.tsx:15-28`) **hand-rolls** `useSyncExternalStore` directly against `form.subscribeToPath`, passing brand-new inline arrow functions for both `subscribe` and `getSnapshot` on every render — it does **not** use the React adapter's own `useFormPath` hook. Vue's `NeutroField` (`bench/apps/vue/src/NeutroField.vue`) uses the adapter's `useVueFormPath`. Svelte's `NeutroField` (`bench/apps/svelte/src/NeutroField.svelte`) uses `useSvelteFormPath`. The React adapter's real `useFormPath` (`packages/adapters/react/src/index.ts:51-60`) wraps both `subscribe` and `getSnapshot` in `useCallback` for a stable identity across renders — the demo's hand-rolled version does not. This is a real, previously-unnoticed structural gap between what the demo measures and what the shipped adapter actually does, and a plausible mechanism on its own: `useSyncExternalStore` re-subscribing on every render because its `subscribe` argument's identity changes every time is a known real footgun, independent of anything about the parent component. See hypothesis 0 below.
- **The parent components are structurally different, and — counter to the "granularity" framing — the *coarser* parent subscription correlates with the *better* (lower) render count:**
  - React's parent (`SchemaValidateNeutroPage`, same file, lines 30-50) subscribes *specifically* to `field0` via `subscribeToPath('field0', ...)`, to show an error banner for that one field.
  - Vue's parent (`SchemaValidateNeutro.vue:16-17`) subscribes to the **whole form** (`form.subscribe((s) => { state.value = s })`), reading `state.errors.field0` for the same banner.
  - Svelte's parent (`SchemaValidateNeutro.svelte:15-16`) does the same — a **whole-form** `form.subscribe(...)`.
  - Despite React's parent subscription being the *more targeted* of the three (field-specific, not whole-form), React is the one with the 2x render count. Vue and Svelte, with the *coarser* whole-form parent subscription, both land at the clean baseline. This rules out "parent subscribes too broadly" as the mechanism, and points instead at something specific to how each framework's rendering model responds to a parent re-render — most plausibly, **React re-executes every unmemoized child function component whenever its parent re-renders, regardless of whether that child's own props changed, while Vue's and Svelte's compiler-driven fine-grained reactivity does not force child re-execution just because a parent's local reactive state changed.** This is a genuine, testable hypothesis, not yet confirmed — see Design.
  - This hypothesis does **not**, on its own, cleanly explain the *exact* 2x arithmetic (if React's parent re-render cascaded to *all* 10 unmemoized children on every keystroke, the total would be far higher than 40 — closer to 200, matching the render counts TanStack/felte show on this same surface). The real mechanism is more specific than a blanket cascade-to-everyone theory, and Phase 2 exists specifically to nail down what it actually is rather than have this spec assert an unverified explanation.
- Neither app uses `StrictMode` (which would double-invoke renders in dev mode); all three are served from production `vite preview` builds via the existing Playwright bench infra — so it's not a dev-mode artifact.
- Neither React's nor Vue's adapter package (`packages/adapters/react/`, `packages/adapters/vue/`) currently has any component-level test coverage. React's adapter package has **zero tests of any kind** — no test runner references, no `react-dom`/testing-library devDependency. Vue's one existing test (`packages/adapters/vue/test/set-errors.test.ts`) runs the `useVueForm` composable inside a bare `effectScope()`, never mounting a real component tree.

So the real gap this item closes is: **neutro's React adapter has a real, unexplained 2x re-render cost relative to Vue/Svelte for an equivalent scenario, the mechanism has never been isolated (the naive "dual same-path subscriber" and "cascade to all children" theories don't survive contact with the actual demo structure or arithmetic), and neither React's nor Vue's adapter package has ever had component-level test coverage to investigate it with.**

## Design

### Phase 1: New component-level test infrastructure

Neither React's nor Vue's adapter package can currently mount a real component tree and observe render counts. Add that capability to both — React because it's this item's actual fix target, Vue because Vue's known-good structure (whole-form parent, no cascade) is the most useful available contrast for diagnosing React's behavior, and because Vue's adapter package has the same pre-existing test-coverage gap this item is already fixing for React:

- **`packages/adapters/react`**: add `react-dom` and `@testing-library/react` as devDependencies (react itself is already a peerDependency; `@types/react` is already present). New `packages/adapters/react/test/` directory, naming files by concern (e.g. `rerender-repro.test.tsx`) the same way `packages/adapters/vue/test/set-errors.test.ts` names its one existing file — not yet an established multi-file convention, just a sensible default to follow.
- **`packages/adapters/vue`**: add a real DOM-mounting test utility (`@testing-library/vue`, or `@vue/test-utils` if it fits the existing `effectScope`-based test style more naturally — the implementer should pick whichever integrates with the least friction against the existing `set-errors.test.ts` pattern, and document the choice) as a devDependency. Extend `packages/adapters/vue/test/`.
- Both run through the existing root `vitest.config.ts` (which already excludes only `bench/**`/`node_modules/**` and aliases `@neutro/form-core` to source) plus `jsdom` (already a root devDependency, used by other packages already) — no new top-level test runner or config needed. `vue` itself is resolvable today without an explicit devDependency (confirmed by the existing Vue adapter test importing `effectScope` successfully) — the implementer should trace exactly why (workspace hoisting via another package's dependency, e.g. VitePress's own `vue` dependency) and add an explicit `vue` devDependency to `packages/adapters/vue/package.json` if the implicit resolution is fragile, rather than leave it implicit.

### Phase 2: Minimal repro + root-cause

Build two minimal repros — one per framework — each mirroring the *actual structure* found in its respective bench demo (not a synthetic worst case, the real shape confirmed in the Problem section):

- **React repro, variant A (demo-faithful)**: a parent component with a `subscribeToPath('field0', ...)` subscription (matching the real demo's field-specific parent), rendering a list of child components, one of which (`field0`) subscribes to `field0` via the *exact same hand-rolled pattern the real demo uses* — `useSyncExternalStore((cb) => form.subscribeToPath('field0', cb), () => form.get('field0'))`, with fresh inline functions each render, **not** the adapter's `useFormPath` hook. This must faithfully reproduce the demo's actual code, per Phase 2's own fidelity requirement — building it against `useFormPath` instead would test the wrong thing.
- **React repro, variant B (adapter's real hook)**: identical structure, but the `field0` child uses the adapter's actual `useFormPath` hook (stable `useCallback`-wrapped `subscribe`/`getSnapshot`) instead of the hand-rolled version. Comparing variant A's count against variant B's is the direct test of hypothesis 0 below.
- **Vue repro**: the same shape as variant A/B's parent, but with the parent's subscription changed to match Vue's real demo (`form.subscribe(...)`, whole-form) rather than React's field-specific one, and the child using the adapter's real `useVueFormPath` (matching what Vue's demo already does) — this is a deliberately *different* parent structure per framework, matching what's actually deployed, not an artificially matched pair. Count the same way.

Use these repros to test concrete hypotheses via `systematic-debugging` discipline — form a hypothesis, test it against the repro, don't guess-and-patch. The Problem section's investigation ruled out two of the original theories already (dual same-path parent+child subscription — false, since Vue/Svelte's parents subscribe even *more* broadly and still hit the clean baseline; blanket cascade-to-all-children — arithmetically inconsistent with the observed 2x rather than ~10x). Concrete hypotheses to test, roughly in order of how well-evidenced they already are:
0. **Non-memoized `useSyncExternalStore` callback-identity hypothesis (most evidence-backed going in):** does variant A (hand-rolled, unstable `subscribe`/`getSnapshot` identity every render) reproduce the extra render(s) that variant B (adapter's `useFormPath`, stable identity) does not? If confirmed, the real fix may not touch `packages/adapters/react/src/index.ts` at all — the adapter's `useFormPath` may already be correct, and the actual finding is "the bench demo doesn't use the adapter's own hook and should" (see the Out of Scope note on this exact scenario). This would still be a genuine, valuable finding — just one that changes where the fix lands.
1. **Memoization-boundary hypothesis**: independent of hypothesis 0, does wrapping the React child in `React.memo` (or an equivalent bail-out) eliminate any *remaining* extra render(s) (test against whichever of variant A/B still shows an anomaly after hypothesis 0 is resolved)? This tests whether React's lack of an automatic props-unchanged skip (vs. Vue's/Svelte's compiler-driven dependency tracking) is a separate, additional mechanism.
2. **Partial-cascade hypothesis**: if a cascade-style effect is real but *not* blanket (i.e., something limits it to exactly field0 rather than all 10 fields), what is that something? Trace `useSyncExternalStore`'s exact re-render-triggering behavior in React 18/19 — does it force a synchronous re-render of *only* the subscribed component when its own snapshot changes, and separately, does the parent's own re-render (if it happens at all, and how often) additionally re-invoke `field0`'s child specifically without touching the other 9? This hypothesis requires literally counting parent re-renders in the repro, not just the child's count, to distinguish "child renders twice from its own subscription firing twice" from "child renders once from its own subscription plus once from a parent cascade."
3. **`useSyncExternalStore` double-notification-from-core hypothesis (least likely, keep as a cheap rule-out):** does neutro's `notify()`/`notifyPathSubscribers` (`packages/core/src/engine.ts:236-281`) call a single path's subscribers more than once per `set()` call? Reading the real implementation during this spec's own review found no such mechanism for a scalar field like `field0` — `notifyPathSubscribers` accumulates a `Set` and iterates each entry exactly once, so this hypothesis's originally-stated mechanism (an "ancestor-notification pass" re-hitting the same path) does not exist in the current code as read. Keep this as a fast, cheap empirical rule-out (mount the child alone, no parent, count) rather than a live suspect — if it were true, Vue and Svelte would show the same doubling, which they don't, so this is expected to fail and mainly serves to close off the "is this a core bug" question definitively before Phase 3.

Document whichever hypotheses are confirmed or ruled out, with the repro test as evidence, before proposing any fix. If none of the above pan out, that's a signal to escalate (more repro variations, or flag to the user) rather than ship a spec-mandated theory that turned out to be wrong.

### Phase 3: Fix (if warranted) + re-verify

- **If hypothesis 0 is confirmed (the demo's hand-rolled `useSyncExternalStore` usage, not the adapter, is the cause):** the adapter itself needs no code change — `useFormPath` already does the right thing. The fix is updating `bench/apps/react/src/SchemaValidateNeutro.tsx`'s `Field` component to use the adapter's `useFormPath` hook instead of hand-rolling `useSyncExternalStore`, which is a `bench/apps/*` change — flagged here as an explicit exception to the Out of Scope section's default "no demo changes" stance, since it's the direct, evidence-driven consequence of this exact finding, not scope creep. This is still a valuable outcome: it documents a real anti-pattern (inline, non-memoized `useSyncExternalStore` arguments) worth calling out even though the shipped adapter was never broken.
- **If root-cause instead finds a genuine, fixable inefficiency inside `packages/adapters/react/src/index.ts` itself** (e.g., hypothesis 1 or 2 holds even with `useFormPath`'s stable callbacks), fix it there, confirm via the Phase 2 repro test (render count drops to the expected value), and re-run the full test suite for both adapter packages plus `packages/core/test/` to confirm no regression. A Vue-side code change is not anticipated (Vue is already at baseline) — if Phase 2's Vue repro somehow surfaces a real Vue-side issue despite the demo-level numbers looking clean, treat that as a genuine, disclosed surprise finding and flag it to the user before fixing, since it wasn't anticipated by this spec.
- Whichever of the above lands, re-run the existing browser-level `bench/suites/browser/schema-validate-rerenders.spec.ts` (already covers all three frameworks, no new browser test needed) to confirm the real, browser-measured `neutro/form (React)` number moved in the expected direction. **Before this re-run, kill any stale Playwright preview servers on ports 4173-4175** (`bench/playwright.config.ts` sets `reuseExistingServer: !process.env.CI` on all three preview servers, which silently serves a stale build if a preview server from an earlier run is still bound to those ports locally). This is a general hygiene precaution for any local Playwright re-run in this repo, not a claim about what caused item 3's original wrong Vue number — that number's actual cause, per the `project_v050_release_gate` memory (line 26) and commit `5fac9ba`, was a render-counter reset bug in `App.vue` zeroing orphaned local objects instead of the live `window.__neutroSchemaRenders`, unrelated to preview-server staleness (the memory's own account mentions killing stale servers only as a precaution taken *during* that fix's verification, not as the bug's cause). If the number moves enough to be worth republishing, regenerate `docs/benchmarks/index.md` per the established pipeline (`bench:merge`/`bench:generate`, copying `latest.json` → `baseline.json` first per the documented local-run convention) and disclose the before/after numbers plainly.
- If root-cause instead shows the gap is inherent to React's own re-render/batching model (not something neutro's adapter code controls or could avoid without a fundamentally different subscription API), document that finding precisely — which mechanism, why it's out of neutro's control, with the repro tests kept as permanent regression coverage proving the *current, understood* behavior — and stop. No fix should be forced where none is warranted; this is an acceptable, honest outcome per this cycle's established standard (matching item 6's "no bug found, mechanism confirmed nesting-agnostic" outcome).

## Expected outcome / hypothesis

Not yet known which of Phase 2's four hypotheses (0-3) will hold — this is genuinely open, unlike some of this cycle's earlier items where a specific mechanism was already suspected with reasonable confidence. The Round-1 correction above already ruled out the two theories the original draft implicitly leaned on (dual-same-path-subscriber, blanket-cascade), and hypothesis 0 (found during Round-2 review) is the best-evidenced live candidate going into Phase 2. Three broad possible final outcomes, all real findings either way:
- **If hypothesis 0 is confirmed:** the adapter itself needs no fix (`useFormPath` already avoids the problem); the fix is to `bench/apps/react/src/SchemaValidateNeutro.tsx` (an explicit, narrow Out of Scope exception — see below), `neutro/form (React)`'s browser-measured count should drop toward Vue/Svelte's 20, and both adapter packages still gain permanent component-level test coverage they currently entirely lack.
- **If hypothesis 1 or 2 confirms a real, fixable inefficiency inside the adapter itself** (present even when using `useFormPath`'s stable callbacks): Phase 3 fixes `packages/adapters/react/src/index.ts`, the same browser-count improvement is expected, and the same test-coverage gain applies.
- **If none of hypotheses 0-2 hold** (and hypothesis 3's core-engine rule-out, as expected, also comes back negative): the gap is an inherent React rendering-model cost not otherwise explained. This is disclosed precisely (which exact mechanism, with the repro tests as evidence — not hand-waved as "just how React works"), the repro tests still ship as permanent coverage proving both adapters behave as understood, and the finding becomes documentation (likely a note near the schema-validate-rerenders numbers in `docs/benchmarks/index.md`, since the existing "reflecting each adapter's own subscription granularity" language is now known to be an inaccurate simplification per the Problem section) rather than a code change.

## Out of Scope

- `packages/core/` — this item is about adapter-level render behavior, not the core engine's `notify`/`pathSubscribers` mechanism itself, **unless** Phase 2's hypothesis 3 (`useSyncExternalStore` double-notification) confirms the double-notify originates in `notify()`/`pathSubscribers` itself rather than in React's own rendering response to a single notification — in that case the cause is core-engine-level, not adapter-level, and is a genuine scope-expansion trigger: stop and flag it to the user rather than silently expanding scope, since it would change this item's blast radius significantly (a core-engine bug would affect Vue's and Svelte's adapters too, contradicting their clean baseline numbers — which would itself be a strong signal the double-notify theory is wrong, but must be confirmed empirically, not assumed).
- A Vue-side *fix* — per the Round-1 correction, Vue is not anomalous (matches Svelte's baseline already). Vue's new test infrastructure and repro (Phase 1/2) exist to provide a contrast baseline for diagnosing React, not because Vue itself needs fixing. If Phase 2 unexpectedly surfaces a real Vue-side issue anyway, that's a disclosed surprise finding per Phase 3, not a planned deliverable of this item.
- Solid and Angular adapters — item 3's `schema-validate-rerenders` surface never measured them (no comparable data exists), so there's no signal to investigate for either. A future item, not bundled here.
- `bench/apps/*` demo component changes, **by default** — with one explicit, already-anticipated exception: if Phase 2 confirms hypothesis 0 (the React demo's hand-rolled, non-`useFormPath` `useSyncExternalStore` usage is the actual cause — see Problem section and Phase 3), the fix to `bench/apps/react/src/SchemaValidateNeutro.tsx` is in scope, since it is the direct, evidence-driven consequence of that specific finding, not open-ended demo cleanup. Vue's and Svelte's demos are, by contrast, confirmed by direct inspection during this spec's own investigation to already use their adapters' real per-field hooks (`useVueFormPath`, `useSvelteFormPath`) — no equivalent exception is anticipated for them. Any other demo-structure finding beyond hypothesis 0 becomes a disclosed finding for the user to weigh, not an automatically-in-scope fix.
- Republishing `docs/benchmarks/index.md` unconditionally — only regenerate if Phase 3 lands a real fix with numbers worth updating; a documented-inherent-cost outcome does not, by itself, require a docs page change beyond correcting the now-known-inaccurate "subscription granularity" explanation already published there (matching the "no docs changes unless genuinely noteworthy" default used throughout this cycle for items 5-7, while still fixing a now-identified inaccuracy).
- React Native — no such adapter exists in this codebase; irrelevant to this item.
