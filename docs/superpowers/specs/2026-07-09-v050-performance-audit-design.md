# v0.5.0 Performance Audit — Design

Date: 2026-07-09
Status: Approved (design phase)
Release gate: v0.5.0, item 7 of 7 (see memory `project_v050_release_gate`) — runs now, before items 3-6

## Problem

The modular bundle-splitting work (release-gate item 2) hoisted `createForm`'s closure state into a shared `ctx` object and relocated feature clusters into `attachX(ctx, config?)` modules. This achieved its goal (a working `@neutro/form/core/minimal` tier, ~33% smaller gzip) but introduced two measured, previously-undisclosed costs, found only after the fact by directly re-benchmarking against a pre-split worktree:

1. **`set-get.bench.ts` (the hottest write path, `setFieldValue`) is ~2-5% slower** — median-of-3 runs, old vs new, across all three fixture sizes (small/large/xlarge). The likely cause: `setFieldValue` now calls `ctx.isComputedField(path)` and `ctx.hasComputedFields()` through function-pointer indirection on every write, replacing the old direct `computedMap.has(path)` / `computedMap.size > 0` checks. The plan's own Risk section predicted this indirection was "unlikely to be measurably slower" — it was wrong, though the actual cost is modest.
2. **The full `@neutro/form/core` tier's own gzip size grew ~16%** (10,414 → 12,107 bytes), confirmed via git history of `bench/results/bundle-size.json` and independently reproduced by building both the pre-split and current commits in a worktree and comparing `packages/core/dist/index.js` directly (35,335 → 43,086 bytes raw, +414 source lines across the split files). Root cause understood in general terms (the mutation-invariant two-phase conversions replaced concise reassignment with more explicit code; the hook-composition pattern defines each hook twice — a no-op default plus a real override in a separate file) but never quantified or root-caused precisely, and never weighed as a conscious tradeoff.

Since v0.5.0 treats performance as the axiom immediately behind correctness, these costs — and any others hiding in the other 8 core benchmark suites that were never re-checked after the split — need to be found, understood, and fixed (where fixable without compromising correctness) before the release ships, not discovered later by a user.

## Non-goals

- **No re-litigating the mutation invariant or hook-composition design.** Both are load-bearing correctness properties from release-gate item 2, established through 7 spec-review rounds and 3 plan-review rounds. This audit optimizes *within* that design, not around it — a fix that reintroduces reassignment-based state or removes a hook slot to save bytes/cycles is out of scope, no matter how much it would help the numbers.
- **No new benchmark suites.** The 9 existing suites under `bench/suites/core/` are the measurement surface. If a suite doesn't cover something worth checking, that's a finding for a future spec, not scope creep into this one.
- **No speculative fixing.** Nothing gets "optimized" without a real, reproducibly-measured (median-of-3-or-more, not single-run) regression to justify it. Single-run bench comparisons have shown ~15% run-to-run noise on identical code in this repo; a fix without a real measured problem behind it is not in scope.

## Design

### Stage 1 — Measurement

**Method** (established and validated during this spec's own investigation): create ONE scratch git worktree at `7b383e9d5c8e524f3e0a700c59d5bb275548c27f` (the commit immediately before release-gate item 2's first commit) up front, reused across all 9 suite files — do not create/remove a worktree per suite, only `bench/vitest.config.ts`'s alias changes between measurements. For each of the 9 suites under `bench/suites/core/`:

1. Temporarily point `bench/vitest.config.ts`'s `@neutro/form-core` alias at the shared worktree's `packages/core/src/index.ts`.
2. From the `bench/` directory, run `BENCH_OUTPUT_FILE=/tmp/perf-audit-old-<N>.json pnpm exec vitest bench suites/core/<suite>.bench.ts --run --reporter=./reporters/json-bench.ts` three times (minimum — more if the spread between the 3 runs is wide enough to leave the verdict ambiguous, per the noise levels already observed). Inline the env var directly (no `cross-env` prefix) — `cross-env` is only needed for Windows env-var syntax and this repo's own `bench:core`/`bench:core:sample` scripts invoke it through pnpm's script runner, which puts `.bin` on PATH; a manually-typed command does not have that PATH entry, so a bare `cross-env` invocation fails with "command not found" here. **Do not use a bare `vitest bench --run` with the default console reporter** — the default table has no `median` field at all (`hz`/`mean`/`p75`/etc. only); `median` (a time statistic, ms) only exists on tinybench's result object and is captured exclusively by this repo's own `bench/reporters/json-bench.ts`. The JSON reporter groups by **describe-block name as the top-level key**, not by suite file name — each core suite wraps its bench(es) in one `describe(...)` per block, so a 3-block file like `set-get.bench.ts` produces THREE top-level keys (`"set-get/small"`, `"set-get/large"`, `"set-get/xlarge"`), each mapping to a single-element array: `{ "set-get/small": [ { "library": "neutro/form", "median": ..., "opsPerSec": ..., "rme": ..., "samples": ... } ] }`. Extract `median` via `output["<describe-block-name>"][0].median` — do NOT try to disambiguate multiple blocks by `library` within one array; every core suite's `library` is always `"neutro/form"`, so it carries no block identity. Identify blocks by their top-level key.
3. Restore the alias to point at current `main`'s source, run the same suite 3+ times the same way, into `/tmp/perf-audit-new-<N>.json`.
4. Record the **median of the three (or more) `median` (ms) values** per bench block (i.e. per top-level JSON key), old vs new — use `median` (ms), not `opsPerSec`/hz, for every suite uniformly. This removes any risk of comparing different units across suites or getting the improvement/regression direction backwards.
5. Restore `bench/vitest.config.ts` to its committed state before moving to the next suite file (the alias, not the worktree, is the only per-suite state — the worktree itself is created once and removed once, after all 9 suite files are done).

**Suites to measure** (all 9 files under `bench/suites/core/`, 21 bench blocks total — the findings doc must have 21 rows, not 9): `array-ops.bench.ts` (2 blocks: remove, move), `array-ops-scale.bench.ts` (3 blocks: remove-start, remove-end, remove-start-with-unrelated-fields), `computed-fields.bench.ts` (1 block), `dependency-chain.bench.ts` (1 block), `dependency-scopes.bench.ts` (1 block), `nested-set.bench.ts` (1 block), `schema-validate.bench.ts` (4 blocks: zod small, zod large, yup small, yup large), `set-get.bench.ts` (3 blocks: small/large/xlarge — already measured once during this spec's investigation; re-measure formally with the JSON-reporter methodology above so the numbers are captured consistently alongside everything else, not left as an ad-hoc side note recorded a different way), `ssr-mount.bench.ts` (1 block — this file also contains an unrelated `test()`/`expect` block; `vitest bench` ignores it, the JSON reporter only walks benchmark tasks, so it's harmless noise, not a 22nd row), `subscriptions.bench.ts` (3 blocks). Know this inventory going into Stage 1 so the sequential-vs-parallel timing question (see Open Questions) can be answered against a real number of runs (21 blocks × 6+ runs each = 126+ individual bench invocations minimum), not guessed at.

**`setFieldValue`-driven cluster**: `set-get`, `subscriptions` (all 3 sizes), `dependency-scopes`, `dependency-chain`, and `nested-set` all drive `a.set(...)` through the exact same `setFieldValue` code path in `engine.ts` that the already-confirmed hook-indirection cost lives in (`ctx.isComputedField`/`ctx.hasComputedFields`, `engine.ts:608`/`:636`). If that indirection is real, expect it to surface (diluted by each suite's own overhead) across this whole cluster, not just `set-get` alone — flag this explicitly when recording Stage 1's findings so Stage 2 doesn't treat `set-get` as an isolated case.

**Bundle size**: no re-measurement needed — `bench/results/bundle-size.json`'s git history already gives a clean before/after (10,414 → 12,107 gzip bytes for the full tier; the minimal tier has no "before" since it's new). This stage's job for bundle size is root-cause investigation (see Stage 2), not remeasurement.

**Verdict threshold**, stated concretely to remove any direction/unit ambiguity: a bench block is a **regression** iff `(new_median_ms − old_median_ms) / old_median_ms > 0.03` (new is slower by more than 3%); an **improvement** iff that ratio is `< -0.03` (new is faster by more than 3%); otherwise **no significant change**. 3% is below the smallest consistent delta this spec's own `set-get` investigation already confirmed real (~2-5%, surviving well below the ~15% single-run noise floor observed on identical code) — conservative enough not to misclassify noise as a regression, sensitive enough to catch anything at or above the magnitude already confirmed real.

**Output**: `docs/superpowers/specs/2026-07-09-v050-performance-audit-findings.md` — one row per bench block (21 rows minimum): old median (ms), new median (ms), % delta, verdict, and a "cluster" tag for any block in the `setFieldValue`-driven group above. This becomes the fix stage's input; nothing in Stage 2 starts until this table exists and is complete.

### Stage 2 — Fix

For every suite/fixture-block classified as a **regression** in Stage 1's findings doc, plus the two already-confirmed issues (`set-get`, bundle-size):

1. **Root-cause investigation** — read the actual relocated code, identify what specifically changed between old and new that plausibly explains the delta. Do not guess; trace it to specific lines, the same way this spec's own bundle-size investigation traced the 16% growth to +414 source lines from the two-phase mutation conversions and the duplicated hook-default/override pattern.
2. **Fix, constrained to the Non-goals above** — the fix must preserve the mutation invariant (no reassignment reintroduced) and the hook-composition pattern (no hook slot removed or collapsed back into a direct cross-cluster call). Within that constraint, apply the least invasive change that measurably helps. Two concrete candidates already identified, to investigate first (not a commitment to implement exactly these — the actual fix depends on Stage 1's findings and Stage 2's root-cause step):
   - **`setFieldValue`'s hook-check cost** (`engine.ts:602-660`) — the cluster splits into two genuinely different cases that a naive fix would conflate:
     - **Early-returning suites (`set-get`, `subscriptions`, `nested-set`)**: their `set()` calls write a value deep-equal to the current one, so `setFieldValue` hits `isDeepEqual(currentVal, val)` at line 618 and returns immediately — it never reaches line 636 at all. The ONLY hook call in their hot path is `ctx.isComputedField(path)` at line 608 (the first statement in the function, evaluated unconditionally before the early return). These three suites' regression, if confirmed by Stage 1, can only be addressed by reducing the cost of that single line-608 call — hoisting `ctx.hasComputedFields()` to gate it (`if (hasComputed && ctx.isComputedField(path))`) does NOT help here and would be a net-neutral-or-worse change for this group, since it adds a `hasComputedFields()` call to a path that currently makes zero such calls before the early return, for no offsetting removal (the line-636 call it also short-circuits is never reached anyway in this group). Do not apply the hoist to this group; if their regression is real, the fix has to target the line-608 call itself (e.g., confirm `isComputedField`'s no-op-default implementation is as cheap as it can be, or investigate whether the call can be skipped entirely when `ctx.hasComputedFields()` is already known false from a prior write in the same batch — a genuinely different, smaller optimization, not this candidate).
     - **Value-changing suites (`dependency-scopes`, `dependency-chain`)**: their `set()` calls write a genuinely new value each time, so execution reaches both line 608 (`isComputedField`) and line 636 (`hasComputedFields`). For this pair, hoisting `const hasComputed = ctx.hasComputedFields();` before line 608, gating it as `if (hasComputed && ctx.isComputedField(path))`, and reusing `hasComputed` at line 636 is behavior-preserving (`!hasComputedFields() ⇒ !isComputedField(path)` for any path) and genuinely reduces 2 indirect ctx-hook calls to 1 per write when no computed fields are configured.
     - Acceptance gate: re-run all 5 cluster suites regardless of which group a fix targets, since both groups share `setFieldValue` and either fix could in principle move the other group's numbers too (even if the mechanism given above says it shouldn't) — verify, don't assume.
   - **Array-ops `validatedPaths`-tail consolidation, authorized as a bundle-size fix only** — `shiftStateIndices`, `rekeyArrayState`, and `arraySwap`'s `swapKeys` (`features/array-ops.ts`) are *structurally parallel* (each does a two-phase "collect, then delete, then write" pass over the tracked-state maps) but are **not near-identical**, and the shareable slice is narrower than it first appears: `rekeyArrayState` (lines 204-224) and `arraySwap`'s validated-tail (lines 390-410) both build a `validatedRenames: Array<[string, string]>` pair list, then run a clean, separated delete-all-old / add-all-new pass over it — these two genuinely match and are the safe consolidation target (extract just the two apply-loops — delete+unindex all old keys, then add+index all new keys — as a helper taking a pre-built `[oldKey, newKey][]` array; the pair *computation* itself stays per-function, since `rekeyArrayState`'s numeric-regex/sliding-window transform and `arraySwap`'s exact-or-dot-child string matcher are genuinely different). `shiftStateIndices` (lines 93-125) does **not** match this shape: it stores only new-key strings (not `[old, new]` pairs) and deletes `ctx.validatedPaths`/calls `ctx.unindexKey` *inline*, interleaved inside its numeric-regex/±1-index compute loop, not as a separated phase-2 pass — it would need its own refactor (stop deleting inline, build a pair list first) before it could even become a third caller of the shared helper. Scope this fix to `rekeyArrayState`+`arraySwap` only; treat folding in `shiftStateIndices` as a separate, larger follow-up decision, not part of this fix. This fix is authorized *only* as a bundle-size recovery (the growth is measured and real); any runtime effect on `array-ops`/`array-ops-scale` must be neutral-or-better — a guardrail to re-verify, not a goal to chase. Do not pursue this for runtime reasons unless Stage 1 actually flags `array-ops`/`array-ops-scale` as regressions.
3. **Verification**: the specific bench block(s) that flagged the regression — plus every other block in the same causal cluster per the note above — must be re-run (median-of-3+, worktree-vs-current methodology, using the JSON-reporter `median`-ms metric from Stage 1) and show the new numbers within the ±3% no-significant-change band of the pre-split baseline, or better. The full existing test suite must stay green with zero behavior change (this is a performance-only stage — any fix that changes observable output is a correctness bug, not a valid fix, per this spec's own axiom ordering: correctness first, performance second).
4. **Discipline**: same as the rest of this release cycle — fresh implementer per fix, fresh independent reviewer, the specific benchmark as an explicit acceptance gate (not just "tests pass").

### Bundle-size fix, specifically

Unlike the other regressions (which have a bench suite as a direct acceptance test), the bundle-size fix's acceptance test is re-running `bench/scripts` bundle-size measurement (same script Task 14 of release-gate item 2 wired up) and confirming the full tier's gzip number has measurably decreased from 12,107 bytes, ideally back toward (not necessarily all the way to) the pre-split 10,414-byte baseline — full reversion isn't the bar, since some of the growth is the direct, accepted cost of correctness properties (the mutation invariant, the hook slots) that this spec's Non-goals explicitly forbid unwinding. The bar is: recover what's recoverable (e.g., the array-ops duplication above) without touching what's load-bearing.

## Testing

1. Stage 1 produces a findings doc with zero code changes — no tests needed for this stage itself, but the doc's own numbers must be independently spot-checked by a second pass before Stage 2 starts (re-run at least 2 of the 21 bench blocks' measurements independently, confirm they match the findings doc's own numbers within reasonable variance) — this mirrors the "don't trust a single measurement pass" lesson this spec's own investigation already learned the hard way.
2. Stage 2's fixes are verified against: (a) the specific flagged bench block(s)' median (ms), back within the ±3% band, including every other block in the same causal cluster for the `setFieldValue` fix; (b) the full existing `packages/core/test` suite, zero behavior change; (c) `pnpm lint && pnpm exec tsc --noEmit && pnpm build && pnpm test` (full monorepo), green.
3. A final whole-phase review re-confirms: every regression identified in Stage 1's findings doc was either fixed-and-reverified or explicitly and consciously left as an accepted tradeoff (documented in the findings doc with a stated reason) — nothing silently falls through the cracks between "found" and "shipped."

## Risks

- **Bench noise could produce a false-negative or false-positive verdict for a suite near the ±3% threshold.** Mitigated by the median-of-3-or-more methodology and by widening the sample count for any suite whose 3 runs don't cluster tightly.
- **A fix for one suite could regress another** (e.g., consolidating the array-ops two-phase helper could subtly change `array-ops-scale.bench.ts`'s numbers even if it helps `array-ops.bench.ts`). The fix-stage verification step must re-run every suite touched by a given fix, not just the one it targeted.
- **The bundle-size fix has a real floor** — some of the 16% growth is the accepted, load-bearing cost of item 2's design. Stage 2 must not chase full reversion at the expense of the Non-goals; a smaller, honestly-reported recovery is a valid outcome.

## Open questions for the implementation plan

- Exact ordering of the 21 bench-block measurement runs (126+ individual invocations at 6 runs/block minimum) — sequential per-suite is safest (avoids resource contention skewing numbers, and matches the alias-swap-per-suite-file granularity in Stage 1's method) but slower; the plan should decide based on how long a full sequential pass actually takes once Stage 1 starts.
- The array-ops fix is scoped to `rekeyArrayState` + `arraySwap`'s `validatedPaths` phase-2 rename-tail only, NOT `shiftStateIndices` (which stores/deletes differently and isn't a drop-in third caller — see the corrected Stage 2 candidate above) — decide during planning whether this two-function consolidation alone is worth a dedicated task, or should be folded into the bundle-size fix task as one step, given its scope is narrower than the original "consolidate all three loops" framing.
