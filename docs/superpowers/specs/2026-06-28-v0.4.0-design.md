# v0.4.0 Design Spec

## Overview

v0.4.0 promotes two prototype features to stable, ships a breaking type-safety improvement, and defers React Native to 0.5.0.

**Scope:**
1. **Computed fields** — promote from prototype to stable, with nested object config, transient marker, and configurable pass limit
2. **Runtime path validation** — promote from prototype to stable, with configurable `pathValidation` option
3. **Compile-time path checking + dynamic escape hatches** — breaking change: all path-accepting methods remove `| string` / `| (string & {})` fallbacks; `setDynamic`/`getDynamic` added as escape hatches
4. **React Native adapter** — deferred to 0.5.0

**Non-goals for 0.4.0:**
- React Native adapter
- Array wildcard computed fields (`items.*.price`)
- Dynamic variants beyond `setDynamic`/`getDynamic` (no `touchDynamic`, `setErrorDynamic`, etc.)

---

## Section 1: Release Scope

v0.4.0 is a focused stability release. Every feature shipped is either already prototyped in the codebase or a type-level change with no runtime cost. No new runtime mechanisms are introduced beyond what is described below.

The compile-time path checking change is the only breaking change. Consumers on strict TypeScript with correctly typed paths will compile without modification. Consumers passing computed strings to path methods must migrate to `setDynamic`/`getDynamic`.

## Section 2: Computed Fields

### Overview

Computed fields are derived values that `createForm` maintains automatically. They are declared at form creation, evaluated after every mutation, and included in form state. Computed fields:
- Never enter `wasSet`, so they never contribute to `isDirty()` or `isFieldDirty()`
- Are included in `getPayload()` and the submit snapshot (`onSubmitSuccess`/`onSubmitError`) unless marked `transient: true`
- Cannot be set by the user — `set()` on a computed path is a no-op with a dev warning

### Path support

Computed config mirrors the shape of `initialValues` using nested object notation. Any node with a `fn` property is a computed leaf; any node without one is a traversal namespace. Depth inherits the existing 50-segment internal guard; no separate user-configurable depth limit. Array wildcard computed fields (`items.*.price`) are out of scope for 0.4.0.

### `ComputedConfig<T>` type

The config type is a recursive mapped type. At any level, a key either terminates with a computed leaf or continues as a namespace:

```ts
type ComputedLeaf<T, V> = {
  fn: (values: T) => V;
  transient?: boolean;
};

type ComputedConfig<T, Root = T> = {
  [K in keyof T]?: T[K] extends object
    ? ComputedLeaf<Root, T[K]> | ComputedConfig<T[K], Root>
    : ComputedLeaf<Root, T[K]>;
};
```

`Root` threads the original `T` through so every `fn` always receives the full form values, not a subtree.

### Evaluation model

After every mutation, `runComputedPass` runs up to `computedPassLimit` passes (default: 5). Each pass:
1. Runs all computed `fn` functions against the current values snapshot
2. Writes results via `setNestedValue`
3. Exits early if no computed value changed in the pass

If the pass limit is reached without stabilizing, a dev warning fires. This guards against accidental circular computed definitions (e.g. field A derives from B, B derives from A).

The pass limit replaces the current hardcoded 2-pass cap in `runComputedPass`. The same limit applies to the init-time seeding call (`runComputedPass()` at `createForm` init) so initial computed values are derived under the same constraints as runtime mutations.

### Transient marker

`transient: true` on a computed field declaration excludes that field from:
- `getPayload()` — the public snapshot of current values
- The `valuesSnapshot` argument passed to `onSubmitSuccess` and `onSubmitError`

The value still lives in internal form state and is accessible via `get()` and all subscribers. It exists for frontend-only derived values (e.g. display totals, UI flags) that must not reach the server.

### API shape

```ts
createForm({
  initialValues: {
    qty: 1,
    unitPrice: 10,
    total: 0,
    pricing: { vat: 0 },
  },
  computedPassLimit: 5, // optional, default 5
  computed: {
    total: { fn: (v) => v.qty * v.unitPrice },
    pricing: {
      vat: { fn: (v) => v.total * 0.2, transient: true },
    },
  },
})
```

### Internal implementation

At `createForm` init time, the nested `ComputedConfig<T>` is recursively walked once and flattened to a `Map<string, { fn: (values: T) => unknown; transient: boolean }>` keyed by dot-notation path (e.g. `"pricing.vat"`). This flat map is what `runComputedPass` iterates — no per-mutation traversal of the config object.

The prototype used bare functions (`computed: { total: (v) => v.qty * v.unitPrice }`). The stable API wraps them in `{ fn, transient? }` objects. The prototype config shape is removed; there is no compatibility shim since it was never public API.

### Documentation deliverables

- New guide: `docs/guides/computed-fields.md` — what they are, nested notation, transient, pass limit, chaining example, circular guard
- `docs/api/core.md` — add `computed`, `computedPassLimit` to the `createForm` config reference

### Stability

Promoted from prototype to stable in 0.4.0. The `describe.skip('computed fields prototype (0.4.0 candidate)')` block in `packages/core/test/form.test.ts` is unskipped and expanded with full coverage:
- Top-level computed fields
- Nested computed fields
- `transient: true` excluded from `getPayload()` and submit snapshot
- `transient: false` (default) included in `getPayload()` and submit snapshot
- Pass limit with circular guard (dev warning at limit)
- `set()` on computed path is a no-op with dev warning
- Dirty isolation — computed paths never in `wasSet`, never dirty
- Init seeding — computed values correct before first user interaction

## Section 3: Runtime Path Validation

### Overview

`buildPathTrie` constructs a trie from all known paths at `createForm` init time. On every `set()`, `get()`, `touch()`, etc. call, `isKnownPath` checks the trie and warns on unknown paths.

Currently dev-only and always-on. In 0.4.0 this becomes explicit and configurable.

### Config

```ts
createForm({
  pathValidation: 'dev' | 'always' | 'off', // default: 'dev'
})
```

| Value | Behavior |
|-------|----------|
| `'dev'` | Warn in development (`NODE_ENV !== 'production'`), silent in production. **Default.** |
| `'always'` | Warn regardless of `NODE_ENV`. For SSR or environments without a clear dev/prod boundary. |
| `'off'` | Disable entirely. Trie is never built; `isKnownPath` check is skipped. Zero overhead. |

The trie is only constructed when `pathValidation !== 'off'`. The `isKnownPath` call is skipped entirely when `pathValidation === 'dev'` and `NODE_ENV === 'production'`.

### Performance

Benchmarked overhead at `'dev'` mode: ~4,900,000 ops/sec, ~0.0002ms mean. Effectively free at any realistic form size.

### Documentation deliverables

- `docs/api/core.md` — add `pathValidation` to the `createForm` config reference

### Stability

Promoted from prototype to stable in 0.4.0. Tests added for all three `pathValidation` modes.

## Section 4: Compile-time Path Checking + Dynamic Escape Hatches

### Overview

All path-accepting methods in `FormInstance<T>` remove their `| string` and `| (string & {})` fallbacks, leaving only `Path<T>`. TypeScript catches invalid paths at compile time with no runtime cost. This is a breaking change. `setDynamic` and `getDynamic` are added as explicit escape hatches for runtime-constructed paths.

### Current state

The existing interface is already partially strict — the breaking change is finishing the job consistently:

| Method | Current type | Change |
|--------|-------------|--------|
| `get` | `Path<T>` (already strict) | None |
| `subscribeToPath` | `Path<T>` strict overload + `string` loose overload | Remove loose overload |
| `set` | `Path<T> \| (string & {})` | Remove `(string & {})` |
| `arrayAppend`, `arrayInsert` | `Path<T> \| (string & {})` | Remove `(string & {})` |
| `arrayRemove`, `arrayMove`, `arraySwap` | strict overload + `Path<T> \| (string & {}) \| string[]` loose | Remove loose overload |
| `connect`, `isFieldDirty`, `isFieldValid`, `focus`, `watch`, `getAriaProps`, `resetField` | `Path<T> \| string` | Remove `\| string` |
| `setErrors` | `Record<Path<T> \| (string & {}), string>` | Remove `(string & {})` |

The `(string & {})` pattern was intentional — it prevents widening to `string` while accepting literals, acting as a soft guide. Removing it makes the constraint hard.

### Complete list of methods that go strict

- `set(path, value)`
- `get(path)`
- `subscribeToPath(path, listener)` — loose `string` overload removed
- `connect(path, element)`
- `isFieldDirty(path)`
- `isFieldValid(path)`
- `focus(path)`
- `watch(paths, callback)`
- `getAriaProps(path)`
- `resetField(path)`
- `setErrors(errors)` — key type becomes `Path<T>` only
- `arrayAppend(path, item)`
- `arrayInsert(path, index, item)`
- `arrayRemove(path, index)`
- `arrayMove(path, from, to)`
- `arraySwap(path, from, to)`

### Type enforcement

```ts
// ✅ Valid paths — inferred as Path<T>
form.set('pricing.vat', 0.2)
form.get('total')
form.subscribeToPath('qty', (v) => console.log(v))
form.setError('qty', 'Required')

// ❌ Invalid path — TS error at compile time, zero runtime cost
form.set('pricing.typo', 0.2)
form.get('doesNotExist')
```

### Dynamic escape hatches

```ts
form.setDynamic(runtimePath: string, value: unknown): void
form.getDynamic(runtimePath: string): unknown
```

Only `set` and `get` receive dynamic variants — these are the only methods realistically called with runtime-constructed paths. Other methods accept a `as Path<T>` cast at the call site when truly needed.

### Migration story

- Consumers with correctly typed paths (string literals or variables typed as `Path<T>`): compile unchanged, no migration needed
- Consumers passing computed strings or `string`-typed variables: migrate to `setDynamic`/`getDynamic`

### Documentation deliverables

- New page: `docs/guides/migration-v0.4.md` — lists every method that changed, before/after examples, `setDynamic`/`getDynamic` substitution patterns
- `docs/api/core.md` — add `setDynamic`, `getDynamic` to the instance methods reference; update all method signatures

- `docs/public/playground.html` — add a `setDynamic`/`getDynamic` demo snippet; rebuild `docs/public/form-core.esm.js` from the updated packages
