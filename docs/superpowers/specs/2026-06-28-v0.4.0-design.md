# v0.4.0 Design Spec

## Overview

v0.4.0 promotes two prototype features to stable, ships a breaking type-safety improvement, and defers React Native to 0.5.0.

**Scope:**
1. **Computed fields** — promote from prototype to stable, with nested object config, transient marker, and configurable pass limit
2. **Runtime path validation** — promote from prototype to stable, with configurable `pathValidation` option
3. **Compile-time path checking + dynamic escape hatches** — breaking change: all path-accepting methods remove `| string` / `| (string & {})` fallbacks; `setDynamic`/`getDynamic` added as escape hatches
4. **React Native adapter** — deferred to 0.5.0

**Non-goals for 0.4.0:**
- React Native adapter
- Array wildcard computed fields (`items.*.price`)
- Dynamic variants beyond `setDynamic`/`getDynamic` (no `touchDynamic`, `setErrorDynamic`, etc.)
- Strict path typing in adapter hook `paths` parameters — deferred to 0.5.0 (see Section 4)

---

## Section 1: Release Scope

v0.4.0 promotes two prototype features to stable and ships a breaking compile-time path-safety improvement. New runtime additions in this release: `setDynamic`/`getDynamic` methods, `transient` snapshot filtering in `submit()`, `computedPassLimit` config, `pathValidation` config, and `runComputedPass()` invocation in the `reset()` path.

The compile-time path checking change is the only breaking change for consumers. Consumers on strict TypeScript with correctly typed paths will compile without modification. Consumers passing computed strings to path methods must migrate to `setDynamic`/`getDynamic`.

## Section 2: Computed Fields

### Overview

Computed fields are derived values that `createForm` maintains automatically. They are declared at form creation, evaluated after every mutation, and included in form state. Computed fields:
- Never enter `wasSet`, so they never contribute to `isDirty()` or `isFieldDirty()`
- Are always accessible via `get()` and all subscribers (transient or not)
- Non-transient computed fields are included in the submit snapshot (`valuesSnapshot`); transient ones are excluded from it
- Cannot be set by the user — `set()` on a computed path is a no-op with a dev warning

### Path support

Computed config mirrors the shape of `initialValues` using nested object notation. Any node with a `fn` property is a computed leaf; any node without one is a traversal namespace. Depth inherits the existing 50-segment internal guard; no separate user-configurable depth limit. Array wildcard computed fields (`items.*.price`) are out of scope for 0.4.0.

### `ComputedConfig<T>` type

The config type is a recursive mapped type. At any level, a key either terminates with a computed leaf or continues as a namespace. `NonNullable` is used so optional/nullable object fields (`pricing?: { vat: number }`) still permit namespace recursion:

```ts
type ComputedLeaf<T, V> = {
  fn: (values: T) => V;
  transient?: boolean;
};

type ComputedConfig<T, Root = T> = {
  [K in keyof T]?: NonNullable<T[K]> extends Array<any>
    ? ComputedLeaf<Root, T[K]>
    : NonNullable<T[K]> extends object
      ? ComputedLeaf<Root, T[K]> | ComputedConfig<NonNullable<T[K]>, Root>
      : ComputedLeaf<Root, T[K]>;
};
```

`Root` threads the original `T` through so every `fn` always receives the full form values, not a subtree. `NonNullable` allows optional/nullable object fields (`pricing?: { vat: number }`) to recurse. The `Array<any>` check comes first so array fields are treated as leaves — without it, `Array extends object` is `true` and TypeScript would allow nonsensical numeric index namespacing into array fields.

### Evaluation model

After every mutation, `runComputedPass` runs up to `computedPassLimit` passes (default: 5). Each pass:
1. Runs **all** computed `fn` functions unconditionally — there is no dependency tracking. Every fn executes on every pass regardless of which field changed. Computed `fn` must be pure and cheap; side effects (logging, network calls, heavy computation) are not safe here because they fire on every `set()` call to any field.
2. Writes results via `setNestedValue` directly against the live values object (pass 2 sees writes from pass 1, enabling A→B→C chaining). Bypasses `setFieldValue` and the path trie check.
3. Exits early if no computed value changed in the pass.

If the pass limit is reached without stabilizing, a dev warning fires. This guards against accidental circular computed definitions (e.g. field A derives from B, B derives from A).

The pass limit replaces the current hardcoded 2-pass cap in `runComputedPass`. The same limit applies to the init-time seeding call (`runComputedPass()` at `createForm` init) so initial computed values are derived under the same constraints as runtime mutations.

### Notification contract for computed fields

The current implementation calls `notify()` (no path) after `runComputedPass()` returns true. `notify()` with no argument notifies only **global** subscribers (`subscribe(fn)`) — path subscribers (`subscribeToPath('total', fn)`) are skipped entirely. This means `subscribeToPath('total', fn)` never fires when `qty` changes and `total` is recomputed, which breaks per-field reactivity in all framework adapters.

**Fix required:** `runComputedPass` must return the list of changed dot-notation paths (not just a boolean). The caller must call `notify(changedPath)` for each path that changed, in addition to the global `notify()`. This ensures path subscribers for computed fields receive updates when their derived value changes.

The implementation must also handle the case where `runComputedPass` is called inside `batch()` — changed computed paths should enter the pending set alongside the user-triggered mutation path, and flush together when the batch completes.

### Transient marker

`transient: true` excludes a computed field from the submit snapshot — specifically `valuesSnapshot`, the `Partial<T>` argument passed to the `onSubmitSuccess` and `onSubmitError` config hooks.

It does **not** affect the primary user-facing submit payload. When a user calls `form.submit(async (payload) => fetch(...))` or wires up `handleSubmit`, `payload` comes from `_getPayload()` (DOM-connected paths only) — computed fields are absent there regardless of `transient`, because they are never DOM-connected via `connect()`. The same applies to framework-adapter users who never call `connect()` directly. Transient exclusion is therefore specifically about the lifecycle hooks receiving a full `valuesSnapshot`.

Transient fields remain in internal form state and are accessible via `get()`, `getState().values`, and all subscribers. They exist for frontend-only derived values (e.g. running totals, UI flags) that must not reach the server via the lifecycle hooks.

Non-transient computed fields are included in `valuesSnapshot` like any other field value.

### `reset()` interaction

`reset()` and `reset(newValues)` must call `runComputedPass()` after reinitialising `values`. Without this, computed fields revert to their `initialValues` entries (e.g. `total: 0`) rather than being re-derived from the reset state.

If `reset(newValues)` is called with an explicit value at a computed path (e.g. `reset({ qty: 2, total: 999 })`), the computed pass runs after and silently overwrites the provided value. Computed paths in `newValues` are ignored in favour of the derived result — this is the correct behaviour and should be documented in the computed fields guide.

### API shape

```ts
createForm({
  initialValues: {
    qty: 1,
    unitPrice: 10,
    total: 0,
    pricing: { vat: 0 },
  },
  computedPassLimit: 5, // optional, default 5
  computed: {
    total: { fn: (v) => v.qty * v.unitPrice },
    pricing: {
      vat: { fn: (v) => v.total * 0.2, transient: true },
    },
  },
})
```

### Internal implementation

At `createForm` init time, the nested `ComputedConfig<T>` is recursively walked once and flattened to a `Map<string, { fn: (values: T) => unknown; transient: boolean }>` keyed by dot-notation path (e.g. `"pricing.vat"`). This flat map is what `runComputedPass` iterates — no per-mutation traversal of the config object.

The computed-field no-op guard (which blocks `set()` on computed paths) must also use this flattened map's keys — not `Object.keys(computedFields)` (the raw config's top-level keys). With nested notation, `Object.keys({ pricing: { vat: { fn: ... } } })` returns `["pricing"]`, missing `"pricing.vat"`. If the guard uses raw top-level keys, `set("pricing.vat", ...)` silently bypasses it.

The prototype used bare functions (`computed: { total: (v) => v.qty * v.unitPrice }`). The stable API wraps them in `{ fn, transient? }` objects. The prototype config shape is removed; there is no compatibility shim since it was never public API.

### Benchmark gate

The existing bench files test 1 and 5 computed fields under the old hardcoded 2-pass model. Before computed fields are promoted to stable, the bench suite must be updated to reflect the new 5-pass model and confirm that overhead per `set()` remains within an acceptable bound. This is a hard release gate — "negligible" must be verified, not assumed.

### Documentation deliverables

- New guide: `docs/guides/computed-fields.md` — what they are, nested notation, transient, pass limit, chaining example, circular guard, `reset()` interaction
- `docs/api/core.md` — add `computed`, `computedPassLimit` to the `createForm` config reference

### Stability

Promoted from prototype to stable in 0.4.0. The `describe.skip('computed fields prototype (0.4.0 candidate)')` block in `packages/core/test/form.test.ts` is unskipped and expanded with full coverage:
- Top-level computed fields
- Nested computed fields (including optional parent paths)
- `transient: true` excluded from submit snapshot (`valuesSnapshot`)
- `transient: false` (default) included in submit snapshot
- Pass limit with circular guard (dev warning fires at limit)
- `set()` on computed path is a no-op with dev warning
- Dirty isolation — computed paths never in `wasSet`, never dirty
- Init seeding — computed values correct before first user interaction
- `reset()` re-seeds computed fields; explicit computed values in `newValues` are overwritten
- `subscribeToPath('total', fn)` fires when a source field (`qty`) changes and `total` is recomputed
- Global `subscribe(fn)` receives updated state including recomputed values
- Computed field notifications flush correctly inside `batch()`

## Section 3: Runtime Path Validation

### Overview

`buildPathTrie` constructs a trie from all known paths at `createForm` init time. On every `set()`, `get()`, and other path-accepting method calls, `isKnownPath` checks the trie and warns on unknown paths.

Currently dev-only and always-on. In 0.4.0 this becomes explicit and configurable.

### Config

```ts
createForm({
  pathValidation: 'dev' | 'always' | 'off', // default: 'dev'
})
```

| Value | Behavior |
|-------|----------|
| `'dev'` | Warn on unknown paths in development (`NODE_ENV !== 'production'`), silent in production. **Default.** |
| `'always'` | Warn on unknown paths regardless of `NODE_ENV`. For SSR or environments without a clear dev/prod boundary. |
| `'off'` | Disable entirely. Trie is never built; `isKnownPath` check is skipped. Zero overhead. |

The trie is not constructed when `pathValidation === 'off'` OR when `pathValidation === 'dev'` and `NODE_ENV === 'production'`. Skipping construction in the latter case avoids building a data structure that would never be queried. The `isKnownPath` call is likewise skipped in those same conditions.

Computed field writes via `runComputedPass` call `setNestedValue` directly and do not route through `setFieldValue` — so the path trie check does not fire for computed writes. Computed paths exist in `initialValues` and are therefore in the trie anyway, but the bypass is important to preserve as the implementation evolves.

### Performance

Benchmarked overhead at `'dev'` mode: ~4,900,000 ops/sec, ~0.0002ms mean. Effectively free at any realistic form size.

### Documentation deliverables

- `docs/api/core.md` — add `pathValidation` to the `createForm` config reference

### Stability

Promoted from prototype to stable in 0.4.0. Tests added for all three `pathValidation` modes.

## Section 4: Compile-time Path Checking + Dynamic Escape Hatches

### Overview

All path-accepting methods in `FormInstance<T>` remove their `| string` and `| (string & {})` fallbacks, leaving only `Path<T>`. TypeScript catches invalid paths at compile time with no runtime cost. This is a breaking change. `setDynamic` and `getDynamic` are added as explicit escape hatches for runtime-constructed paths.

**Adapter hooks are explicitly out of scope for 0.4.0.** All five adapters expose their own path parameters (e.g. `useFormField(form, path)`, `useFormPaths(form, paths)`) that currently type as `Path<T> | string`. Tightening those is a parallel breaking change across five separate packages with their own guide examples to update — deferred to 0.5.0 alongside React Native. This means the compile-time guarantee in 0.4.0 is complete at the engine layer; framework users gain it when they call `FormInstance<T>` methods directly.

**`Path<T>` has a compile-time depth cap of 5.** `PathImpl<T>` defaults to `Depth = 5`, generating paths up to 5 levels deep. Paths deeper than 5 levels exist at runtime (via `setNestedValue`/`getNestedValue`) but will not appear in the `Path<T>` union and cannot be expressed as strict `Path<T>` arguments — they require `setDynamic`/`getDynamic`. This is an existing limitation, not introduced in 0.4.0, but the migration guide must document it clearly.

### Current state

The existing interface is already partially strict — the breaking change is finishing the job consistently:

| Method | Current type | Change |
|--------|-------------|--------|
| `get` | strict `Path<T>` overload + loose `string \| string[]` overload returning `any` | Remove loose overload; `getDynamic` covers runtime strings |
| `subscribeToPath` | `Path<T>` strict overload + `string` loose overload | Remove loose overload |
| `set` | strict `Path<T> \| (string & {})` overload + loose `string[]` overload | Remove `(string & {})` from strict overload; remove `string[]` loose overload; `setDynamic` covers both |
| `arrayAppend`, `arrayInsert` | `Path<T> \| (string & {})` | Remove `(string & {})` |
| `arrayRemove`, `arrayMove`, `arraySwap` | strict overload + `Path<T> \| (string & {}) \| string[]` loose | Remove loose overload |
| `connect`, `isFieldDirty`, `isFieldValid`, `focus`, `watch`, `getAriaProps`, `resetField` | `Path<T> \| string` | Remove `\| string` |
| `setErrors` | `Record<Path<T> \| (string & {}), string>` | Remove `(string & {})` |
| `validate` | `Array<Path<T> \| (string & {}) \| string[]>` | Remove `(string & {})` — `string[]` array-of-segments entries remain (e.g. `['items', '0', 'name']` as an alternative to `'items.0.name'`) |

The `(string & {})` pattern was intentional — it prevents literal widening while staying permissive. Removing it makes the constraint hard.

### Complete list of methods that go strict

- `set(path, value)`
- `get(path)`
- `subscribeToPath(path, listener)` — loose `string` overload removed
- `validate(scopePaths?)` — `(string & {})` removed; `string[]` array-of-segments entries remain (e.g. `['items', '0', 'name']` as an alternative to `'items.0.name'`)
- `connect(path, element)`
- `isFieldDirty(path)`
- `isFieldValid(path)`
- `focus(path)`
- `watch(paths, callback)`
- `getAriaProps(path)`
- `resetField(path)`
- `setErrors(errors)` — key type becomes `Path<T>` only
- `arrayAppend(path, item)`
- `arrayInsert(path, index, item)`
- `arrayRemove(path, index)`
- `arrayMove(path, from, to)`
- `arraySwap(path, from, to)`

Note: the global `subscribe(fn: FormSubscriber<T>)` takes no path and is unaffected.

### Type enforcement

```ts
// ✅ Valid paths — inferred as Path<T>
form.set('pricing.vat', 0.2)
form.get('total')
form.subscribeToPath('qty', (v) => console.log(v))
form.focus('qty')

// ❌ Invalid path — TS error at compile time, zero runtime cost
form.set('pricing.typo', 0.2)
form.get('doesNotExist')
```

### Dynamic escape hatches

```ts
form.setDynamic(runtimePath: string, value: unknown): void
form.getDynamic(runtimePath: string): unknown
```

Only `set` and `get` receive dynamic variants — these are the only methods realistically called with runtime-constructed paths. For other methods (e.g. `arrayAppend` to a runtime-determined array field), use a `as Path<T>` cast at the call site:

```ts
// T must be the form values type, not the form instance:
form.arrayAppend(runtimeArrayPath as Path<T>, item)

// If T isn't locally named, use typeof initialValues:
form.arrayAppend(runtimeArrayPath as Path<typeof initialValues>, item)
```

Note: `as Path<typeof form>` is wrong — `form` is `FormInstance<T>`, so that would generate paths into the form object (`"get"`, `"set"`, etc.), not the values. Always cast against `T` or `typeof initialValues`.

This is an explicit opt-out of type safety at that call site, not a silent fallback. The migration guide covers this pattern.

`setDynamic` still respects the computed field guard — calling it on a computed path is a no-op with a dev warning, identical to `set()` behaviour.

### Migration story

- Consumers with correctly typed paths (string literals or variables typed as `Path<T>`): compile unchanged, no migration needed
- Consumers passing computed strings or `string`-typed variables to `set`/`get`: migrate to `setDynamic`/`getDynamic`
- Consumers using other methods with dynamic paths: use `as Path<T>` cast
