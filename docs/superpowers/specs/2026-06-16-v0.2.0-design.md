# @neutro/form v0.2.0 Implementation Design

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship seven targeted quality-of-life improvements to `@neutro/form-core` and one workflow improvement (changelog automation) in strict priority order, without breaking existing runtime behaviour.

**Architecture:** All API additions are additive or use TypeScript overload layering so existing consumers compile and run without changes. The only exception is `classValidatorAdapter`'s expanded type signature for `children`, which is technically a type-level breaking change but is backward-compatible in practice. Each feature is gated behind its own section of this spec; implementations must be delivered in the order listed.

**Tech Stack:** TypeScript, pnpm workspaces, Vitest, VitePress, Biome, GitHub Actions.

**Guiding tenets (carry through every task):**
- Zero runtime regressions — existing unit tests must continue to pass before and after each change.
- Performance is not negotiated — no O(n) work added to hot paths (per-keystroke `set`, `notify`, `runValidation`).
- Fault-tolerant — all new public methods must handle bad inputs gracefully (wrong path, null value, missing DOM) without throwing.
- Test coverage — every new code path gets a test in `packages/core/test/form.test.ts` (or a new file for DOM/panel concerns). Aim for edge cases, not just happy path.
- Documentation — every new API surface gets a JSDoc block in source and a corresponding update in the relevant `docs/` pages.

## Feature 1: Strongly Typed Field Paths

### What and Why

`Path<T>` and `GetPathValue<T, P>` are already defined and exported from `packages/core/src/index.ts` (lines 21–50). The `get()` method already has a typed overload (`get<P extends Path<T>>(path: P): GetPathValue<T, P>`). However, `set()`, array operations, and `validate()` still accept a plain `string`, and the value parameter of `set()` is typed as `any`. This means `form.set('email', 42)` on a `{ email: string }` form doesn't produce a TypeScript error today.

The fix: add typed overloads everywhere plain `string` is accepted, using the `Path<T> | (string & {})` trick for IDE completion without breaking existing consumers who pass computed path strings.

### API Design

**`FormInstance<T>` changes:**

```ts
// Before
set: (path: Path<T> | string | string[], val: any, options?: SetOptions) => void;

// After — typed overload first, loose fallback second
set<P extends Path<T>>(path: P, val: GetPathValue<T, P>, options?: SetOptions): void;
set(path: Path<T> | (string & {}), val: any, options?: SetOptions): void;
```

```ts
// Before
validate: (scopePaths?: Path<T>[] | string[] | string[][]) => Promise<boolean>;

// After
validate(scopePaths?: Array<Path<T> | (string & {})>): Promise<boolean>;
```

Array operations — add typed first overload to each:

```ts
arrayAppend<P extends Path<T>>(path: P, item: ArrayItem<GetPathValue<T, P>>): void;
arrayAppend(path: Path<T> | (string & {}), item: any): void;
// (same pattern for arrayInsert, arrayRemove, arrayMove, arraySwap)
```

Where `ArrayItem<V> = V extends Array<infer U> ? U : any`.

**`FormConfig<T>` changes:**

```ts
// Before
dependencies?: Record<string, string[]>;

// After
dependencies?: Partial<Record<Path<T> | (string & {}), Array<Path<T> | (string & {})>>>;
```

`rules` and `validationMode.fields` already use `Path<T> | (string & {})` — no change needed there.

**New exported utility type:**

```ts
export type ArrayItem<V> = V extends Array<infer U> ? U : never;
```

### Implementation Notes

- All changes are type-only on `FormInstance<T>` (the interface). The implementation body inside `createForm` does not change — it already works with strings. Only the interface declarations change.
- The `(string & {})` trick preserves backwards compatibility: TypeScript treats `Path<T> | (string & {})` as effectively `string`, so all existing call sites continue to compile. But editors will offer completions for the `Path<T>` branch.
- `set`'s typed overload adds value-type safety: passing a number into a `string` field becomes a TypeScript error. This is intentional and the one place where stricter typing could surface errors in existing (type-incorrect) code.

### Blindspot / Known Gap Addressed

`form.set('emal', value)` still doesn't error at runtime, but it now errors at compile time for TypeScript consumers — which is the highest-value catch. Runtime path validation is not in scope for v0.2.0.

### Testing

- All existing tests continue passing with no changes (types are non-runtime).
- Add a test file `packages/core/test/types.test-d.ts` (a type-test file for `tsd` or `vitest`'s `expectTypeOf`) covering:
  - `form.set('email', 'valid@example.com')` — passes
  - `form.set('email', 42)` — type error
  - `form.get('email')` returns `string` not `any`
  - `form.arrayAppend('items', validItem)` — passes
  - `form.validate(['email'])` — passes with a valid path
- Verify `pnpm exec tsc --noEmit` still passes.

### Documentation

- Update the "TypeScript" FAQ in `docs/community.md` — the "Does TypeScript catch typos in field paths?" answer currently says "partially". After this change, value-type safety is enforced. Update accordingly. Remove from the "Honest Gaps" section.
- Add a JSDoc block to `set`'s typed overload explaining the type inference.
- New doc page: `docs/guides/typescript.md` — covers the type utilities (`Path<T>`, `GetPathValue<T, P>`, `ArrayItem<T>`), the overload resolution, and how to express dynamic paths that TypeScript can't infer.

## Feature 2: `resetField` — Reset a Single Field

### What and Why

`form.reset()` resets the entire form. There is no way to restore a single field to its initial value while leaving the rest of the form alone. This is common in UI flows: a user clears one section, or a "clear" button appears next to a single input. The "Honest Gaps" section in `docs/community.md` documents this explicitly.

Internally, `initialValues` is already captured and preserved as a deep clone at `createForm` time (line 646). It is updated when `reset(newValues)` is called (line 1453). All the pieces are in place.

### API Design

```ts
export interface ResetFieldOptions {
  keepError?: boolean;    // retain errors[path] (default: false — error is cleared)
  keepTouched?: boolean;  // retain touched[path] (default: false — touched is cleared)
  keepDirty?: boolean;    // retain dirty[path] (default: false — dirty is cleared)
}
```

On `FormInstance<T>`:

```ts
resetField(path: Path<T> | (string & {}), options?: ResetFieldOptions): void;
```

Behaviour:
1. Reads `getNestedValue(initialValues, path)` — always the value from the most recently confirmed seed (updated by `reset(newValues)` if called).
2. Deep-clones and writes it via `setNestedValue(values, path, deepClone(initialVal))`.
3. Clears `errors[path]`, `touched[path]`, `dirty[path]` unless the corresponding `keep*` option is `true`.
4. Calls `notify(path)` to fan out to subscribers.
5. Dispatches `{ type: 'RESET_FIELD', path }` for devtools.

**Add to `FormAction` union:**

```ts
| { type: 'RESET_FIELD'; path: string }
```

### Implementation Notes

- `resetField` must NOT trigger validation after resetting. The field returns to its initial value silently. If the user wants to validate afterward, they call `form.validate([path])` explicitly.
- When the path points to an array item (`items.0.name`), only that leaf is reset. The array's `errors['items.0.name']`, `touched['items.0.name']`, and `dirty['items.0.name']` are cleared.
- When the path points to an object key (`address`), all nested state under `address.*` should also be cleared. Implementation: iterate `errors`, `touched`, and `dirty` keys and delete any that start with `path + '.'` or exactly equal `path`.
- If `path` does not exist in `initialValues`, `getNestedValue` returns `undefined`. The field value is set to `undefined` — this is intentional and consistent with how `form.set(path, undefined)` works.
- Connected DOM elements for that path need a value sync (same pattern as in `reset()` at line 1461). Reuse that logic in a shared helper.

### Testing

In `packages/core/test/form.test.ts` — add a `'resetField'` describe block:

- `resetField` restores a field value to its initial value
- `resetField` clears `errors[path]` by default
- `resetField` clears `touched[path]` by default
- `resetField` clears `dirty[path]` by default
- `keepError: true` preserves the existing error
- `keepTouched: true` preserves the touched flag
- `keepDirty: true` preserves the dirty flag
- `resetField` on a nested path (`address.city`)
- `resetField` on an array item path (`items.0.name`)
- `resetField` after `reset(newValues)` uses the new seed, not the original
- Subscribers are notified after `resetField`
- `resetField` on a nonexistent path sets the value to `undefined` without throwing

### Documentation

- Update `FormInstance<T>` JSDoc in `packages/core/src/index.ts`.
- Update `docs/api/core.md` with `resetField` signature and options table.
- Update `docs/community.md` FAQ: "Reset a single field to its initial value" moves from the "Honest Gaps" section into the "Resetting & Loading Data" FAQ with a working code example.
- Update the testing package helper `createFormFixture` to expose `resetField` if it wraps `FormInstance`.

## Feature 3: `isValid` Without Calling `validate()`

### What and Why

The "Honest Gaps" section notes: "To know if the current values are valid, call `await form.validate()` and check `Object.keys(form.getState().errors).length === 0`. Disabling a submit button before the user has interacted requires this upfront validation call, which can be jarring."

The solution: add `isValid: boolean | null` to `FormState<T>`. The three-valued type is intentional:
- `null` — the form has not been fully validated yet (initial state, or after `reset()`). Using `null` is honest: we don't know if the current values are valid.
- `true` — the last full validation run (via `form.validate()` with no scope, or via `form.submit()`) found no errors.
- `false` — the last full validation run found at least one error, OR there are current errors in state (e.g., from `setErrors()`).

This allows three UI patterns:

```tsx
// Conservative: button disabled until form is valid (null = disabled)
<button disabled={state.isValid !== true}>Submit</button>

// Optimistic: button enabled until form is known-invalid (null = enabled)
<button disabled={state.isValid === false}>Submit</button>

// Neutral: show state badge
{state.isValid === null && <span>Not validated yet</span>}
{state.isValid === true && <span>Ready to submit</span>}
{state.isValid === false && <span>Fix errors to continue</span>}
```

### API Design

```ts
export interface FormState<T> {
  values: T;
  errors: Record<string, string>;
  touched: Record<string, boolean>;
  dirty: Record<string, boolean>;
  isSubmitting: boolean;
  isValidating: boolean;
  isValid: boolean | null;  // NEW
}
```

Internal variable: `let hasValidated = false`.

`getState()` updated:

```ts
const getState = (): FormState<T> => ({
  values: deepClone(values),
  errors: { ...errors },
  touched: { ...touched },
  dirty: { ...dirty },
  isSubmitting,
  isValidating,
  isValid: hasValidated
    ? Object.keys(errors).length === 0
    : null,
});
```

When does `hasValidated` become `true`?
- When `form.validate()` is called with no arguments (full form validation completes — either synchronously or after async resolution).
- When `form.submit()` completes (which always runs a full `runValidation()`).

When does `hasValidated` reset to `false`?
- When `form.reset()` or `form.reset(newValues)` is called. The form is re-seeded and any previous validity knowledge is stale.

When does `isValid` become `false` even with `hasValidated = true`?
- Whenever `errors` has any key — after `setErrors()`, after a failed field validation, etc.

This means `isValid` is a live derived value: `hasValidated ? errors is empty : null`.

### Implementation Notes

- `hasValidated` must be set AFTER the async validation promise resolves, not before. Inside `runValidation`, track whether it was called without a scope (no `scopePaths`). After resolution, if it was a full-form run, set `hasValidated = true`.
- `setErrors()` does NOT set `hasValidated = true`. Server-injected errors make `isValid` `false` only if `hasValidated` was already `true`.
- Scoped `form.validate(['email'])` does NOT set `hasValidated = true`. Only a full `validate()` call does. This is a deliberate decision: partial validation doesn't mean the whole form is valid.
- The `computeDiff` function in `devtools.ts` checks `isSubmitting` and `isValidating` — add `isValid` to the diff tracking.
- Framework adapters that re-export `FormState<T>` (all 5) automatically pick up the new field — no adapter changes required.

### Testing

Add to `packages/core/test/form.test.ts` in a new `'isValid'` describe block:

- Initial `state.isValid` is `null`
- After `form.validate()` with no errors: `state.isValid === true`
- After `form.validate()` with errors: `state.isValid === false`
- After `form.submit()` on a valid form: `state.isValid === true`
- After `form.submit()` on an invalid form: `state.isValid === false`
- `form.validate(['email'])` (scoped) does NOT change `isValid` from `null`
- `form.reset()` resets `isValid` back to `null`
- `form.setErrors({ email: 'taken' })` after a valid validate: `isValid` flips to `false`
- `form.clearErrors()` after `setErrors` when `hasValidated`: `isValid` flips to `true`

### Documentation

- Update `FormState<T>` JSDoc in source.
- Update `docs/api/core.md` with the `isValid` field entry and the three-value semantics table.
- Update `docs/community.md` FAQ: "`isValid` without running validation" moves from "Honest Gaps" into the "Submission" FAQ section.

## Feature 4: Persistence Middleware

### What and Why

There is currently no built-in way to persist form values to `localStorage` or `sessionStorage`. The FAQ documents a manual workaround using `form.subscribe()`. A packaged persistence adapter removes boilerplate and handles edge cases (storage quota errors, SSR, debouncing, partial restoration when the schema evolves).

### API Design

```ts
export interface PersistenceAdapter<T> {
  /**
   * Called once at form init (via form.hydrate()). Return null/undefined
   * to use initialValues unchanged.
   */
  read(): T | null | undefined | Promise<T | null | undefined>;

  /** Called (debounced) on every form state change. */
  write(values: T): void | Promise<void>;

  /** Called when form.reset() is called without new values. */
  clear(): void | Promise<void>;
}

export interface PersistenceConfig<T extends object> {
  adapter: PersistenceAdapter<T>;
  /**
   * Debounce delay in milliseconds before calling adapter.write().
   * Default: 300. Set to 0 to write synchronously on every change.
   */
  debounceMs?: number;
  /**
   * Field paths whose values should NOT be persisted. Useful for passwords,
   * one-time tokens, and file inputs.
   */
  exclude?: Array<Path<T> | (string & {})>;
}
```

Add to `FormConfig<T>`:

```ts
persistence?: PersistenceConfig<T>;
```

Add to `FormInstance<T>`:

```ts
/**
 * Reads stored values from the persistence adapter (if configured) and
 * merges them into the form as new initialValues. Must be called manually
 * after mount. Returns a Promise that resolves when hydration is complete.
 * No-op if no adapter is configured.
 */
hydrate(): Promise<void>;
```

**Built-in adapter factories (exported from `@neutro/form/core`):**

```ts
export function localStorageAdapter<T>(key: string): PersistenceAdapter<T>;
export function sessionStorageAdapter<T>(key: string): PersistenceAdapter<T>;
```

Both guard against SSR (`typeof localStorage === 'undefined'`). Both wrap storage access in `try/catch` for `QuotaExceededError`. Both use `JSON.parse`/`JSON.stringify` — file values are not serializable, which is intentional (pair with `exclude`).

### Merge Strategy for hydrate()

When `read()` returns stored data, `hydrate()` merges stored values into `initialValues` using deep-merge: stored fields override config fields, but config fields not present in stored data retain their initial values. This handles schema evolution — newly added fields get their default from `config.initialValues`.

```ts
// Deep merge (stored values win on conflict):
const merged = deepMerge(config.initialValues, storedValues);
form.reset(merged);  // reset() is used so initial values are also updated
```

Implement `deepMerge` as a private utility inside `createForm`'s scope — not exported. It only needs to handle plain objects and primitives (File/Date values are not JSON-serializable and won't appear in stored data).

### Implementation Notes

- `hydrate()` returns `Promise<void>` regardless of whether the adapter's `read()` is sync or async. Always `await` the result and then call `reset(merged)`.
- `form.reset()` (no args) calls `adapter.clear()` — the form goes back to `config.initialValues` and the storage slot is cleared.
- `form.reset(newValues)` calls `adapter.write(newValues)` — the storage is updated to the new seed. This is appropriate for "load server data into form and persist from there".
- Debounce implementation: a simple `setTimeout`/`clearTimeout` pair inside `createForm`. NOT reusing the async debounce timer — persistence writes are on a separate timer. Cleared on `destroy()`.
- The `exclude` paths are applied both on write (omit those paths from the serialized object) and on read (don't override those paths with stored values even if they exist in storage).
- `write()` errors (e.g., `QuotaExceededError`) are swallowed with a `console.error` — persistence failures must never interrupt form operation.
- `read()` errors are caught in `hydrate()` and logged; the form falls back to `config.initialValues` unchanged.
- `destroy()` must clear the pending write debounce timer.

### Testing

Add `packages/core/test/persistence.test.ts`:

- Mock adapter that records `read`/`write`/`clear` calls.
- `hydrate()` merges stored values with config initialValues.
- `hydrate()` uses config initialValues when adapter returns null.
- Setting a field value triggers `adapter.write()` (after debounce).
- Excluded paths are not written to or read from storage.
- `reset()` (no args) calls `adapter.clear()`.
- `reset(newValues)` calls `adapter.write(newValues)`.
- Storage write errors are caught and do not throw.
- `localStorageAdapter` is a no-op in SSR (no `localStorage` global).
- `localStorageAdapter` JSON round-trips values correctly.
- `sessionStorageAdapter` is scoped to the session (reads/writes `sessionStorage`).
- After `destroy()`, no pending writes fire.

### Documentation

- Add `hydrate()` to `FormInstance<T>` JSDoc.
- New doc page: `docs/guides/persistence.md` — covers `localStorageAdapter`, `sessionStorageAdapter`, custom adapters, exclude paths, and the "reset clears storage" behaviour.
- Update `docs/api/core.md` with `PersistenceAdapter`, `PersistenceConfig`, `hydrate()`.
- Update `docs/community.md` FAQ: "Persistence middleware" moves from "Honest Gaps" into the existing "Resetting & Loading Data" FAQ section.

## Feature 5: Built-in File Validations

### What and Why

`BuiltInRule` has comprehensive validators for strings, numbers, arrays, and enums — but nothing for `File` or `FileList` values. The FAQ says users must write file validation in their `validator` function. Add first-class `BuiltInRule` entries for the most common file constraints, consistent with the existing structured-rule shape.

### API Design

Add to the `BuiltInRule` union in `packages/core/src/index.ts`:

```ts
// File / FileList validation
| { maxFileSize: number; message?: string }        // File.size ≤ n bytes
| { minFileSize: number; message?: string }        // File.size ≥ n bytes
| { fileTypes: string[]; message?: string }        // File.type is in MIME-type list
| { maxFiles: number; message?: string }           // FileList.length ≤ n
| { minFiles: number; message?: string }           // FileList.length ≥ n
```

**Usage examples:**

```ts
const form = createForm({
  initialValues: { avatar: null as File | null, attachments: null as FileList | null },
  rules: {
    avatar: [
      'required',
      { maxFileSize: 5 * 1024 * 1024, message: 'Max 5 MB' },
      { fileTypes: ['image/jpeg', 'image/png', 'image/webp'] },
    ],
    attachments: [
      { minFiles: 1, message: 'Attach at least one file' },
      { maxFiles: 3 },
      { maxFileSize: 10 * 1024 * 1024, message: 'Each file must be under 10 MB' },
    ],
  },
})
```

**Default messages (when `message` is not provided):**

| Rule | Default message |
|---|---|
| `maxFileSize: n` | `File must be at most {formatted size}` (e.g. "5 MB", "200 KB") |
| `minFileSize: n` | `File must be at least {formatted size}` |
| `fileTypes: [...]` | `File type must be one of: image/jpeg, image/png` |
| `maxFiles: n` | `Select at most {n} file(s)` |
| `minFiles: n` | `Select at least {n} file(s)` |

### Implementation Notes

- The rule evaluation function `validateBuiltInRule` (or equivalent) needs branches for the new rule shapes. Add them after the existing array rules.
- `maxFileSize`/`minFileSize`/`fileTypes` apply when `value instanceof File`.
- `maxFiles`/`minFiles` apply when `typeof FileList !== 'undefined' && value instanceof FileList`. Apply `maxFileSize`/`minFileSize`/`fileTypes` on each item in a `FileList` as well if both rule shapes are present.
- SSR guard: all `File` and `FileList` instance checks must be wrapped in `typeof File !== 'undefined'` and `typeof FileList !== 'undefined'`.
- `deepClone` already passes `File` objects through without cloning (line 286) — this is correct. Do not change it.
- `formatBytes(n)` is a private utility for default messages: `n >= 1024*1024 ? (n/1024/1024).toFixed(1) + ' MB' : n >= 1024 ? (n/1024).toFixed(0) + ' KB' : n + ' B'`.
- `fileTypes` uses exact MIME type matching (`File.type === 'image/jpeg'`). Wildcards (`image/*`) are NOT supported in v0.2.0 — scope them to 0.3.0.

### Testing

Add a `'file validation rules'` describe block in `packages/core/test/form.test.ts`:

- `maxFileSize` rejects a File whose `.size` exceeds the limit
- `maxFileSize` accepts a File within the limit
- `minFileSize` rejects a File that is too small
- `fileTypes` rejects a File with a disallowed MIME type
- `fileTypes` accepts a File with an allowed MIME type
- `maxFiles` rejects a FileList with too many entries
- `minFiles` rejects a FileList with too few entries
- `maxFileSize` applied to each item in a FileList
- Custom `message` overrides the default
- Default message for `maxFileSize` uses human-readable format ("5 MB" not "5242880 B")
- All rules are no-ops when value is `null` or `undefined` (required handles that case)
- All rules compile correctly when value is not a File (string field — no error thrown)

Use a mock `File` class in tests since jsdom may or may not have a real `File` implementation. Vitest + jsdom does expose `File` — verify this in the test environment setup.

- Update `docs/api/core.md` built-in rules table with the file entries.
- Update `docs/community.md` FAQ: "Built-in file validation rules" moves from "Honest Gaps" into the existing "Integration with UI Libraries" FAQ section, with examples for `<input type="file">` and `<input type="file" multiple>`.

## Feature 6: Nested `ValidationError.children` for `classValidatorAdapter`

### What and Why

`classValidatorAdapter` calls `class-validator`'s `validate()` and maps each top-level `ValidationError` to a flat key. But `ValidationError.children` contains nested errors for nested DTOs — e.g., `address.city` validation failure produces `{ property: 'address', children: [{ property: 'city', constraints: {...} }] }`. The adapter currently drops `children` entirely.

### API Design

No public API change. The adapter's call signature expands its internal type to include `children`:

```ts
// The second argument type becomes:
validate: (obj: T) => Promise<ValidationErrorLike[]>

// Where:
interface ValidationErrorLike {
  property: string;
  constraints?: Record<string, string>;
  children?: ValidationErrorLike[];
}
```

The current signature uses an inline type that is identical to `ValidationErrorLike` but without `children`. Expanding it to include the optional `children` field is backwards-compatible — callers who pass the real `class-validator` `validate` function already have it; callers who pass a mock that doesn't set `children` are unaffected (undefined is ignored).

### Implementation

Add a private `flattenClassValidationErrors` function adjacent to `classValidatorAdapter`:

```ts
function flattenClassValidationErrors(
  errors: ValidationErrorLike[],
  prefix: string = ''
): Record<string, string> {
  const result: Record<string, string> = {};
  for (const error of errors) {
    const path = prefix ? `${prefix}.${error.property}` : error.property;
    if (error.constraints && Object.keys(error.constraints).length > 0) {
      // Take only the first constraint message (consistent with current behaviour)
      result[path] = Object.values(error.constraints)[0];
    }
    if (error.children && error.children.length > 0) {
      Object.assign(result, flattenClassValidationErrors(error.children, path));
    }
  }
  return result;
}
```

Update `classValidatorAdapter` to use it:

```ts
export function classValidatorAdapter<T extends object>(
  cls: new () => T,
  validate: (obj: T) => Promise<ValidationErrorLike[]>
) {
  return async (values: T): Promise<Record<string, string>> => {
    const instance = Object.assign(new cls(), values);
    const validationErrors = await validate(instance);
    return flattenClassValidationErrors(validationErrors);
  };
}
```

### Edge Cases

- An error with both `constraints` and `children`: use `constraints` for the parent path's error message AND recurse into `children` for nested paths. Both are recorded.
- Array-indexed children: `class-validator` uses numeric string properties (`"0"`, `"1"`) for array items. The resulting path becomes `items.0.name`, which is exactly the dot-notation the form engine expects.
- Circular references in `children` are not possible in `class-validator` output (it builds a tree, not a graph) — no cycle guard needed.
- A `children` entry with no `constraints` and no further `children`: no entry is added for that path. This is correct — `class-validator` creates wrapper errors with no message for group-level nodes.

### Testing

Add to `packages/core/test/form.test.ts` in the `classValidatorAdapter` describe block:

- Flat DTO: existing behaviour unchanged
- Nested DTO: errors at `address.city` and `address.zip` are flattened correctly
- Deeply nested: three levels deep (`order.billing.postalCode`)
- Array of nested DTOs: `items.0.name` and `items.1.name` paths appear
- Entry with `children` but no `constraints` (wrapper node): no error recorded for the parent path
- Entry with both `constraints` and `children`: parent path gets a message AND children are recursed

### Documentation

- Update `classValidatorAdapter` JSDoc in source.
- Update the "Can I use `class-validator`?" FAQ in `docs/community.md` to mention nested DTOs are now supported.
- Update `docs/api/validation.md` with the `children` traversal note.

## Feature 7: Devtools Panel / Overlay UI

### What and Why

The existing `devtools()` function (`packages/core/src/devtools.ts`) logs to the browser console using `console.group`. This is useful during development but invisible in production and inaccessible to non-engineer stakeholders. A DOM panel provides an always-visible, in-page view of form state that integrates into visual regression tooling, Storybook, and embedded testing environments.

### API Design

Add to `packages/core/src/devtools.ts`:

```ts
export interface DevtoolsPanelOptions {
  name?: string;
  theme?: 'light' | 'dark' | 'auto';  // default: 'auto' (follows prefers-color-scheme)
  maxLogEntries?: number;              // default: 50 — oldest entries are dropped
  collapsed?: boolean;                 // default: false — panel starts expanded
}

/**
 * Mounts a reactive DOM panel inside `container` showing the form's current
 * state and an action log. Returns an unsubscribe function that unmounts the panel.
 */
export function createDevtoolsPanel(
  form: FormInstance<any>,
  container: HTMLElement,
  options?: DevtoolsPanelOptions
): () => void;
```

The panel renders three collapsible sections inside `container`:

1. **Header** — form name, `isValid` badge, `isSubmitting` badge, `isValidating` spinner.
2. **State** — live tree of `values`, `errors`, `touched`, `dirty`. Each section is individually collapsible. Values are shown as JSON with syntax highlighting via safe `innerHTML` injection using a tiny tokenizer (no third-party library).
3. **Action log** — newest-first list. Each entry shows action type, elapsed time, and the diff rows (same data as the console version). Capped at `maxLogEntries`.

**Styling:**
- All styles are injected into a `<style>` tag within the container's shadow root (if `attachShadow` is available) or as a scoped `<style id="neutro-devtools-panel">` tag in `<head>`.
- CSS custom properties for theming: `--nf-panel-bg`, `--nf-panel-text`, `--nf-panel-border`, `--nf-panel-accent`. Light/dark tokens set by `theme` option.
- No external CSS file is required — the panel is self-contained.

**Shadow DOM preference:**
- If `container.attachShadow` is available, use shadow DOM to isolate styles.
- Otherwise, inject a globally-scoped `<style>` with a specific ID so it's only injected once.

### Implementation Notes

- The panel re-renders only the diff on each state change, not the full DOM. Use a simple reconciler: store the current rendered values, compare with new state, update only changed text nodes or badge classes. No virtual DOM — just targeted `textContent` and `className` mutations.
- Global subscribers via `form.subscribe()` drive the state section.
- `form._subscribeToActions()` drives the action log.
- The `unsubscribe` function returned by `createDevtoolsPanel` must remove all event listeners, clear the container's `innerHTML`, and remove the injected `<style>` tag if it was globally injected.
- The panel should be lightweight enough to ship in development builds without impacting production bundle size. It is gated behind the `./devtools` subpath — tree-shaking removes it from production if the import is absent.
- `createDevtoolsPanel` must be guarded against being called in SSR (no `document` global). If `typeof document === 'undefined'`, log a warning and return a no-op.

## Feature 8: Changelog Automation

### Current State

There is no `CHANGELOG.md`, no changeset tooling, and no automated CHANGELOG generation. Releases are made by pushing a `v*` tag manually. The `publish.yml` workflow runs tests, builds, and publishes to npm, but it does not create a GitHub Release or generate any release notes.

### Recommended Approach: `release-please`

`release-please` (by Google) integrates with GitHub Actions to:
1. Parse conventional commits pushed to `main` and compute the next version bump.
2. Open a "release PR" that bumps `package.json` versions and generates `CHANGELOG.md` entries.
3. When the release PR is merged, create a GitHub Release with the generated notes and push a `v*` tag automatically.

This replaces the manual tag-pushing step and produces a `CHANGELOG.md` per package automatically.

**Conventional commit types used in this repo:**

| Prefix | Version bump | CHANGELOG section |
|---|---|---|
| `feat:` | minor | Features |
| `fix:` | patch | Bug Fixes |
| `docs:` | none (by default) | Documentation |
| `ci:` | none | CI |
| `refactor:` | none | — |
| `feat!:` or `BREAKING CHANGE:` | major | Breaking Changes |

### Files to Add

**`.github/workflows/release-please.yml`**

```yaml
name: release-please
on:
  push:
    branches: [main]
jobs:
  release-please:
    runs-on: ubuntu-latest
    permissions:
      contents: write
```

### Publish Workflow Update

The existing `publish.yml` triggers on `v*` tags. With `release-please`, the tag is auto-created when the release PR merges. The existing workflow continues to work unchanged — `release-please` creates the tag, which triggers `publish.yml`.

### Coordination: All Packages Version Together

By default, `release-please` in monorepo mode bumps only packages whose commits reference them. Since this monorepo treats all packages as a coordinated release, add `"linked-versions"` grouping (or the `group` option in v4) to ensure all packages move together on any feat/fix that touches core.

Alternatively: adopt the simpler "single package" strategy — treat the repo as one unit with one version in `release-please-config.json`. All packages get the same version on every release. This matches the current manual practice.

## Appendix: Bugs and Blindspots Found During Analysis

These issues were discovered while analyzing the codebase for this spec. They are not new features but correctness fixes that should ship alongside v0.2.0:

### A. `reset()` does not clear `hasValidated`

When Feature 3 is implemented, `reset()` must set `hasValidated = false` to return `isValid` to `null`. This is noted in Feature 3's implementation section — do not skip it.

### B. `classValidatorAdapter` takes only the first constraint message per property

The current implementation takes only `messages[0]` for each property (line 272). For fields with multiple failing constraints, only the first error is shown. This is consistent with how the engine currently shows one error per field — no fix needed, but document it.

### C. `destroy()` does not abort the persistence write debounce timer (Feature 4)

When the persistence adapter is added, `destroy()` must clear the pending debounce timer. Noted in Feature 4's implementation section.

### D. `runValidation` called after `arrayRemove` re-validates the full array path

Array operations call `runValidation([targetPath])` after each operation. If `targetPath` is `'items'`, and the form has a `dependencies: { 'items.*.name': ['items.*.qty'] }` style dependency, the wildcard expansion may not correctly substitute all remaining indices post-remove. This is an existing edge case — track it as a separate 0.3.0 issue.

### E. `FormAction` type exported but `RESET_FIELD` is missing

When Feature 2 is implemented, add `{ type: 'RESET_FIELD'; path: string }` to the exported `FormAction` union. Devtools and `_subscribeToActions` consumers need this to recognise the new action.

### F. Devtools `computeDiff` does not track `isValid`

When Feature 3 adds `isValid` to `FormState<T>`, update `computeDiff` in `devtools.ts` to include it in the meta-level diff rows.

## Deferred to v0.3.0

The following were discussed or are natural extensions but are explicitly out of scope for v0.2.0:

- **`fileTypes` wildcard matching** (e.g., `image/*`) in built-in file rules
- **`form.resetField` for DOM-connected elements** — restoring the element's `.value` attribute (DOM sync) when the field has a connected element. Defer until DOM bridge patterns are clearer.
- **Strongly typed runtime path validation** — throwing at runtime on invalid paths (not just TypeScript errors)
- **React Native adapter** — the honest gap remains
- **`isValid` without runValidation for individual fields** — field-level validity without full form validation
- **Nested array index wildcard in `dependencies`** (`destinations.*.url`) — currently has a best-effort substitution; a proper implementation requires index tracking at validation time
