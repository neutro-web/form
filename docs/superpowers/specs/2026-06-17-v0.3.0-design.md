# v0.3.0 Feature Design

**Goal:** Nine additive features that close honest gaps, raise the competitive baseline, and deepen NF's performance-first and DX positioning — without touching the hot path.

**Architecture:** Additive changes only — no existing properties, methods, or behaviours are removed or renamed. `FormState<T>`, `FormInstance<T>`, and `FormConfig<T>` all gain new members; consumers who mock or stub these interfaces will need to add the new fields/methods to their mocks (see Breaking Changes section at the bottom). No changes to `notify()`, `runValidation()`, or the subscriber model. The two prototypes (runtime path validation, computed fields) are research tasks with defined benchmarks; their release decision is deferred to 0.4.0.

**Tech Stack:** Same monorepo — `packages/core`, framework adapters (`react`, `vue`, `svelte`, `angular`, `solid`), VitePress docs.

**Non-goals for this release:** React Native adapter, runtime path validation release, computed/derived fields release.

## Feature 1: `fileTypes` Wildcard Matching

### What and Why

Built-in `fileTypes` rule today requires exact MIME type strings: `['image/jpeg', 'image/png']`. Every new format means updating the list. `image/*` wildcard matching is the standard pattern (HTTP Accept header, file input `accept` attribute) and is what developers expect.

### API

No new API surface. Existing `fileTypes` rule value arrays gain wildcard support:

```ts
rules: {
  avatar: { fileTypes: ['image/*'] },            // any image type
  media:  { fileTypes: ['image/*', 'video/*'] }, // images or videos
  doc:    { fileTypes: ['application/pdf', 'application/msword'] }, // exact types still work
}
```

Exact types and wildcards can be mixed in the same array. Non-wildcard strings continue to match exactly as today. To accept any file type, omit the `fileTypes` rule entirely — a `['*/*']` catch-all is not supported and has no meaningful use case.

### Implementation Notes

Inside `evaluateRule` where `fileType` is validated, change the matching logic to:

```ts
function matchesMimeType(ruleType: string, fileType: string): boolean {
  const normalRule = ruleType.toLowerCase()
  const normalFile = fileType.toLowerCase()
  if (normalRule.endsWith('/*')) {
    return normalFile.startsWith(normalRule.slice(0, -1))  // 'image/' prefix
  }
  return normalRule === normalFile
}
```

Replace the current `fileTypes.includes(file.type)` check with `fileTypes.some(r => matchesMimeType(r, file.type))`.

MIME types are case-insensitive per RFC 2045. Browsers return lowercase in practice, but normalise both sides to be safe.

### Edge Cases

- `image` (no slash) — treated as an exact match as before, not a wildcard. The `/` is the wildcard delimiter.
- Empty `fileTypes: []` — no change; existing behaviour (always fails) is preserved.
- Multiple files (array field) — apply the check to each file independently; existing array-field handling is unchanged.
- File with empty `type` string (some browser/OS combinations) — no MIME match, fails validation. Document this.

### Testing

- `image/*` matches `image/jpeg`, `image/png`, `image/webp`; does not match `video/mp4`
- `video/*` matches `video/mp4`, `video/webm`; does not match `image/png`
- Mixed array `['image/*', 'application/pdf']` matches both patterns independently
- Exact types still match exactly; regression test existing suite
- Case: `Image/JPEG` in `ruleType` and `image/jpeg` from browser both match
- Error message for a wildcard mismatch is identical to the existing exact-mismatch message — no new message string is introduced

## Feature 2: `form.isFieldValid(path)` — Per-Field Validity

### What and Why

`isValid: boolean | null` in `FormState<T>` is form-level: `null` before any validation, `true`/`false` after a full run. There is no way to ask "has this specific field been validated and does it pass?" without inspecting `errors[path]` directly — which cannot distinguish "no error because valid" from "no error because never validated."

This enables per-field "ready" indicators, progressive disclosure UIs, and multi-step wizards that show a tick/cross per section.

### API

New method on `FormInstance<T>`:

```ts
isFieldValid(path: Path<T> | string): boolean | null
```

Return values:
- `null` — this path has not been through a validation run yet
- `true` — path was validated and has no current error
- `false` — path was validated and has a current error

### Implementation Notes

Add a `validatedPaths: Set<string>` inside the `createForm` closure alongside `errors`, `touched`, `dirty`.

**Population:** Inside `runValidation`, after the scope is resolved and errors are written, add every path in the resolved scope to `validatedPaths`. `runValidation` already computes the full set of paths it validated to produce `errors` — reuse that set directly. Do **not** call `extractAllPaths(values)` fresh here; that would be O(total paths) redundant work on every `validate()` call for large array-heavy forms. A scoped run adds only the paths in that scope.

**Clearing:** `reset()` clears `validatedPaths` alongside `errors`, `touched`, `dirty`. `resetField(path)` removes that path from `validatedPaths`.

**Implementation of `isFieldValid`:**

```ts
const isFieldValid = (path: string): boolean | null => {
  if (!validatedPaths.has(path)) return null
  return !errors[path]
}
```

**`setErrors()` interaction:** `setErrors()` does NOT add paths to `validatedPaths`. If `hasValidated` is already `true`, server errors correctly drive `isFieldValid` to `false` because the path is already in `validatedPaths`. If not yet validated, server-set errors leave `isFieldValid` as `null` for that path — this is intentional and consistent with the form-level `isValid` semantics.

Add `isFieldValid` to `FormInstance<T>` interface and to the return object of all framework adapter hooks.

### Edge Cases

- Dynamic array paths (`items.0.name`): added to `validatedPaths` during array-scoped validation. `arrayRemove(0)` must remove all keys starting with `items.0.` from `validatedPaths` to avoid stale `true` results for now-deleted rows. `arrayInsert(0, item)` and `arrayMove` must renumber `validatedPaths` with the same `shiftStateIndices` / `rekeyArrayState` helpers that already handle `errors`, `touched`, and `dirty` — without this, `isFieldValid('items.1.name')` returns stale data after an insert shifts all indices. This is the same correctness requirement those state maps already satisfy.
- Path does not exist in schema: `isFieldValid('nonexistent')` returns `null` (never validated — correct).
- `clearErrors()` after validation: path remains in `validatedPaths`, error is removed → `isFieldValid` returns `true`. This is intentional; if the user wants to re-check validity they call `validate()`.
- **`hydrate()` and server-set errors:** When a form is hydrated from server state and errors are pre-populated via `setErrors()`, `validatedPaths` starts empty. `isFieldValid` will return `null` for every field even if server errors are present — which is correct (the form hasn't been validated client-side yet). The docs must include a pattern for this: "Call `validate()` after hydration if you need `isFieldValid` to reflect server-set errors, or use `errors[path]` directly for server-error display."

### Testing

- Initial state: `isFieldValid('email')` returns `null`
- After scoped `validate(['email'])` with no error: returns `true`
- After scoped `validate(['email'])` with error: returns `false`
- After full `validate()`, both paths return non-null
- `reset()` returns all paths to `null`
- `resetField('email')` returns only email to `null`; other paths unaffected
- `setErrors({ email: 'taken' })` before any validation: `isFieldValid('email')` remains `null`
- `setErrors({ email: 'taken' })` after validate has run: `isFieldValid('email')` returns `false`
- `clearErrors()` after validation: paths with cleared errors return `true`
- Array path `items.0.name`: `arrayRemove(0)` clears it back to `null`
- `arrayInsert(0, item)`: old `items.0.name` shifts to `items.1.name` in `validatedPaths` — `isFieldValid('items.1.name')` reflects the old field's state, not `null`
- Scoped validation of a parent path: `validate(['address'])` — if the validator resolves leaf paths (`address.city`, `address.zip`), those are added to `validatedPaths`; `'address'` itself is only added if it appears in the computed scope. Verify and document the exact scope expansion behaviour during implementation.
- `isFieldValid('email')` on a form that was hydrated with `setErrors({ email: 'required' })` but never validated: returns `null` (correct)

## Feature 3: Nested Array Wildcard in `dependencies`

### What and Why

`dependencies: { 'destinations.*.url': ['destinations.*.name'] }` currently uses best-effort wildcard substitution computed at `createForm` init time. Post-`arrayRemove` / `arrayMove`, the pre-computed scope can reference stale indices. The dependency graph needs runtime index resolution rather than static pre-computation for wildcard entries.

### Design

Separate dependencies into two categories at init time:

1. **Static entries** — no `*` in any path segment. Pre-computed into `preComputedScopes` exactly as today. Zero behaviour change.
2. **Wildcard entries** — any path segment is `*`. Stored as `wildcardDependencies: Array<{ pattern: string; dependents: string[] }>`. Not pre-computed.

**Runtime resolution inside `runValidation`:** For each path being validated, check each wildcard entry:

```ts
function matchesWildcardPattern(pattern: string, path: string): string[] | null {
  // Returns captured indices if path matches pattern, or null if not.
  const patternParts = pattern.split('.')
  const pathParts = path.split('.')
  if (patternParts.length !== pathParts.length) return null
  const indices: string[] = []
  for (let i = 0; i < patternParts.length; i++) {
    if (patternParts[i] === '*') {
      if (!/^\d+$/.test(pathParts[i])) return null  // only numeric indices
      indices.push(pathParts[i])
    } else if (patternParts[i] !== pathParts[i]) {
      return null
    }
  }
  return indices
}

function resolveWildcardDependents(
  dependentPatterns: string[],
  indices: string[]
): string[] {
  return dependentPatterns.map(dep => {
    let resolved = dep
    let i = 0
    resolved = resolved.replace(/\*/g, () => indices[i++] ?? '*')
    return resolved
  })
}
```

This is O(wildcardDependencies.length × depth) per path validated — negligible for realistic forms with 1–3 wildcard dependency rules.

**Pre-computed scopes remain valid for static entries** — no regression in that path.

**`compileDependencyScopes` must be updated** to route entries containing `*` in any segment to `wildcardDependencies` rather than into `preComputedScopes`. This is the key structural change in this feature.

### Edge Cases

- Multiple wildcards in one pattern (`matrix.*.*.value`): capture both indices in order and substitute both in the dependent pattern.
- Dependent pattern has more `*` than the triggering pattern: any unmatched `*` in the resolved dependent is left as `*` (effectively a no-op dependency for that slot — warn in dev mode).
- Non-numeric wildcard segments (e.g., `items.foo.bar` against `items.*.bar`): `matchesWildcardPattern` returns `null` (no match). Only numeric array indices trigger wildcard substitution.
- **Cross-array-to-static dependency** (`{ 'items.*.qty': ['summary.total'] }`): `resolveWildcardDependents(['summary.total'], ['0'])` returns `['summary.total']` unchanged (no `*` to substitute). This is correct and useful — changing any item's qty triggers re-validation of `summary.total`. Must be supported and tested.
- **Wildcard-resolved path that doesn't exist:** If a resolved dependent path (e.g., `destinations.2.name`) references an index that no longer exists after an `arrayRemove`, `getNestedValue(values, path)` returns `undefined`. `runValidation` passes `undefined` to the validator for that path. The validator must handle this gracefully — the spec does not define a special error message for this case; it is the validator's responsibility.

### Testing

- `validate(['destinations.1.url'])` triggers validation of `destinations.1.name` when `dependencies: { 'destinations.*.url': ['destinations.*.name'] }`
- After `arrayRemove(0)` on a 3-element array: `validate(['destinations.0.url'])` correctly resolves to `destinations.0.name` (which is now the old index 1 after the remove)
- After `arrayMove`, wildcard resolution uses current index, not original index
- Static (non-wildcard) dependencies are unaffected — existing tests pass without change
- Double-wildcard (`matrix.*.*.value`) resolves correctly
- Non-numeric segment does not trigger wildcard match
- Cross-array-to-static: `{ 'items.*.qty': ['summary.total'] }` — changing `items.0.qty` triggers validation of `summary.total`
- Out-of-bounds resolved path: wildcard resolves to a deleted index, `runValidation` receives `undefined` for that path without throwing

## Feature 4: `watch` / `useWatch` — Multi-Path Subscription

### What and Why

`subscribeToPath` covers single-path imperative subscription. The gap is multi-path subscription — "give me a value that updates when any of these paths changes" — and better framework-level ergonomics. `useFormPath` in React handles single-path controlled component re-renders; `useWatch` handles the read-only observation pattern across multiple paths.

### Core API

New method on `FormInstance<T>`:

```ts
watch(
  paths: Path<T> | string | Array<Path<T> | string>,
  callback: (values: Record<string, unknown>) => void
): () => void
```

Single path: `form.watch('email', (v) => console.log(v['email']))`
Multi-path: `form.watch(['email', 'username'], (v) => console.log(v))`

The callback always receives `Record<string, unknown>` where **the key is the exact path string passed to `watch`**. For nested paths this means the key contains dots — `form.watch('address.city', (v) => v['address.city'])`. This cannot be destructured with shorthand syntax. Document this explicitly: for nested-path watching, use bracket notation or assign to a named variable. Top-level paths (`'email'`, `'username'`) can be destructured normally in the multi-path object form.

Returns a teardown function (same as `subscribeToPath`). Calling the teardown function twice must be idempotent — the second call is a no-op.

**Implementation:** For each path in the paths array, call `subscribeToPath` internally. On any change in any watched path, re-read all watched paths from current values and fire the callback with the full set. Use a single shared de-dupe flag (a boolean set during one notify cycle, cleared after the callback fires) so the callback fires at most once per batch even if multiple watched paths change in the same batch.

The `watch` callback fires from inside the existing `subscribeToPath` subscriber loop, which is already wrapped in try-catch (the subscriber exception isolation from the 0.3.0 security work). The `watch` callback therefore benefits from the same isolation — an exception in the callback is logged and swallowed without breaking other subscribers.

An empty paths array `watch([], callback)` is valid — the callback never fires. This is not an error.

This requires no changes to `notify()` or the subscriber model. It's a thin wrapper over N `subscribeToPath` calls with shared teardown.

### Framework Adapter APIs

**React — `useWatch`:**

```tsx
import { useWatch } from '@neutro/form/adapters/react'

// Single path — returns value directly
const email = useWatch(form, 'email')

// Multiple paths — returns object
const { email, username } = useWatch(form, ['email', 'username'])
```

`useWatch(form, path)` is equivalent to `useFormPath(form, path)` for a single path — it subscribes via the core `watch` method and triggers a re-render on change. The component re-renders only when a watched path changes.

`useWatch(form, paths[])` returns a stable object reference that only changes when any watched path changes. Use `useMemo` keyed on each watched value to keep referential stability.

**Vue — `useVueWatch`:**

```ts
const { email, username } = useVueWatch(form, ['email', 'username'])
// email and username are readonly Refs
```

Accepts `MaybeRef<string[]>` so the paths list can be reactive.

**Svelte — `useSvelteWatch`:**

```ts
const watched = useSvelteWatch(form, ['email', 'username'])
// $watched.email, $watched.username
```

Returns a single readable store of the watched values object.

**Angular — `useAngularWatch`:**

```ts
// Returns a Signal of the watched values object
const watched: Signal<Record<string, unknown>> = useAngularWatch(form, ['email', 'username'])
// template: watched()['email'], watched()['username']
```

Single path returns `Signal<unknown>`. Must be called inside an injection context (same constraint as `useAngularForm`).

**SolidJS — `useSolidWatch`:**

```ts
// Returns a readonly signal of the watched values object
const watched = useSolidWatch(form, ['email', 'username'])
// JSX: watched()['email'], watched()['username']
```

Single path returns a signal of the value directly.

### Performance Constraint

`useWatch` with no path argument (form-level watch) is intentionally not supported at the adapter level. Developers who need all values should use the existing `useForm` / `useSvelteForm` hooks and accept the full-state re-render. For form-level observation at the core level, use `form.subscribe()` directly — it is the existing, documented API for that purpose. Document this in the `watch` API reference: "To observe all form state changes, use `form.subscribe()` instead."

### Edge Cases

- Same path passed twice in the array: deduplicate — only one `subscribeToPath` call per unique path.
- Path added to watch list after initial call: not supported; re-call `watch` with the new list (or re-mount the hook).
- Teardown: calling the returned function from `form.watch()` unsubscribes all paths in that call atomically. Calling it a second time is a no-op (idempotent).
- Empty paths array `watch([], callback)`: valid, callback never fires, teardown is a no-op.

### Testing

- Single path callback fires when path changes, not when other paths change
- Multi-path callback fires when any watched path changes; callback receives current values for ALL watched paths (not just the changed one)
- Teardown stops all callbacks
- Double teardown: calling the teardown function twice does not throw or unsubscribe other watches
- Deduplication: `watch(['email', 'email'])` fires only once per change
- Empty array: `watch([], cb)` — `cb` never fires, teardown succeeds
- Nested path key: `watch('address.city', cb)` — callback receives `{ 'address.city': <value> }` (full dotted string as key)
- React: `useWatch(form, ['a', 'b'])` component does not re-render when `c` changes

## Feature 5: Schema Type Inference

### What and Why

Current boilerplate when using a schema library:

```ts
const schema = z.object({ email: z.string(), username: z.string() })
type Values = z.infer<typeof schema>          // ← explicit type extraction
const form = createForm<Values>({             // ← explicit generic
  initialValues: { email: '', username: '' },
  validator: zodAdapter(schema),
})
```

If `createForm` can infer `T` from `initialValues` alone (which TypeScript already does in most cases), the middle line is pure boilerplate. The goal: make the explicit `z.infer<>` and `<Values>` unnecessary when `initialValues` is present.

### Design

**Verify first:** Confirm whether `createForm({ initialValues: { email: '', username: '' }, validator: zodAdapter(schema) })` already infers `T = { email: string, username: string }` correctly from `initialValues` without an explicit generic. If TypeScript already does this, the change is documentation only — update all guide examples to drop the `type Values = z.infer<typeof schema>` line and the explicit `<Values>` generic where `initialValues` covers the type.

**If inference does not work today** (e.g., initialValues typed too broadly), add an overload to `createForm`:

```ts
// Overload: infer T from validator signature when initialValues is not fully typed
function createForm<T extends object>(
  config: Omit<FormConfig<T>, 'validator'> & {
    validator: (values: T, signal?: AbortSignal) => any
    initialValues: T
  }
): FormInstance<T>
```

The typed validator from `zodAdapter` already carries the schema's inferred type in its parameter. TypeScript can flow this back to `T` without any runtime change — this is purely a type-level overload.

**Adapter changes:** `zodAdapter`, `yupAdapter`, `valibotAdapter` must return a function typed as `(values: T, signal?: AbortSignal) => ...` rather than `(values: any) => ...`. The `any` in the current return was a practical shortcut; tightening it to `T` enables backward inference. Verify this doesn't break existing callers that pass a mismatched schema type.

**No runtime change.** The adapters and `createForm` body are unchanged. This is entirely in the TypeScript type signatures.

### Scope Constraint

If the verify step shows TypeScript already infers correctly, scope is limited to:
1. Updating adapter return types to be typed instead of `any`
2. Updating docs — all Zod/Yup/Valibot examples drop the explicit type line

If the verify step shows inference is broken, add the overload described above.

### Testing

- Type tests (`.test-d.ts`): `createForm({ initialValues: { email: '' }, validator: zodAdapter(z.object({ email: z.string() })) })` — verify returned `FormInstance` is `FormInstance<{ email: string }>` without explicit generic
- Existing explicit-generic call sites continue to compile
- Mismatched `initialValues` and schema (schema has `email`, initialValues has `emal`) produces a TypeScript error, not silent mismatch
- **TypeScript compatibility test:** verify that consumer code that explicitly types the adapter result as `(values: any) => Record<string, string>` still compiles after the return type is tightened to `(values: T) => Record<string, string>`. If it does not, document the migration: remove the explicit type annotation and let it infer.

## Feature 6: `form.isDirty()` / `form.isFieldDirty(path)` — Dirty Predicates

### What and Why

Accessing `state.dirty.email` requires subscribing to full state, reading an object, and doing a boolean coercion. Predicate methods are more composable, more discoverable, and `isFieldDirty` handles the nested-prefix case (is any field under `address.*` dirty?) which direct property access cannot express.

Naming mirrors `isFieldValid` — both field-level checks carry "Field" in the name and require a path. The form-level dirty check has no "Field" prefix and no path argument. We avoid a form-level `isValid()` method because `state.isValid` already covers that and a same-named method alongside a state property creates unnecessary confusion.

### API

```ts
isDirty(): boolean                              // is any field in the form dirty?
isFieldDirty(path: Path<T> | string): boolean  // is this specific field (or subtree) dirty?
```

### Implementation

```ts
const isDirty = (): boolean =>
  Object.values(dirty).some(Boolean)

const isFieldDirty = (path: string): boolean => {
  if (dirty[path]) return true
  const prefix = path + '.'
  return Object.keys(dirty).some(k => k.startsWith(prefix) && dirty[k])
}
```

The nested prefix match (`isFieldDirty('address')` returns `true` if `address.city` is dirty) is the primary reason this is a method rather than a state accessor. It cannot be expressed with direct property access.

**Performance note:** `isFieldDirty` is O(number of dirty fields) due to the prefix scan. For typical forms this is negligible, but it should not be called inside tight loops or on every keystroke. If called in a React render function inside a `useForm`-subscribed component, it runs on every field change. For high-field-count forms (100+ fields), prefer caching the result or restructuring the render to avoid repeated calls.

**Dirty semantics note:** `dirty` tracks whether `set()` has ever been called for a path, not whether the current value differs from the initial value. `isFieldDirty('email')` returns `true` after `set('email', '')` even if `initialValues.email` is also `''`. Document this clearly — developers who want "value differs from initial" must compare `form.get(path)` against `initialValues` themselves.

Add both to `FormInstance<T>` interface and return from all framework adapter hooks.

### Edge Cases

- `isFieldDirty('items')` on an array field: returns `true` if any `items.*` child is dirty, including `items.0.name`, `items.1.qty`, etc.
- After `reset()`: dirty is cleared, `isDirty()` and `isFieldDirty(any)` return `false`.
- After `resetField('email')`: `isFieldDirty('email')` returns `false`; other fields unaffected.

### Testing

- Initially: `isDirty()` → `false`, `isFieldDirty('email')` → `false`
- After `set('email', 'x')`: `isFieldDirty('email')` → `true`, `isFieldDirty('username')` → `false`, `isDirty()` → `true`
- After `reset()`: all return `false`
- Prefix: `set('address.city', 'London')` → `isFieldDirty('address')` → `true`
- `isFieldDirty('addr')` does NOT match `address.city` (prefix must include the `.` separator)
- `isFieldDirty('phone')` when `dirty['phone']` is `undefined` (key never set): returns `false`
- `isFieldDirty('email')` after `set('email', '')` when `initialValues.email === ''`: returns `true` — dirty tracks whether `set()` was called, not whether the value changed

## Feature 7: Submission State Tracking

### What and Why

There is no way to know how many times the user has tried to submit, or what values were last successfully submitted. Both are common needs: "show a support link after 3 failed attempts", "warn about unsaved changes since last submit", "disable the retry button until something changes."

### API

Two new fields in `FormState<T>`:

```ts
interface FormState<T> {
  // ... existing fields ...
  submissionAttempts: number          // increments on every submit() call
  lastSubmittedValues: Partial<T> | null  // snapshot at last successful submission
}
```

Initial values: `submissionAttempts: 0`, `lastSubmittedValues: null`.

### Implementation

**`submissionAttempts`:** Increment inside `submit()` at the very start, before validation. This means even a validation failure is counted — which is the correct semantics (the user attempted to submit).

**`lastSubmittedValues`:** Set to a **deep clone** of `getPayload()` after:
1. Validation passes
2. The user-provided async submit handler resolves without throwing

A shallow spread (`{ ...getPayload() }`) is insufficient — if any value is a nested object (e.g., `address: { city, zip }`), the reference is shared and subsequent `set('address.city', x)` calls mutate the snapshot. Use `structuredClone(getPayload())` (available in all modern environments) or the existing `deepMerge({}, getPayload())` helper. Verify that `getPayload()` is called **after** the handler resolves, not before, so the snapshot reflects the state at the moment of successful submission.

If the handler throws or rejects, `lastSubmittedValues` is NOT updated. The previous snapshot (or null) is preserved.

```ts
// Inside submit():
submissionAttempts++
notify()

const valid = await runValidation()
if (!valid) { isSubmitting = false; notify(); return false }

const payload = getPayload()
try {
  await handler(payload)
  lastSubmittedValues = structuredClone(payload) as Partial<T>
  // onSubmitSuccess runs after lastSubmittedValues is set
  try { await config.onSubmitSuccess?.(payload) }
  catch (hookErr) { console.error('[NeutroForm] onSubmitSuccess threw:', hookErr) }
} catch (submitErr) {
  // lastSubmittedValues unchanged
  try { await config.onSubmitError?.(submitErr, payload) }
  catch (hookErr) { console.error('[NeutroForm] onSubmitError threw:', hookErr) }
  throw submitErr  // original error must still propagate to the caller
} finally {
  isSubmitting = false
  notify()
}
```

> **Note:** `onSubmitSuccess` and `onSubmitError` hooks are shown inline here because Feature 9 depends on Feature 7 being implemented first. Implement both features together or ensure Feature 7 is committed before Feature 9 is started. If `onSubmitSuccess`/`onSubmitError` are not yet implemented, the try/catch wrappers around them are simply absent.

**Async hooks and `isSubmitting`:** If `onSubmitSuccess` or `onSubmitError` return a Promise, `submit()` awaits them before the finally block runs. This means `isSubmitting` remains `true` for the entire hook duration. Document this: if `onSubmitSuccess` performs a redirect or long operation, the form stays in submitting state until the hook resolves.

**`reset()` behaviour:** Resets `submissionAttempts` to `0` and `lastSubmittedValues` to `null`. A full reset means starting fresh.

**`reset(newValues)` behaviour:** Same — both reset to initial state. The new values become the baseline, and the submission history is cleared.

### Edge Cases

- `handleSubmit` wrapper: delegates to `submit()` internally — `submissionAttempts` increments correctly.
- Multiple rapid submissions (double-click): `isSubmitting` guard already blocks concurrent submissions; `submissionAttempts` only increments for the first.
- `lastSubmittedValues` is a **shallow clone of `getPayload()`** — only connected/persisted paths. This is consistent with how `getPayload` works: non-connected hidden fields are excluded.
- Devtools `computeDiff` must be updated to diff `submissionAttempts` and `lastSubmittedValues` as meta-level state (same treatment as `isSubmitting`, `isValid`).

### Testing

- Initial: `submissionAttempts === 0`, `lastSubmittedValues === null`
- Submit with validation failure: `submissionAttempts === 1`, `lastSubmittedValues === null`
- Submit with validation pass + handler resolves: `submissionAttempts === 1`, `lastSubmittedValues` matches payload
- Submit handler throws: `submissionAttempts === 2` (second attempt), `lastSubmittedValues` still holds previous snapshot
- `reset()`: both fields return to initial values
- `reset(newValues)`: both fields return to initial values
- Bare `form.submit()` with no handler: `submissionAttempts` increments; `onSubmitSuccess` fires if validation passes (no handler = nothing to reject); `lastSubmittedValues` is set
- `submissionAttempts` increments correctly when triggered via `handleSubmit(fn)(event)` wrapper
- Deep clone: mutating a nested field after a successful submission does not change `lastSubmittedValues`

## Feature 8: `form.focus(path)` — Programmatic Focus

### What and Why

After `validate()` fails, the ergonomic pattern is to focus the first invalid field. Currently developers must maintain their own ref map or use DOM querySelector hacks. Since `connect()` already holds a `WeakRef<HTMLElement>` per path in `connectionRegistry`, we have the element reference — we just need to expose it as a focus API.

### API

```ts
focus(path: Path<T> | string): boolean
```

Returns `true` if an element was found and focused; `false` if no connected element exists for that path (element not mounted, or using framework-controlled input without `useFormConnect`).

### Implementation

```ts
const focus = (path: string): boolean => {
  const entry = connectionRegistry.get(path)
  if (!entry) return false
  const el = entry.ref.deref()
  if (!el || !el.isConnected) return false
  el.focus()
  return true
}
```

**Convenience pattern — focus first error:**

```ts
const focusFirstError = (): boolean => {
  const errorPaths = Object.keys(getState().errors)
  if (errorPaths.length === 0) return false

  // Sort by DOM order so the first visible error is focused, not the first
  // error inserted into the errors object (which is validation order, not DOM order).
  const connected = errorPaths
    .map(p => ({ path: p, el: connectionRegistry.get(p)?.ref.deref() }))
    .filter((e): e is { path: string; el: HTMLElement } =>
      e.el !== undefined && e.el.isConnected
    )

  if (connected.length === 0) return false

  // compareDocumentPosition: if A precedes B, the result has DOCUMENT_POSITION_FOLLOWING (4)
  connected.sort((a, b) =>
    a.el.compareDocumentPosition(b.el) & Node.DOCUMENT_POSITION_FOLLOWING ? -1 : 1
  )

  connected[0].el.focus()
  return true
}
```

Using `compareDocumentPosition` ensures `focusFirstError()` moves focus to the **first error the user sees in the DOM**, not the first error in validation order. This is the correct a11y behaviour — screen readers announce the focused element, so focusing an error that appears lower on the page than another visible error is confusing. Note: "first" here means first in document tree order, which may differ from visual order in CSS-reordered layouts (flexbox `order`, CSS `position`). Document this limitation.

`focus()` should wrap `el.focus()` in a try-catch — while uncommon, some environments throw on focus calls (JSDOM quirks, detached shadow DOM). Log and return `false` if it throws.

Add both `focus` and `focusFirstError` to `FormInstance<T>`.

### Scope Constraint

`focus()` and `focusFirstError()` only work for elements connected via `form.connect()` / `useFormConnect`. Framework-controlled inputs (React `value=` + `onChange=`, Vue `v-model`, etc.) do not use `connectionRegistry`. Document this clearly: for controlled inputs, use native React ref / Vue ref forwarding. `form.focus()` and `form.focusFirstError()` are the zero-rerender / DOM bridge path only.

### Edge Cases

- Element connected but scrolled off screen: `focus()` still calls `.focus()` — scroll behaviour is browser default (scroll into view). This is correct.
- Input type `type="hidden"`: browsers silently ignore `focus()` on hidden inputs. `focus()` returns `true` (element found) but nothing visible happens. Document this.
- Multiple elements on same path (shouldn't happen, but connect() would overwrite the registry entry): last connected element wins.
- `focusFirstError()` when errors is an empty object: returns `false` immediately.

### Testing

- Connect an input, call `form.focus('email')`: input receives focus (use jsdom `document.activeElement`)
- Element removed from DOM: `focus()` returns `false`
- No element connected for path: `focus()` returns `false`
- `focusFirstError()` with errors and multiple connected elements: focuses the element that appears first in document order (not first inserted into errors), returns `true`
- `focusFirstError()` with no errors: returns `false`
- `focusFirstError()` when errors exist but no element is connected for any error path: returns `false`
- `focus()` on a `type="hidden"` input: browser silently ignores the focus call; returns `true` (element found) — nothing visible happens
- `focus()` when `el.focus()` throws: logs error, returns `false`

## Feature 9: `onSubmitSuccess` / `onSubmitError` Hooks

### What and Why

Server error handling today requires wrapping every `handleSubmit` call:

```ts
form.handleSubmit(async (payload) => {
  const res = await fetch('/api/submit', { body: JSON.stringify(payload) })
  if (!res.ok) {
    const { errors } = await res.json()
    form.setErrors(errors)
  }
})
```

This pattern is repeated at every submit site. `onSubmitSuccess` and `onSubmitError` in `createForm` config let this live once at the form definition level, reducing callsite boilerplate and enabling a single error-handling strategy across all submit handlers on that form.

### API

```ts
interface FormConfig<T> {
  // ... existing fields ...
  onSubmitSuccess?: (payload: Partial<T>) => void | Promise<void>
  onSubmitError?: (error: unknown, payload: Partial<T>) => void | Promise<void>
}
```

`payload` in both hooks is the `getPayload()` snapshot at submission time — the same value passed to the submit handler.

### Execution Order and Interaction

The hooks are **lifecycle callbacks that complement the submit handler**, not replace it. They are implemented inside `submit()` alongside Feature 7's submission state tracking — see Feature 7's pseudocode for the complete implementation shape. In summary:

1. `submit()` increments `submissionAttempts`, runs validation
2. If valid: calls the user-provided submit handler
3. If handler resolves: updates `lastSubmittedValues`, then calls `onSubmitSuccess(payload)` (wrapped in its own try-catch — if it throws, the error is logged and swallowed; the submission is not reversed)
4. If handler throws: calls `onSubmitError(originalError, payload)` (wrapped in its own try-catch), then re-throws the **original** submit error — the hook error is logged separately and does not replace the original

Re-throwing after `onSubmitError` preserves the existing contract — callers of `handleSubmit` can still catch in a try-catch or `.catch()`. The hook is for side effects (logging, `setErrors`, analytics), not error suppression.

`onSubmitSuccess` and `onSubmitError` are async-safe — if they return a Promise, `submit()` awaits it before the finally block runs (meaning `isSubmitting` stays `true` for the hook's duration — document this).

**Implementation dependency:** Feature 9 must be implemented in the same task or after Feature 7. The `submit()` pseudocode in Feature 7 already includes both hook call sites.

### Edge Cases

- `onSubmitSuccess` throws: treat it as an unexpected hook error. Log with `console.error('[NeutroForm] onSubmitSuccess threw:', err)`. Do not propagate — the submit itself succeeded, the hook failure should not reverse that.
- `onSubmitError` throws: same treatment — log and swallow. Then re-throw the original submit error.
- No submit handler passed (bare `form.submit()`): hooks still fire. `onSubmitSuccess` fires if validation passes; `onSubmitError` fires if `submit()` itself throws (shouldn't happen, but defensive).
- `onSubmitError` calling `form.setErrors()`: this is the primary intended use case. Works exactly as it does today in a `handleSubmit` wrapper.
- Both hooks are optional; neither being present changes existing behaviour. (Fix: "changes no existing behaviour" → "changes existing behaviour" — the original phrasing was a double negative.)

### Testing

- `onSubmitSuccess` called with correct payload after handler resolves
- `onSubmitSuccess` not called if validation fails
- `onSubmitSuccess` not called if handler throws
- `onSubmitError` called with the thrown error and payload after handler rejects
- `onSubmitError` not called if validation fails (that's not a submit error — surface it via `isValid`)
- `onSubmitError` not called if handler resolves
- `onSubmitError` calling `form.setErrors()` correctly populates errors state
- Hook re-throw: original submit error still propagates from `submit()` after `onSubmitError` fires — the hook's own error (if it throws) is separate, logged, and swallowed
- Async hooks: `submit()` awaits them before the finally block runs; `isSubmitting` remains `true` during hook execution
- `onSubmitSuccess` throws: error is logged, submission is not reversed, `lastSubmittedValues` retains the snapshot
- No `onSubmitSuccess` defined: submit resolves normally without calling any hook — no error

## Breaking Changes

These changes are additive — nothing is removed or renamed — but they will cause TypeScript compilation errors in consumer code that mocks or stubs NF interfaces:

**⚠️ BC-1: `FormState<T>` gains two new required fields** (`submissionAttempts: number`, `lastSubmittedValues: Partial<T> | null`).
Any test mock or stub typed as `FormState<T>` will fail to compile. Fix: add both fields with their zero values (`submissionAttempts: 0`, `lastSubmittedValues: null`) to existing mocks. Document in the changelog with before/after examples.

**⚠️ BC-2: `FormInstance<T>` gains six new methods** (`isFieldValid`, `isDirty`, `isFieldDirty`, `watch`, `focus`, `focusFirstError`).
Any consumer wrapper, higher-order component, or test mock implementing `FormInstance<T>` will fail TypeScript compilation. Fix: add stub implementations to mocks. Document in the changelog.

**⚠️ BC-3: Adapter validator return type tightened** (Feature 5).
`zodAdapter`, `yupAdapter`, `valibotAdapter` return types change from `(values: any) => ...` to `(values: T) => ...`. Consumer code that explicitly annotates the adapter result as `(values: any) => Record<string, string>` may produce a TypeScript error. Verify during Feature 5's verify step and document the migration if needed.

**Non-breaking:** `FormConfig<T>` new optional fields, new adapter hook exports (`useWatch`, etc.), new core methods. All additive.

## Prototype Work — Build in 0.3.0, Release Decision in 0.4.0

These are not shipping features in 0.3.0. They are research tasks to be worked on **after all nine shipping features are complete and committed**. The goal is to arrive at 0.4.0 planning with working prototypes, benchmark data, and a clear go/no-go decision rather than making that call speculatively.

---

### Prototype A: Runtime Path Validation

**What:** A trie-based path checker that warns at runtime when `set()`, `get()`, or `connect()` is called with a path that doesn't exist in the form's schema. Today `form.set('emal', value)` silently does nothing; this prototype catches it.

**Approach:**

At `createForm` init time, walk `initialValues` once and build a path trie. Each node records whether its children are object keys or array slots. Array nodes use a wildcard marker (`[*]`) so that any numeric index is considered valid — `items.0.name` is valid after `arrayAppend` because the trie knows `items` is an array node.

```
initialValues: { items: [{ name: '', qty: 0 }], email: '' }

trie:
  email       → leaf
  items       → array-node
  items.[*]   → object-node
  items.[*].name → leaf
  items.[*].qty  → leaf
```

At runtime, before the actual `set()` / `get()` operation, validate the path against the trie in O(depth) steps. If no match: emit `console.warn('[NeutroForm] Unknown path: ...')`. Do not throw — preserves the dynamic-path escape hatch.

**Scope for the prototype:**
- Dev-only by default (`process.env.NODE_ENV !== 'production'` guard, or `import.meta.env.DEV`)
- Warn, never throw
- The trie must handle: static paths, numeric array indices at any depth, paths produced by all five array operations after they run

**Benchmark gate (must pass before 0.4.0 release):**

| Metric | Threshold |
|---|---|
| `set()` overhead on a 50-field form | < 2μs per call |
| False positives on full correctness matrix | 0 |

**Correctness matrix** — the prototype must produce zero warnings for all of the following:
- All paths in `initialValues`
- `items.N.name` for any N after one or more `arrayAppend` calls
- `items.N.name` after `arrayInsert(0, item)` shifts existing indices
- Paths at the new indices after `arrayRemove`, `arrayMove`, `arraySwap`
- Deeply nested arrays (`matrix.0.tags.2`)

**What "done" looks like for the prototype:** trie builds correctly, all matrix cases pass with zero false positives, microbenchmark is written and numbers are recorded. The 0.4.0 decision is: do the numbers hit the threshold? If yes, remove the dev guard and ship. If no, fix the implementation until they do.

### Prototype B: Computed / Derived Fields

**What:** First-class support for fields whose value is derived from other field values — e.g. `total` = `qty × unitPrice`, or `shippingDate` derived from `orderDate`. Currently developers implement this with a `subscribe()` callback that calls `set()`, which triggers a second notification cycle per keystroke.

**Approach:**

Extend `FormConfig<T>` with a `computed` map:

```ts
createForm({
  initialValues: { qty: 1, unitPrice: 10, total: 0 },
  computed: {
    total: (values) => values.qty * values.unitPrice,
  },
})
```

Computed fields are **read-only** — calling `set('total', x)` is a no-op with a dev warning.

**The hard problem — notification cascades:** If a computed field calls `set()` naively, it triggers a second `notify()` cycle. If computed fields chain (A → B → C), that's three cycles per keystroke. The prototype must prove a cascade-safe model before this ships.

**Candidate approach — deferred computed pass inside `batch()`:**

After each `set()` call resolves its normal notify cycle, run a single "computed pass" inside an implicit batch: evaluate all computed functions against current values, write any that changed, then notify once for all derived changes. This keeps the per-keystroke cost to: one normal notify + one computed pass + one derived notify. No recursive cycles possible because computed fields are read-only.

**Dependency tracking:** For the prototype, no automatic dependency detection — the developer declares which fields a computed depends on via a `deps` hint if needed for optimisation, but the prototype runs all computed functions on every change. Selective re-run (only recompute when deps change) is an optimisation for 0.4.0+ if the baseline is too slow.

**Benchmark gate (must pass before 0.4.0 release):**

| Scenario | Threshold |
|---|---|
| 1 computed field, simple expression | No measurable extra render cycles vs baseline |
| 5 computed fields, independent | Same — one computed pass, one extra notify |
| Chained: A → B → C derived from each other | Still one computed pass, one extra notify — no cascade |

The cascade scenario (`A → B → C` chain) is the critical test. If the prototype produces more than one extra notification cycle per `set()` call in any chain scenario, the model is wrong and needs redesign before 0.4.0.

**What "done" looks like for the prototype:** computed fields update correctly after each `set()`, read-only enforcement works, chain scenario produces exactly one extra notification cycle, benchmark numbers are recorded. The 0.4.0 decision is: do the cascade guarantees hold across all test scenarios? If yes, ship. If the model requires more work (e.g. selective dependency tracking to hit performance goals), that work happens in 0.4.0 before release.
