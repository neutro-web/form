# Browser-Level Schema-Validate Competitor Comparison — Design

Date: 2026-07-09
Status: Approved (design phase)
Release gate: v0.5.0, item 3 of 6 remaining (see memory `project_v050_release_gate`)
Builds on: `docs/superpowers/specs/2026-07-02-bench-schema-validator-overhead-design.md`, whose "Competitor comparison belongs in the browser suite, not core" section explicitly deferred this exact follow-on. That spec's Node-level, neutro-only `schema-validate/zod/*`, `schema-validate/yup/*` core surfaces are already implemented and measured (confirmed present in `bench/suites/core/schema-validate.bench.ts`, remeasured as part of the v0.5.0 performance audit with "No change" verdicts against the pre-modular-split baseline).

## Problem

neutro/form ships Zod/Yup/class-validator schema adapters, and schema validation is a well-known strength area for the competitor ecosystem — react-hook-form's `@hookform/resolvers` in particular. The existing Node-level `schema-validate` core surface only measures neutro's own schema-parse overhead relative to its own plain-validator baseline (a deliberate, previously-decided scope — no Node-level competitor shims, per commit `3da9090`). There is currently zero data on how neutro's schema-validated write/validate/render cycle compares to competitors' *real* schema integrations running in their actual render context (React/Vue/Svelte), which is the only fair way to compare libraries whose validation is tightly coupled to their own render/reactivity model.

## Non-goals

- **No new Node-level competitor adapters.** Already explicitly rejected by prior project decision (commit `3da9090`); this spec's whole premise is that a fair comparison requires a real browser render context, which a Node harness cannot provide.
- **No Formik+Zod comparison.** Formik has no official Zod resolver — only an unofficial third-party package (`zod-formik-adapter`). Per explicit decision, Formik is marked N/A for this specific comparison (not silently dropped, not force-fit via an unofficial adapter) — Formik keeps its existing full participation in every other browser surface (`mount-cost`, `re-renders`, etc.), this exclusion is scoped to schema-validate only.
- **No Yup or class-validator browser comparison in this spec.** Zod-everywhere was the explicit decision, since every included competitor (RHF, tanstack-form, vee-validate, felte) has an official first-party Zod integration, making it the one schema library where a like-for-like comparison across all of them is actually possible. A Yup-based or class-validator-based browser follow-on is out of scope here (class-validator was already out of scope for the Node-level spec too, for the same "no fair ecosystem equivalent" reason).
- **No changes to the existing Node-level `schema-validate` core surface.** That work is done; this spec is purely additive (new browser routes + specs).

## Design

### Fixture shape: identical to the existing Node-level fixtures — schema only, not `initialValues`

Reuses the exact 10-field shape and Zod schema already defined in `bench/fixtures/schema-zod.ts`'s `zodSmallSchema` (`z.object({ field0: z.string().min(1), ..., field9: z.string().min(1) })`), so the browser-level numbers this spec produces are directly comparable in shape (not magnitude — different measurement environments) to the Node-level schema-parse-cost numbers already measured. **Only the schema is reused — not the Node fixture's `initialValues`.** `schemaZodSmallFixture.initialValues` seeds every field to `'x'` (deliberately valid, for the Node-level parse-cost measurement's own purposes). This spec's browser routes need the opposite: all 10 fields start as empty string, so the form is invalid from mount, which is required for the submit-latency spec's "fill invalid, submit, wait for errors" flow to have something to measure. Do not copy-paste the Node fixture's `initialValues` — only its schema shape.

### Prerequisite: install `zod` and each library's official Zod-integration package in the bench apps

`zod` is currently a `bench/package.json` devDependency only (`^3.24.0`) — it is NOT installed in any of the three bench apps (`bench/apps/{react,vue,svelte}/package.json`), and `bench:apps:build:*`'s `pnpm --dir apps/<app> install --ignore-workspace` does not hoist the root's `zod` into them. Before any route can `import { z } from 'zod'`, add `zod` (pinned to the same `^3.24.0` already benched at Node level, so browser and Node numbers stay same-version-comparable) as a direct dependency of all three apps.

Each library's Zod integration must likewise be added as a new dependency (none currently exist in any app's `package.json`) — this is a real "add a dependency," not merely "verify availability." **Pin each to an explicit version verified against this repo's pinned core-library version and the `zod` `^3.24.0` pin above — do not install "latest" and assume compatibility:**
- **react-hook-form**: `@hookform/resolvers` (its `zod` subpath export, `zodResolver`) — real and currently published, but flagged for extra care: `bench/apps/react/package.json` pins `react-hook-form: ^7.52.0`, and an unpinned/latest install of `@hookform/resolvers` resolves to its current major line, whose `zodResolver` internals target a newer zod/Standard-Schema era than `zod@^3.24.0` may fully align with. Verify `zodResolver`'s exact call signature against the installed `@hookform/resolvers` major and `zod@^3.24.0` specifically during implementation (e.g. a quick smoke test rendering one validation error) before trusting the wiring — this is the one resolver pairing in this table without a clean "obviously fine" version story.
- **vee-validate**: `@vee-validate/zod` (`toTypedSchema`) — real, tracks the pinned `vee-validate` v4 line (`^4.13.2` here); lower version-compatibility risk than the RHF pairing above, but still pin an explicit version rather than "latest."
- **felte**: `@felte/validator-zod` — real, compatible with the pinned felte `^1.3.0`; lower version-compatibility risk, same "pin explicitly" instruction.
- **tanstack-form**: **no separate adapter package exists for the pinned v1 line** — `@tanstack/zod-form-adapter` was a v0.x-era package, deprecated and removed at v1. TanStack Form v1 uses **Standard Schema** directly: pass the Zod schema object straight into the field/form validator config (e.g. `validators: { onChange: schema }`), no extra package needed beyond `zod` itself. The earlier "official Zod validator adapter" framing was wrong — correct it to "Standard Schema: the Zod schema passed directly, no adapter package."

If any of the three real resolver packages listed above turns out, during implementation, to be incompatible with the exact pinned competitor version already in this repo (version drift between when this spec was written and when it's implemented), treat that competitor exactly like the Formik case below — N/A with a stated reason — rather than blocking the rest of the work.

### New routes: one per library per app, added to the existing bench apps

| App (port) | Route | Library | Zod integration used |
|---|---|---|---|
| React (4173) | `/schema-validate/neutro` | neutro/form (React) | `zodAdapter` (existing, `packages/core/src/index.ts`) |
| React (4173) | `/schema-validate/rhf` | react-hook-form | `@hookform/resolvers/zod`'s `zodResolver` |
| React (4173) | `/schema-validate/tanstack` | tanstack-form (React) | Standard Schema — Zod schema passed directly, no adapter package |
| Vue (4174) | `/schema-validate/neutro` | neutro/form (Vue) | `zodAdapter` |
| Vue (4174) | `/schema-validate/vee` | vee-validate | `@vee-validate/zod` |
| Svelte (4175) | `/schema-validate/neutro` | neutro/form (Svelte) | `zodAdapter` |
| Svelte (4175) | `/schema-validate/tanstack` | tanstack-form (Svelte) | Standard Schema — Zod schema passed directly, no adapter package |
| Svelte (4175) | `/schema-validate/felte` | felte | `@felte/validator-zod` |

Formik is deliberately absent from this route table (N/A per the Non-goals section, not omitted by oversight) — but per the Reporting section below, Formik still needs an explicit N/A *result row*, which is not the same as "absent from the route table."

**Each library gets its own dedicated, isolated route — libraries are never co-mounted on a shared page for this surface**, unlike `mount-cost`/`re-renders`'s existing pages (which mount every library for a given app simultaneously). Co-mounting would risk cross-library render interference contaminating the submit-latency measurement specifically; isolated routes avoid that risk entirely and cost nothing extra since each route is a small, single-purpose component.

**Routing mechanism**: none of the three apps uses a router library — each `App`/`App.vue`/`App.svelte` dispatches on `window.location.pathname` via a hand-rolled switch (confirmed: `react/src/App.tsx`, `vue/src/App.vue`, `svelte/src/App.svelte` each has one). Adding a new route means adding a new branch to that existing switch plus a new per-library component file (the Vue and Svelte apps already follow a one-file-per-library-per-feature convention, e.g. `VeeAsyncPage.vue`; the new schema-validate components follow the same convention). The Vue app's existing top-level `useVeeForm()` call (in `App.vue`, unconditional at mount) is scoped to the *existing* vee-validate demo — the new schema-validate vee-validate route needs its own independent `useForm({ validationSchema: toTypedSchema(zodSchema) })` call inside its own new component, not a reuse of that top-level instance.

Each route renders 10 text inputs (`data-testid="{prefix}-field{i}"`, matching the existing `mount-cost`/`re-renders` field-testid convention exactly, where `{prefix}` is `neutro`/`rhf`/`tanstack`/`vee`/`felte`). The submit button (`data-testid="{prefix}-submit"`) and error-display region (`data-testid="{prefix}-error"`) are **new testids this spec introduces** — no existing page has a per-library submit button or a per-library error region (the existing async pages share one testid, `async-error`, across all libraries on that page) — so these are a new but consistent convention, not a reuse of something that already exists. Each library's real, idiomatic Zod-resolver wiring is used — no custom validation glue code that could artificially advantage or disadvantage a library, with one acknowledged asymmetry: neutro's own wiring (`validator: zodAdapter(schema)` passed to `createForm`, then the route manually calls `form.validate()`/`form.set(path, val, { validate: true })` on submit and reads `form.getState().errors`) is a few more lines than competitors' single-prop `resolver={zodResolver(schema)}`-style wiring. This is neutro's actual real-world integration shape, not artificially inflated glue — but it's worth stating plainly rather than implying byte-for-byte symmetry across all five libraries' wiring.

**Package/version availability must be verified during implementation, not assumed here** (see the Prerequisite section above for what's already known to need installing). If any resolver package turns out incompatible with this repo's exact pinned competitor version, that specific route is dropped and the competitor is marked N/A for this surface with a stated reason in `bench/annotations.ts` — the same treatment as Formik, applied to whichever library actually hits this, not assumed to never happen.

### Two new Playwright spec files, reusing established patterns exactly

**`bench/suites/browser/schema-validate-rerenders.spec.ts`** — reuses `re-renders.spec.ts`'s `measureReRenders` *test-side helper* as-is (it's generic: reset counters, type into a field, read counters back), but **the counters themselves are app-side instrumentation that must be newly wired for every new component** — `re-renders.spec.ts`'s counters (`window.__neutroRenders` etc., per `apps/react/src/App.tsx`) are module-scoped objects that each *existing* library's field-wrapper component manually increments on every render; none of that exists yet for the new `/schema-validate/*` components, so each new component (neutro/rhf/tanstack/vee/felte × however many apps include it) needs its own render-counting wired in, following the exact same manual-increment pattern. Two implementation choices, either acceptable, decide during planning: (a) reuse the *same* counter object/key the existing plain-form component already writes to (safe only because each schema-validate route mounts in isolation, one library at a time, so there's no risk of the plain-form and schema-validate variants of the same library being mounted simultaneously and double-counting into one object), or (b) introduce a fresh, distinctly-named counter object per new component (e.g. `window.__neutroSchemaRenders`) — if choosing (b), the existing `window.__resetRenders` function (which today zeroes exactly the existing counter objects, hard-coded by name) must also be extended to zero the new ones, or counts will silently leak across repeated test runs within the same page session. Type into `field0` 20 times, count total re-renders across all fields, on the new `/schema-validate/*` routes. Same `COMBOS` array structure (name/port/prefix/key/library/limit) for the real libraries, **plus a separately-coded Formik case (see Reporting item 3) that does not follow this loop body** since there is no route for it to navigate to.

**`bench/suites/browser/schema-validate-submit.spec.ts`** — new measurement, following `mount-cost.spec.ts`'s `performance` API usage pattern but bracketing a user action instead of navigation timing: fill all 10 fields with an invalid value (empty string — already the initial state, so this spec can skip straight to clicking submit), call `performance.mark('schema-validate-submit-start')` via `page.evaluate` immediately before clicking the submit button, wait for the error region (`data-testid="{prefix}-error"`) to become visible, then `performance.mark('schema-validate-submit-end')` and `performance.measure(...)` to compute the elapsed ms, read back via `page.evaluate`. Same `COMBOS`-array/`attach`-helper structure as the other real-library rows, reporting `submitLatencyMs` in the `BrowserResult` attachment, **plus its own separately-coded Formik case** (same reasoning as the re-renders spec above — no route, no navigation, N/A-only attachment).

### Reporting — corrected: this DOES require real, scoped changes to the reporting pipeline, not zero new code

An earlier draft of this section claimed "no new mechanism" — that was checked against the actual pipeline (`bench/types/schema.ts`, `bench/scripts/generate-page.ts`, `bench/scripts/scorecard.ts`, `bench/annotations.ts`) and found wrong in three ways, corrected here:

1. **`BrowserResult`'s type must be widened.** `bench/types/schema.ts`'s `BrowserResult` has no `submitLatencyMs` field today — attaching one from `schema-validate-submit.spec.ts` without adding it to the type is a type error, and `generate-page.ts`'s `browserTable()` (which renders `renderCount`/`p50Ms`/`p99Ms`/`cancellationPass`/`connectedCountAfterCleanup`/`mountMs`/`heapDeltaBytes` today, nothing else) needs a new branch to render `submitLatencyMs` as its own column — otherwise the generated table for that surface would show a `Library` column with no data. `SURFACE_TITLES` also needs two new entries (`schema-validate-rerenders`, `schema-validate-submit`, or whatever exact surface keys the two spec files end up using) — without them, the generated page's section heading falls back to the raw, unfriendly surface key.
2. **The Scorecard summary table does NOT auto-include new surfaces — it's built from hardcoded arrays.** `scorecard.ts`'s `BROWSER_NUMERIC_SURFACES` (and `CORRECTNESS_SURFACES`) are literal, hand-maintained lists, and the existing `metric` union only supports `'renderCount' | 'p50Ms'` — `submitLatencyMs` isn't a valid value today. **Explicit decision for this spec: schema-validate does NOT get a Scorecard summary row.** It appears only in the per-surface Browser detail tables (the existing `for (const surface of browserSurfaces)` loop, which genuinely is dynamic/auto-discovering, unlike the Scorecard). This keeps the change scoped and avoids widening the Scorecard's metric-type union for a brand-new metric on its first appearance — Scorecard inclusion can be a small, separate follow-up once this surface has shipped and someone decides it's important enough to headline. Whoever implements this must not silently add it to the Scorecard arrays without this explicit decision being revisited.
3. **Formik's (and any other dropped competitor's) N/A must be an emitted result row, AND `browserTable()` must be taught to render a reason for a row with no metric value — confirmed as a second, deeper gap on top of the first.** The existing pipeline only calls `reasonMarker()` (which reads `ANNOTATIONS`) for libraries that already have a `BrowserResult` row in `results` — nothing in `generate-page.ts` synthesizes a row from `ANNOTATIONS` alone for a library with zero measurements, so an emitted row is necessary. But it is **not sufficient** on its own: `browserTable()`'s existing per-metric cells (e.g. `hasRender ? (r.renderCount != null ? \`${r.renderCount}${reasonMarker(...)}\` : '—') : ...`) only call `reasonMarker()` **inside the branch where the metric value is present** — for an N/A row every metric is `null`, so the cell renders a bare `—` with no footnote call at all, silently dropping the reason exactly as if it had never been emitted. **`browserTable()` needs a `status`-aware branch, checked before the per-metric branches, that renders something like `— N/A${reasonMarker(surface, r.library)}` whenever `r.status === 'na'`, regardless of which metrics that surface's table normally shows.** Both new spec files must (a) include a Formik test case emitting an explicit `{ library: 'formik', status: 'na' }`-shaped `BrowserResult` attachment (confirmed against `bench/types/schema.ts`: `BrowserResult` is a flat, non-discriminated interface with `status: 'ok' | 'error' | 'na'` and all metric fields optional, so this object shape type-checks cleanly with no structural obstacle) instead of a real measurement, and (b) this attachment is a **distinct code path, not a normal COMBOS loop iteration** — there is no `/schema-validate/formik` route to `page.goto()` to, so the Formik case cannot follow the same "goto then measure" body every other COMBOS row uses; it must skip navigation entirely and only attach the N/A result. This is real, new surface area in two places (the emitted row AND the table-rendering logic) — own both explicitly rather than assuming either one alone is sufficient.

Both specs still feed `bench/results/browser.json` through the existing Playwright-attachment → merge pipeline (that part of "no new mechanism" was correct), and the `for (const surface of browserSurfaces)` loop that discovers per-surface detail tables is confirmed genuinely dynamic (`browserSurfaces = Object.keys(baseline.browser ?? {})`, driven by each spec's `test.describe(...)` title becoming the surface key via `reporters/json-playwright.ts`) — no registration step needed for the surfaces to appear, **provided the two new `describe` titles exactly match whatever strings are added to `SURFACE_TITLES`** (matching is by literal string; a mismatch silently falls back to displaying the raw, unfriendly surface key instead of erroring).

## Testing

1. Both new spec files' assertions are loose sanity bounds, not strict pass/fail thresholds — `expect(renderCount).toBeGreaterThanOrEqual(0)` / a generous library-specific ceiling, and `expect(submitLatencyMs).toBeGreaterThanOrEqual(0)` for the new surface. **Note on the ceiling values: the existing `re-renders.spec.ts` limits (neutro 25, rhf/tanstack/vee 500, felte 2500, formik 4500) have no documented derivation methodology to inherit — they read as empirically-picked-by-feel, not derived from a formula.** There is no existing precedent to follow here; the implementation plan must pick fresh ceilings empirically (run the new routes once, observe real numbers, set each limit comfortably above what's observed) rather than assuming some inheritable "2x the plain-form limit" rule exists. Also note these become `toBeLessThanOrEqual` hard CI assertions (per the existing Playwright config's retry behavior) — a ceiling set too tight will flake, not just misreport, so err generous. The comparative detail table is where the real signal lives for a reader; the assertions exist only to catch a genuine, large regression.
2. Before trusting any number, run the full `bench:browser` pipeline once and manually verify each new route actually renders the 10-field form and its Zod validation genuinely fires (e.g., temporarily log a validation result in the browser console during implementation) — the project's established discipline of not trusting a benchmark number without confirming the harness is measuring what it claims to measure applies here too.
3. `bench:full` (the complete pipeline: apps build → core → correctness → browser → bundle-size → merge → generate) must run clean end-to-end with the two new surfaces present in the regenerated `docs/benchmarks/index.md` before this work is considered complete.

## Risks

- **Different competitors' Zod integrations may have meaningfully different validation-triggering semantics** (e.g., validate-on-submit vs validate-on-blur vs validate-on-change as each library's *default* mode) — if left at each library's own default, the comparison could conflate "schema-validation cost" with "how eagerly does this library validate," which is a different question. The implementation must explicitly configure each library's schema-validate mode to trigger validation the same way (on submit, for the submit-latency spec; on change, for the re-render spec) rather than accepting whatever each library's out-of-the-box default happens to be — otherwise the numbers measure the wrong thing.
- **Formik's N/A treatment must be visible in the generated page, not silently absent — and per the Reporting correction above, this requires an emitted N/A result row, not just an `annotations.ts` entry.** A reader seeing Formik present in every other row of `docs/benchmarks/index.md` but missing from the schema-validate row (with no annotation) would reasonably assume it was overlooked, not deliberately excluded. Verify by inspection after `bench:generate` that Formik's row actually renders with its N/A reason visible — not just that the annotation text exists in `annotations.ts`'s source, since that alone does not guarantee it reaches the page (see Reporting section above).
- **A library whose real Zod package turns out to be unavailable mid-implementation** is a real possibility (this space moves fast, package APIs/exports change) — if this happens, treat it exactly like the Formik case (N/A with a stated reason), not as a blocker for the rest of the spec.
- **`COMPETITOR_VERSIONS` in `bench/annotations.ts` currently tracks only each competitor's core library version, with no slot for a resolver/integration package's version.** Per this project's existing convention (documented in `CLAUDE.md`: keep `COMPETITOR_VERSIONS` in lockstep with whatever's actually benched), the four new resolver packages' versions (`@hookform/resolvers`, `@vee-validate/zod`, `@felte/validator-zod`) should also be recorded once pinned, so a future reader can tell exactly which resolver-package version produced these numbers. Decide the exact shape (extend the existing structure vs. a small parallel map) during planning.

## Open questions for the implementation plan

- **Exact configuration needed per library to force "validate on submit" (for `schema-validate-submit.spec.ts`) vs "validate on change" (for `schema-validate-rerenders.spec.ts`).** Confirmed during spec review that every included library DOES have a real, documented way to control this (RHF: `mode: 'onSubmit'` / `'onChange'` in `useForm`; vee-validate: `validateOnMount`/mode options passed to `useForm`; felte: its `validate`/`onSubmit` config; TanStack Form: per-field `validators: { onSubmit: schema }` vs `{ onChange: schema }`) — this is a real, resolvable "look up the current API" task for the implementation plan, not a sign of a deeper unsolved problem. Look up each library's actual current documentation during planning rather than guessing the option names used above.
- Whether `schema-validate-rerenders.spec.ts`'s per-library render-count limits should be set relative to the existing plain-form `re-renders.spec.ts` limits or as fresh absolute numbers determined empirically after the routes exist — per the Testing section correction above, there's no inheritable derivation methodology either way, so this is really just "pick fresh numbers empirically," not a meaningful choice between two methodologies.
