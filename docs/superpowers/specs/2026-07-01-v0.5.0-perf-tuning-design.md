# v0.5.0 — Benchmark-Driven Performance Tuning

**Date:** 2026-07-01
**Status:** Approved
**Scope:** `packages/core`, `packages/adapters/*` (perf-relevant paths only), `bench/annotations.ts`, `bench/scripts/compare-baseline.ts`, `.github/workflows/bench-regression.yml`, `docs/benchmarks/index.md`

---

## Problem

The benchmark suite (`bench/`) now produces accurate Win/Tied/Behind/Tradeoff verdicts against react-hook-form, formik, tanstack-form, vee-validate, and felte (a prior annotation-lookup bug that mislabeled `async-latency` as Behind instead of Tradeoff has been fixed separately). With that fixed, the Scorecard in `docs/benchmarks/index.md` shows two real, unexplained gaps and a set of near-parity results worth a lightweight look:

**Behind (❌ — real gaps, no documented reason):**
1. `bundle-size` vs `tanstack-form`: neutro/form 10.0 KB gzip vs tanstack-form 6.3 KB gzip
2. `array-ops` (render count) vs `tanstack-form (Svelte)`

**Tied (➖ — within the 10% threshold, investigated opportunistically):**
- `re-renders/10` and `re-renders/100` vs react-hook-form, tanstack-form (React), tanstack-form (Svelte), vee-validate
- `array-ops` vs react-hook-form, vee-validate
- `async-cancellation` vs felte, react-hook-form, tanstack-form (React), tanstack-form (Svelte), vee-validate
- `bundle-size` vs react-hook-form, vee-validate

A third problem surfaced during this release's own CI runs: `bench-regression.yml`'s PR gate (`bench/scripts/compare-baseline.ts`) posted a "Benchmark Regression Detected" comment on PR #9 — a release-please version-bump PR that touched only `package.json` files and `CHANGELOG.md`, zero `packages/core/src` changes — showing 6 unrelated core surfaces (array-ops, computed-fields, dependency-scopes, subscriptions) all regressed 15-36% simultaneously. A real code regression hits the specific path that changed; a uniform simultaneous drop across every unrelated surface with no code change is the signature of GitHub Actions shared-runner variance, not a real slowdown. The gate's only noise filter is single-sample `rme > 10%`, with no cross-run smoothing — so a single noisy CI run trips the 15% threshold easily. This is a false-positive problem with the regression gate itself, not with neutro/form's performance, but it undermines trust in every other Fixed/Annotated verdict this release produces if left unaddressed.

v0.5.0 is dedicated to closing or explaining these gaps, and hardening the regression gate that verifies them. No other feature work ships in this release.

## Definition of Done (per gap)

Every gap in scope resolves one of two ways — never left unexplained:

1. **Fixed** — a real inefficiency is found and corrected; rerunning `pnpm --dir bench bench:full` (with the `results/latest.json` → `results/baseline.json` copy step, since local `bench:generate` reads only `baseline.json`) shows the badge improve to ✅ Win or ➖ Tied for a Behind item, or hold/improve for a Tied item.
2. **Annotated** — the gap is structural (a real architectural tradeoff, not a bug), documented as a `⚖️ Tradeoff` entry in `bench/annotations.ts`'s `ANNOTATIONS` map with the concrete reason, same pattern as the existing `async-latency` debounce annotation.

## Work Plan

One task per gap: investigate root cause, then either implement a fix or write the annotation. No separate research-only phase — investigation and fix live in the same task so root-cause findings translate directly into code or documentation without a context handoff.

### Priority 0 — Regression-gate reliability (fix first — everything below depends on trusting this gate)

**Harden `bench/scripts/compare-baseline.ts` against CI-runner noise.**

Current behavior: one `bench:core` sample per PR run, compared against `results/baseline.json` at a flat 15% threshold, with only single-sample `rme > 10%` as a noise filter. Confirmed false-positive: PR #9 (version-only diff, no engine code changed) showed 6 unrelated surfaces regress 15-36% in one run.

Fix: run `bench:core` multiple times in `bench-regression.yml` (e.g. 3 iterations) and compare the **median** `opsPerSec` per surface against baseline, instead of a single sample. Median-of-N smooths transient runner contention without hiding a real, consistent regression (a genuine slowdown shows up in all N runs; a noise spike shows up in one). Keep the existing `rme`-based skip as a secondary filter on top, not a replacement.

Re-validate the 15% threshold once median-of-N is in place — it may already be conservative enough post-fix, or may need adjustment; decide empirically by re-running `bench-regression` against a few historical no-op PRs (like #9) and confirming zero false positives before considering this task done.

Do not weaken the gate to the point it stops catching real regressions — the goal is fewer false positives, not a rubber stamp. If median-of-N alone doesn't eliminate false positives at the existing threshold, raise the threshold rather than dropping the sample count back down.

### Priority 1 — Behind (must resolve before release)

**1. Bundle size vs tanstack-form**

Investigate what's contributing to neutro/form's 10.0 KB vs tanstack-form's 6.3 KB gzip. Candidate causes to check: dead code not tree-shaken from the bundle-size fixture (`bench/fixtures/bundle/neutro.ts`), included-but-unused validation adapters, or genuinely more surface area (neutro ships array ops + DOM bridge + persistence in the core bundle; tanstack-form's fixture may only exercise a thinner slice). If the size gap traces to a real inefficiency (unused imports leaking into the bundle, missed tree-shaking), fix it in `packages/core/src/index.ts`'s export structure or the build config. If the gap is inherent — neutro's fixture necessarily pulls in more capability than tanstack-form's does — annotate it in `bench/annotations.ts` under `'bundle-size'` keyed by `'tanstack-form'`, with the specific capability difference named.

**2. array-ops vs tanstack-form (Svelte)**

Investigate neutro's Svelte adapter (`packages/adapters/svelte/src/index.ts`) render-triggering behavior on `arrayRemove`/`arrayMove` compared to tanstack-form (Svelte)'s array field handling (`bench/apps/svelte/src/*.svelte`, `@tanstack/svelte-form`'s array field API). Check whether neutro's Svelte reactivity re-renders more array items per mutation than necessary — e.g. whether `useSvelteFormPath` subscribes too broadly for indexed array paths. If a real over-subscription bug is found, fix it. If tanstack-form (Svelte)'s array field API achieves finer-grained reactivity through a mechanism neutro's path-subscription model can't replicate without a larger design change, annotate it in `bench/annotations.ts` under `'array-ops'` keyed by `'tanstack-form (Svelte)'`.

### Priority 2 — Tied (opportunistic, no hard requirement to close all)

For each Tied surface/library pair, do a lightweight investigation pass (read the relevant adapter/engine code path, compare against the competitor's approach at a glance). Only open a fix task if a concrete, low-risk improvement surfaces — do not force a fix where none is obvious. Surfaces to sweep:

- `re-renders/10` and `re-renders/100` vs react-hook-form, tanstack-form (React), tanstack-form (Svelte), vee-validate
- `array-ops` vs react-hook-form, vee-validate
- `async-cancellation` vs felte, react-hook-form, tanstack-form (React), tanstack-form (Svelte), vee-validate
- `bundle-size` vs react-hook-form, vee-validate

If the sweep finds nothing actionable for a given pair, leave it as ➖ Tied with no annotation — "tied" is already an accurate, non-alarming verdict and doesn't require an excuse.

## Verification

After each fix (or annotation) task:
1. Rerun the affected suite (`bench:core`, `bench:browser`, or `bench:bundle-size` as applicable) plus `bench:merge`.
2. Copy `results/latest.json` → `results/baseline.json` (mirrors CI's `bench:update-baseline`, required for local `bench:generate` to reflect fresh data).
3. Run `bench:generate` and confirm the specific badge changed as expected in `docs/benchmarks/index.md`.
4. Run the full existing test suite (`pnpm test`, `pnpm exec tsc --noEmit`, `pnpm lint`) to confirm no regression.

Release closes when Priority 0 is fixed and verified against at least one historical no-op PR, both Priority 1 items are Fixed or Annotated, and the Priority 2 sweep has been completed (fixes shipped for whatever surfaced, remainder left as-is).

## What Stays the Same

- Benchmark methodology, verdict thresholds (`VERDICT_THRESHOLD = 0.10`), and scorecard structure (`bench/scripts/scorecard.ts`, `bench/lib/verdict.ts`) — unchanged, already fixed and correct. (The regression-gate's separate 15% threshold in `compare-baseline.ts` is in scope for Priority 0 — do not confuse the two; the scorecard's Win/Tied/Behind/Tradeoff badges are a different mechanism from the PR regression gate.)
- No new benchmark surfaces are added in this release — this is about closing existing gaps, not expanding coverage.
- Public API surface — no breaking changes in 0.5.0. Any fix must stay backward compatible; if a fix requires a breaking change, it's out of scope for this release and gets logged as a new backlog item instead.

## Out of Scope

- React Native adapter — moved to 0.6.0.
- Strict path typing in adapter hooks — moved to 0.6.0.
- New benchmark surfaces or competitors.
- Chasing Tied gaps with no obvious root cause just to convert ➖ to ✅.
