# Accessibility Helpers — Design Spec

**Date:** 2026-06-14
**Status:** Approved

## Problem

ARIA attributes (`aria-invalid`, `aria-describedby`, `aria-required`) are entirely the developer's responsibility today. The DOM bridge (`connect()`) already manages `aria-invalid` and `aria-describedby` reactively, but has no `aria-required` support. Framework adapter users (React, Vue, Svelte — who never call `connect()`) have no utility at all: they must manually derive ARIA attributes from raw form state on every field they build.

## Solution

Add `getAriaProps(path, options?)` to `FormInstance<T>` as a snapshot method — reads current state, returns a plain object developers spread onto inputs. No new entrypoint or build entry needed; it lives in core alongside `getState` and `getPayload`. Also enhance `connect()` to set `aria-required` automatically when the field has a `required` rule.

## API

### `getAriaProps(path, options?)`

```ts
getAriaProps(
  path: Path<T> | string,
  options?: AriaPropsOptions
): AriaProps
```

```ts
export interface AriaPropsOptions {
  required?: boolean   // true = force on; false = suppress auto-detect; default = infer from rules
  errorId?: string     // override the generated aria-describedby target ID
}

export interface AriaProps {
  'aria-invalid': 'true' | 'false'
  'aria-describedby': string | undefined
  'aria-required': true | undefined
}
```

#### Attribute logic

| Attribute | Value |
|---|---|
| `aria-invalid` | `'true'` when `state.errors[path]` exists, otherwise `'false'` |
| `aria-describedby` | Predictable ID — `error-{path-with-dots-as-dashes}` or `options.errorId` — when an error exists; `undefined` otherwise |
| `aria-required` | `true` when `options.required === true` OR (field's `rules` config includes `'required'` AND `options.required !== false`); `undefined` otherwise |

`aria-required` is `undefined` (not `false`) when the field is not required so that spreading the result onto a DOM element omits the attribute entirely rather than setting it to `false`.

`aria-describedby` uses a predictable ID convention: `error-${path.replace(/\./g, '-')}`. Developers render their error element with the matching `id`:

```tsx
<span id="error-email">{state.errors.email}</span>
<span id="error-billing-address">{state.errors['billing.address']}</span>
```

#### Usage examples

```tsx
// React — re-renders naturally when useFormPath/useForm subscription fires
<input
  value={email}
  onChange={e => form.set('email', e.target.value)}
  {...form.getAriaProps('email')}
/>
<span id="error-email">{state.errors.email}</span>

// required field inferred from rules config
const form = createForm({
  initialValues: { email: '' },
  rules: { email: ['required', 'email'] },
})
form.getAriaProps('email')
// → { 'aria-invalid': 'false', 'aria-describedby': undefined, 'aria-required': true }

// required field with custom validator (no rules config) — explicit override
form.getAriaProps('username', { required: true })

// override the error element ID
form.getAriaProps('email', { errorId: 'my-email-error' })

// suppress aria-required even though rules include 'required'
form.getAriaProps('email', { required: false })
```

## `connect()` Enhancement

The DOM bridge already sets `aria-invalid` (on connect and reactively via `subscribeToPath`) and `aria-describedby` (via `[data-error="${path}"]` element discovery). The only addition is `aria-required`.

On initial connect, after the existing ARIA setup, check the form's `rules` config:

```ts
if (isFieldRequired(stringPath, config.rules)) {
  element.setAttribute('aria-required', 'true');
}
```

`isFieldRequired` is a private helper:

```ts
function isFieldRequired(
  path: string,
  rules: FormConfig<any>['rules']
): boolean {
  const fieldRules = rules?.[path];
  if (!fieldRules) return false;
  return Array.isArray(fieldRules)
    ? fieldRules.includes('required')
    : fieldRules === 'required';
}
```

`aria-required` reflects the static schema and is set once on connect. No reactive subscription needed — field requiredness does not change at runtime.

`connect()` does not get an `errorId` override. Its `aria-describedby` logic uses DOM discovery (`[data-error]` element lookup), which is appropriate for the imperative DOM bridge context and need not align with `getAriaProps`'s predictable-ID convention.

## Implementation

### `packages/core/src/index.ts`

1. Export `AriaPropsOptions` interface and `AriaProps` type.
2. Add `getAriaProps` to `FormInstance<T>` interface after `getPayload`.
3. Add private `isFieldRequired(path, rules)` helper function.
4. Implement `getAriaProps` in the `createForm` return object — reads `getState()` and `config.rules`.
5. In `connect()`, after the existing `aria-invalid` / `aria-describedby` setup, call `isFieldRequired` and conditionally `setAttribute('aria-required', 'true')`.

### `packages/core/test/aria.test.ts` (new file)

`// @vitest-environment jsdom` at top (needed for `connect()` tests).

**`getAriaProps` unit tests (no DOM required):**
- `aria-invalid: 'false'` when no error
- `aria-invalid: 'true'` when error exists for path
- `aria-describedby` is `undefined` when no error
- `aria-describedby` is `'error-email'` when error on `email` path
- `aria-describedby` is `'error-billing-address'` when error on `billing.address` path
- `errorId` option overrides generated ID
- `aria-required` auto-detected when `rules: { email: 'required' }` (string form)
- `aria-required` auto-detected when `rules: { email: ['required', 'email'] }` (array form)
- `options.required: true` forces `aria-required: true` even with no rules
- `options.required: false` suppresses `aria-required` even when `rules` includes `'required'`
- No `aria-required` when field has no required rule (returns `undefined`)

**`connect()` aria-required tests (jsdom):**
- Sets `aria-required="true"` on element when field has `required` rule
- Does not set `aria-required` when field has no required rule

### `docs/api/core.md`

Add `getAriaProps` to the method reference section with signature, options table, and a short usage example.

### `docs/api/connect.md`

Add an "Automatic ARIA" section documenting what `connect()` sets on the element: `aria-invalid` (reactive), `aria-describedby` (via `[data-error]` discovery), and `aria-required` (from `rules` config). Note that `getAriaProps()` is the recommended approach for framework adapter contexts.

## Scope

In scope: `getAriaProps(path, options?)`, `AriaPropsOptions`, `AriaProps` types, `isFieldRequired` helper, `aria-required` in `connect()`, tests, documentation updates to `core.md` and `connect.md`.

Out of scope: `aria-label`, `aria-labelledby`, live region management, per-field `aria-live` announcements, framework adapter hooks (`useAriaProps`), accessibility auditing utilities.
