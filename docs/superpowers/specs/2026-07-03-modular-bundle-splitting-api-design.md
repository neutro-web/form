# Modular Bundle Splitting — API Design

Date: 2026-07-03
Status: Approved (design phase)
Release gate: v0.5.0, item 2 of 6 (see memory `project_v050_release_gate`)
Supersedes/completes: `docs/superpowers/specs/2026-07-02-modular-bundle-splitting-design.md` (that draft identified the opportunity and explicitly deferred "its own brainstorming pass on the actual public API design before implementation" — this spec is that pass, and is the authoritative design going forward)

## Problem

`packages/core/src/index.ts` (3046 lines) bundles array operations, the DOM bridge (`connect`/`disconnect`/`MutationObserver`), persistence adapters, and computed fields into every consumer's bundle unconditionally, even for a form that only uses `set`/`get`/`validate`. `bundle-size` is `➖ Tied` against react-hook-form/vee-validate — closer than the tanstack-form/felte gaps and, unlike those, has real headroom: RHF's own bundle doesn't ship array-field support unless `useFieldArray` is imported.

The blocker isn't `sideEffects: false` (already set in both `packages/core/package.json` and `packages/alias/package.json`) — it's structural: `.connect()`, `.arrayRemove()`, etc. are methods on the object `createForm` returns, not top-level module exports. Tree-shaking has no visibility into which methods a consumer calls at runtime on an opaque closure object; it can only drop unused *module-level* exports. Making features tree-shakeable requires moving them out of `createForm`'s single closure body into separately-imported composition functions.

## Non-goals

- **No immutable/Redux-style state-tree redesign.** The engine keeps its current hybrid mutation model (state is mutated, not replaced with new objects on every change) — see "The mutation invariant" below for the one adjustment this spec makes to that model. A structural-sharing immutable rewrite was explicitly considered and rejected for this item: it would require rewriting the notify/batching/`pathIndex` machinery around immutable snapshots, reintroduces the exact class of shared-mutable-state risk this release has already hit 3+ times (now with a bigger blast radius), and trades away the O(1)/field-level-reactivity performance story that differentiates this engine from competitors — all for a bundle-size goal that doesn't require it.
- **No runtime feature-flag API** (e.g. `createForm({ features: ['arrayOps'] })`). Tree-shaking operates on which *module* a consumer imports, not on runtime configuration values — a feature flag chosen at call time can't be shaken out of the bundle, since the bundler can't prove the flag is always false. The only mechanism that actually reduces bundle size is separate entry points.
- **No finer-than-two-tier granularity** (e.g. separate entry points per individual feature cluster). Two tiers (`full` / `minimal`) is the pragmatic starting point matching real usage (consumers import the whole package and use most of it, or want the smallest possible footprint); a fully composable pick-your-features API is a much larger design space, out of scope unless the two-tier split proves the hypothesis and there's real demand for finer control.
- **No change to framework adapters' behavior.** `minimal` is a headless/vanilla-JS-only tier for this iteration — React/Vue/Svelte/Solid/Angular adapters continue to require the full `@neutro/form/core`, since they call DOM-bridge methods (`.connect()`) that `minimal` doesn't have.

## Scope correction (post-round-1-review)

Round 1 adversarial review found the original draft's cluster boundaries didn't hold up against the real code in several concrete ways. This section documents the corrections; the rest of "Design" below reflects the corrected shape, not the original draft.

1. **`errors` reassignment is not confined to `runValidation`.** `arraySwap`'s `swapKeys`, `shiftStateIndices`, and `rekeyArrayState` (all array-ops) also reassign `errors` wholesale, as does `reset()` (engine-level). The mutation invariant (see below) must apply at every one of these sites, not just the three in `runValidation` — see "Practical effect," corrected below.
2. **`getPayload()`/`submit()` depend on DOM-bridge-only state and would silently break under `minimal`.** `getPayload()` filters `values` by `connectedPaths`/`persistedPaths`, both populated only by `attachDomBridge`'s `connect()`. Under `minimal`, those Sets never populate, so `getPayload()` always returns `{}` and every `submit()` callback receives an empty payload. This is a **pre-existing gap in the current engine**, not one this split introduces — any full-mode consumer today who calls `submit()`/`getPayload()` without ever calling `.connect()` on any field already silently gets `{}` back. The split just surfaces it, since `minimal` is explicitly pitched as usable headlessly. **Decision (confirmed with user): fix this for both tiers.** `getPayload()`/`submit()`'s payload construction falls back to returning the full unfiltered `values` object whenever DOM-bridge was never attached/never used (i.e., `connectedPaths` and `persistedPaths` are both empty because `attachDomBridge` never ran, or ran but nothing was ever connected) — see "Public API surface" corrections below. This is a genuine, intentional behavior change for the narrow existing case of "full-mode app that calls `submit()`/`getPayload()` without using `.connect()`" (today: silently `{}`; after this change: real values) — call this out explicitly in the CHANGELOG for the release this ships in, since it's a user-visible behavior difference, not just an internal refactor.
3. **`reset()`/`resetField()` read from `connectionRegistry` directly** (to push reset values into live DOM elements), which the original draft treated as purely DOM-bridge-owned state.
4. **`computedMap.has(path)` gates writes inside `setFieldValue` itself** (the engine's core write path), and computed-fields execution reaches directly into `batchDepth`/`pendingPaths` (private batch-machinery internals) rather than going through `notify()`. The original draft's framing of computed-fields as "no distinct public methods, just affects values reactively" understated this: it's not a passive bolt-on, it's wired into the write path and batch internals. This requires a real extension-point mechanism — see "Engine extension points" below — not just "feature functions read ctx."
5. **Array-ops methods call `runValidation`/`dispatchAction` directly**, and **`reset()`/`hydrate()` call `notifyGlobalSubscribers`/`notifyPathSubscribers` directly** rather than through `notify()`. Both mean `ctx` must expose these as callable engine-primitive functions, not just data fields.
6. **Confirmed clean**: `notify`/`batch`/`dispatchAction`/`_flushNotifications` contain no cluster-specific branches and are correctly engine-only code as originally described. **Also confirmed**: there is no actual stale-read bug in the *current* `runValidation` (the `oldErrors` capture and reassignment happen synchronously with no `await` between them) — the mutation invariant remains prophylactic for the composition refactor, not a fix for an existing defect, exactly as the original draft stated.

### Engine state reclassification: `connectionRegistry`/`connectedPaths`/`persistedPaths` are engine-level, not DOM-bridge-owned

Per finding 3 (and 2), these three structures must live in `engine.ts`'s `ctx` unconditionally — always present, always empty unless `attachDomBridge` populates them via `connect()`. `attachDomBridge` *populates* them; it does not *own* their existence. This lets `reset()`/`resetField()`/`getPayload()`/`submit()` (all engine-level) reference them without importing anything from `dom-bridge.ts`, and lets the getPayload/submit fallback (finding 2's fix) check "are these empty" without depending on whether `attachDomBridge` ran at all.

**Round 5 found the same reclassification is needed for three more fields, resolving `destroy()`'s cluster coupling without a hook:** `destroy()` (a `FormInstance` method) references `mutationObserver` (dom-bridge), `persistenceUnsubscribe`, and `persistenceWriteTimer` (persistence) directly — `mutationObserver?.disconnect()`, `persistenceUnsubscribe?.()`, `clearTimeout(persistenceWriteTimer)`. Unlike `reset()`'s persistence-write logic (which needed an actual hook — see "Engine extension points" above, this isn't just state, it's an action), these three are genuinely the same shape as `connectionRegistry`: nullable engine-level fields (`mutationObserver: MutationObserver | null`, `persistenceUnsubscribe: (() => void) | null`, `persistenceWriteTimer: ReturnType<typeof setTimeout> | null`), defaulting to `null`, populated only if `attachDomBridge`/`attachPersistence` runs. `destroy()`'s existing optional-chaining/`if` guards (`mutationObserver?.disconnect()`, etc.) already correctly no-op when these stay `null` under `minimal` — no hook needed, just the same "engine owns the slot, feature populates it" reclassification already established for `connectionRegistry`.

### Engine extension points (per finding 4)

Rather than `setFieldValue` hard-coding a `computedMap.has(path)` check and calling `runComputedPass()` directly, `engine.ts` exposes two narrow, generic hook slots on `ctx`, initialized to no-ops and optionally overridden by `attachComputedFields`:

- `ctx.isComputedField: (path: string) => boolean` — defaults to `() => false`. `setFieldValue`/`set`/`setDynamic` call this instead of `computedMap.has(path)` directly.
- `ctx.runComputedPass: () => string[]` — defaults to `() => []`. **Corrected per round-2 review**: the original draft specified this hook as `() => void`, but the real `runComputedPass` returns `string[]` (the changed computed field paths), and `setFieldValue` consumes that return value to notify the correct path subscribers (`notifyPathSubscribers([path, ...changedComputedPaths])`) — a `void`-typed hook would silently break that notification under full mode, the exact call site this hook exists to preserve byte-for-byte. `setFieldValue` calls this instead of importing/calling `runComputedPass` directly, at the same point in the write path as today (including the existing `batchDepth`/`pendingPaths` interaction — that interaction stays inside `engine.ts`'s `setFieldValue`, since it's genuinely part of the engine's batching contract, not something `attachComputedFields` should reach into from outside). **`ctx.runComputedPass` also has two other call sites beyond `setFieldValue`**, found in round-2 review: `reset()` (engine-level, re-derives computed fields from the reset state, discarding the return value) and module initialization (the initial computed pass when a form is first created). Both call the same `ctx.runComputedPass` hook — under `minimal` (no-op default returning `[]`), these become correct no-ops rather than needing separate handling.

**Third hook slot, found in round 3: `ctx.hasComputedFields: () => boolean`** — defaults to `() => false`. Beyond the per-path `isComputedField` check and the `runComputedPass` execution hook, `setFieldValue` also branches on "are any computed fields configured at all" (today: `computedMap.size > 0`) to choose its notification strategy — a third, coarser-grained control-flow dependency the two-hook design from rounds 1–2 didn't cover. `attachComputedFields` overwrites this hook (`ctx.hasComputedFields = () => computedMap.size > 0`) alongside the other two. Under `minimal`, the default `false` makes `setFieldValue` take the same code path it would under full mode with zero computed fields configured — correct, and consistent with the other two hooks' no-op defaults.

`attachComputedFields(ctx)` overwrites all three hooks (`ctx.isComputedField = (path) => computedMap.has(path); ctx.runComputedPass = () => { /* existing logic */ }; ctx.hasComputedFields = () => computedMap.size > 0;`) when it runs. Under `minimal` (where `attachComputedFields` never runs), the defaults mean `setFieldValue`'s existing guard/call sites behave exactly as if no computed fields were ever configured — which is correct, since `minimal` doesn't accept a meaningful `computed` config anyway.

**Correction, round 5: computed-fields is NOT the only cluster with this shape of coupling — `reset()` has an identical hook-worthy dependency on persistence.** A genuinely fresh sweep in round 5 found `reset()` (an engine/minimal method) contains persistence's actual write logic inline: exclude-filtering the reset values, then calling `cfg.adapter.write()` (or `cfg.adapter.clear()`), referencing `config.persistence`/`persistenceUnsubscribe` directly. This is not "state that happens to be empty under minimal" (like `connectionRegistry`, which naturally no-ops when empty) — it's active feature-specific logic (filtering + an adapter call) living inside an engine/minimal-tier method, the same shape of problem computed-fields had inside `setFieldValue`. **Fourth hook, added per round 5: `ctx.onReset: (newValues?: T) => void`** — defaults to a no-op. `reset()` calls this instead of running the exclude-filter/adapter-write logic inline. `attachPersistence(ctx)` overwrites it with the existing write-on-reset behavior. Under `minimal`, the default no-op means `reset()`'s value/state clearing happens exactly as today, just without ever attempting a persistence write — correct, since `minimal` has no persistence adapter to write to.

**Round 6 verification found the `ctx.onReset` override, as first described, would introduce a real full-mode behavior regression — corrected here.** The actual current guard on this logic is not just "is persistence configured" but `if (cfg && persistenceUnsubscribe !== null)` — `persistenceUnsubscribe` is set only once `hydrate()` has actually run, so it doubles as an implicit "has this form finished hydrating yet" flag. Calling `reset()` on a full-mode form with `persistence` configured but *before* `hydrate()` has completed correctly no-ops the write today. If `attachPersistence`'s override of `ctx.onReset` is installed once at composition time (independent of whether `hydrate()` has run yet) and doesn't re-embed this same guard, `reset()` would start attempting persistence writes before hydration completes — a behavior change for existing full-mode consumers, not just a minimal-tier consideration. **`attachPersistence`'s `ctx.onReset` implementation must check `persistenceUnsubscribe !== null` (via the now-engine-level `ctx.persistenceUnsubscribe`) exactly as the current inline code does, not merely check whether `attachPersistence` ran.** This is the same category of subtlety as the `stateMap[bKey] === undefined` check the `pathIndex` work's `arraySwap` fix had to preserve carefully — a guard condition that looks incidental but is load-bearing, and must be carried into the hook body verbatim, not approximated.

This revises the earlier claim: the correct generalization is "any cluster whose logic is invoked from *inside* an engine/minimal-tier method (not just called independently, side-by-side, from the full entry point's composition) needs a hook slot," and this spec has now found two such clusters (computed-fields with three hooks, persistence with one) rather than one. Array-ops and dom-bridge remain genuinely hook-free — their methods (`arrayInsert`, `connect`, etc.) are called independently from outside any engine/minimal method, never invoked *from within* one (the one dom-bridge-adjacent case, `reset()` iterating `connectionRegistry` to push values into live DOM elements, doesn't need a hook because it degrades correctly by iterating an empty Map under `minimal`, per the earlier engine-state reclassification — it's genuinely a "state happens to be empty" case, unlike the persistence-write branch).

## Design

### Architecture

`packages/core/src/index.ts` splits into:

- **`src/engine.ts`** (new): the shared core. Exports `createCoreForm<T>(config): { ctx: FormEngineContext<T>; instance: MinimalFormInstance<T> }`. Contains `values`/`errors`/`touched`/`dirty`/`wasSet`/`validatedPaths`/`pathSubscribers`/`pathIndex`, the notify/batch machinery, validation, and — per the scope correction above — `connectionRegistry`/`connectedPaths`/`persistedPaths` (always present, populated only if `attachDomBridge` runs) and the two `isComputedField`/`runComputedPass` hook slots (defaulted to no-ops). `ctx` exposes not just data fields but callable engine primitives that other clusters need directly. This list has been revised in every one of the three review rounds as further cross-cluster calls were found by fresh, independent greps — treat it as a floor, and re-verify it independently during planning rather than trusting this enumeration:

- `ctx.runValidation`, `ctx.dispatchAction`, `ctx.notify`, `ctx.notifyGlobalSubscribers`, `ctx.notifyPathSubscribers`, `ctx.batch` (round 1).
- `ctx.indexKey`/`ctx.unindexKey` (round 2) — array-ops (`shiftStateIndices`/`rekeyArrayState`), dom-bridge (`initMutationObserver`'s cleanup path), and persistence (`hydrate`/engine's own `reset`) all call these two `pathIndex`-mutating functions directly, at roughly 60 call sites across the current file. Exactly as load-bearing as `notify`/`dispatchAction` for correctness.
- `ctx.getState` (round 3) — called directly from `initMutationObserver` (dom-bridge) and `hydrate()` (persistence), not just from the engine's own `getState()` method.
- `ctx.resolveFieldMode` (round 3) — an engine-closure helper called directly from `connect()` (dom-bridge).
- `ctx.deepMerge` (round 3) — an engine-closure helper called directly from `hydrate()` (persistence), for merging stored values with initial values.
- `ctx.setFieldValue` (round 4) — `arrayAppend` (array-ops) does not reimplement the write+validate+notify sequence the way its four siblings (`arrayInsert`/`arrayRemove`/`arrayMove`/`arraySwap`) do; instead it calls the engine's private `setFieldValue` directly. This matters more than a typical cross-cluster call, since `setFieldValue` is exactly the function housing the three computed-fields hooks (`isComputedField`/`runComputedPass`/`hasComputedFields`) and the `batchDepth`/`pendingPaths` batch-machinery interaction — `arrayAppend` calling it directly means array-ops depends on the full engine write path, hooks included, not just a narrow primitive. `attachArrayOps` must receive `ctx.setFieldValue` and call it exactly as `arrayAppend` does today; this is not optional or a candidate for `arrayAppend` reimplementing its own write logic (that would risk diverging from `setFieldValue`'s computed-fields/batch semantics, a worse outcome than one more ctx primitive).
- `ctx.subscribeToPath` (round 5) — `connect()` (dom-bridge) calls the engine/minimal method `subscribeToPath` directly to wire its internal a11y subscription. Needs to be on `ctx` alongside the other engine primitives, not assumed reachable some other way.
- `ctx.__warnUnknownPath` (round 5) — an engine-init dev-mode helper (backed by `__devPathTrie`) called from both engine methods (`set`/`get`/`setDynamic`) and `connect()` (dom-bridge). Needs to be on `ctx`.
- `ctx.transientPaths` (round 5) — this is genuinely **computed-fields-owned data** (derived from `computedMap`), not an engine primitive, but it's read by two minimal-tier methods: `submit()` and `getPayload()` (both strip transient/computed paths from the outgoing payload). It becomes a `ctx` field defaulting to `[]`, populated by `attachComputedFields` — parallel in shape to `connectionRegistry` et al. (engine owns the slot, feature populates it), not a fifth hook, since it's read-only data from the consuming side.

Given this list has grown across all three rounds purely from fresh greps finding what the previous pass missed, the implementation plan's file-boundary audit task (see "Practical effect" above) should treat finding cross-cluster function calls as part of the *same* exhaustive sweep as the `errors`/`touched`/`dirty`/`wasSet` reassignment audit — search for every function call inside every method being relocated, and classify each target as engine-only, same-cluster, or a cross-cluster primitive that needs to be on this list. Do not treat this enumeration as closed just because three rounds of review already ran; the actual implementation task should re-derive it from scratch and compare against this list, not extend this list piecemeal. `instance` implements `set`/`get`/`validate`/`subscribe`/`subscribeToPath`/`reset`/`resetField`/`submit`/`getState`/`getPayload`/`isFieldValid`/`isFieldDirty`/`isDirty`.
- **`src/features/array-ops.ts`**: exports `attachArrayOps<T>(ctx): ArrayOpsMethods<T>` — `arrayAppend`/`arrayInsert`/`arrayRemove`/`arrayMove`/`arraySwap` and their internal `shiftStateIndices`/`rekeyArrayState` machinery (including the `pathIndex`-based candidate-lookup rewrites from the prior release-gate item). Per the scope correction above, this module's own `errors` reassignment sites (`arraySwap`'s `swapKeys`, `shiftStateIndices`, `rekeyArrayState`) are converted to the same mutate-in-place pattern as `runValidation`'s (see "Practical effect," corrected below) — this is **not** a verbatim move for those specific lines, though the surrounding shift/rekey/swap logic itself is unchanged.
- **`src/features/dom-bridge.ts`**: exports `attachDomBridge<T>(ctx): DomBridgeMethods<T>` — `connect`/`disconnect`/`focus`/`focusFirstError`/`getAriaProps`, the `MutationObserver` lifecycle. Populates (but per the scope correction above, does not own the existence of) `ctx.connectionRegistry`/`ctx.connectedPaths`/`ctx.persistedPaths`.
- **`src/features/persistence.ts`**: exports `attachPersistence<T>(ctx): PersistenceMethods<T>` — `hydrate`, adapter wiring (`localStorageAdapter`/`sessionStorageAdapter` stay as standalone exported functions, unaffected — only the `hydrate()` method and its ctx-wiring move).
- **`src/features/computed-fields.ts`**: exports `attachComputedFields<T>(ctx): ComputedFieldsMethods<T>` — `computedMap`, `flattenComputedConfig`, `runComputedPass`.
- **`src/index.ts`** (existing file, now much smaller): the full entry point. Calls `createCoreForm`, then `Object.assign`s the four `attachX(ctx)` results onto `instance`, returning it typed as `FormInstance<T>`. This is the **only** change existing consumers see, and it's invisible: same function signature, same returned object shape, same method behavior.
- **`src/minimal.ts`** (new): the minimal entry point. Calls `createCoreForm` and returns `instance` as-is, typed as `MinimalFormInstance<T>`.

### The `ctx` object and the mutation invariant

`ctx: FormEngineContext<T>` is a single plain object holding every field currently captured by `createForm`'s closure (`values`, `errors`, `touched`, `dirty`, `wasSet`, `validatedPaths`, `pathSubscribers`, `pathIndex`, `pendingPaths`, `pendingExactPaths`, `batchDepth`, `config`, `initialValues`, `isSubmitting`, `isValidating`, etc.), passed by reference into `createCoreForm` and each `attachX` function. It is purely internal — never exported, never part of any public type.

**Hard invariant, required by this design and enforced going forward: no field on `ctx` is ever reassigned to a new object/array/Set/Map — every field is mutated in place (cleared and repopulated, not replaced).** `validatedPaths`/`pathSubscribers`/`pathIndex` already follow this pattern today. **`errors`, `touched`, `dirty`, `wasSet`, `values`, and `initialValues` do not** — this scope was wrong in every draft through round 6 (each claimed only `errors`, or only the four record structures, was the exception) and was corrected only in round 7 of adversarial review, which found `values`/`initialValues` are ALSO reassigned wholesale — at the same `reset()`/`hydrate()` sites (`reset()`: `initialValues = deepClone(newValues); values = deepClone(initialValues);`; `hydrate()`'s equivalent lines) — and are, if anything, a *more* dangerous omission than the four record structures: `values` is read by every single cluster (dom-bridge's DOM-sync, all five array-ops via `getNestedValue(values, ...)`, persistence's merge logic, computed-fields' `runComputedPass`), making a destructured `const { values } = ctx` at least as natural a mistake as `const { errors } = ctx`, with the exact same permanent-staleness consequence the whole invariant exists to prevent. **This spec requires converting all six** (`errors`/`touched`/`dirty`/`wasSet`/`values`/`initialValues`) to clear-and-repopulate-in-place: for `values`/`initialValues`, this means clearing the existing object's top-level keys and `Object.assign`-ing the clone's keys onto the same object, rather than reassigning the `ctx.values`/`ctx.initialValues` reference — cheap (O(top-level keys), not O(total nested state)) and consistent with the same mechanism already used for the four record structures.

**One remaining, deliberately-scoped exception: `lastSubmittedValues`.** Reassigned at `submit()` and `reset()`, but read only by the engine's own `getState()` — never by any feature-cluster code, since nothing outside the engine has a reason to read the last-submitted snapshot. Converting it would add conversion-task surface for zero risk reduction (nothing external can hold a stale reference to a field nothing external reads), so this spec leaves it as a documented, convention-only exception — **the lint rule described below is not optional for this one field**, since it's the one place the invariant deliberately doesn't apply and a future contributor could plausibly assume it does.

**Why this invariant matters for this specific refactor:** today, each of `errors`/`touched`/`dirty`/`wasSet` is a `let` in one function scope, so every nested closure automatically observes reassignment — there's no way to hold a "stale" reference to any of them, because nothing captures them into a separate variable. Splitting feature code into separately-composed functions that receive `ctx` removes that free guarantee: a feature function could destructure `const { errors, touched } = ctx` at setup time and then read permanently-stale snapshots after the next shift/reset/hydrate reassigns those `ctx` fields to new objects. The correct discipline ("always read `ctx.X` fresh, never destructure-and-cache") is necessary but is a convention, not a guarantee — a human or AI implementer can violate it with no automatic backstop. Making these four fields never-reassigned removes the hazard by construction: even a function that destructures `const { errors } = ctx` gets a reference to the *same* object that keeps being mutated under it, so the destructured reference stays live forever. This is not a performance optimization or a stylistic preference — it is the mechanism that makes the `ctx`-based composition safe without relying on every future contributor remembering a rule.

**Practical effect — every reassignment site, per structure it actually touches (corrected across four rounds of review):** round 1 found the original draft only accounted for `runValidation`'s three `errors = ...` sites. Round 2 found a fourth-file/seventh-site miss (`hydrate()`). Round 3 found the scope itself was wrong — `touched`/`dirty`/`wasSet` also reassign, not just `errors`. **Round 4 found round 3's own "8 sites × 4 structures uniformly" framing over-corrected**: not every site touches all four structures. The precise, per-site breakdown (verified by reading each site's actual current code, not re-asserted from a prior round's summary):

| Site | File (post-split) | Structures reassigned |
|---|---|---|
| `runValidation` (3 branches) | `engine.ts` | `errors` only — `touched`/`dirty`/`wasSet` are never referenced in `runValidation` |
| `shiftStateIndices` | `features/array-ops.ts` | `errors`, `touched`, `dirty`, `wasSet` (all 4) |
| `rekeyArrayState` | `features/array-ops.ts` | `errors`, `touched`, `dirty`, `wasSet` (all 4) |
| `arraySwap`'s `swapKeys` | `features/array-ops.ts` | `errors`, `touched`, `dirty`, `wasSet` (all 4) |
| `reset()` | `engine.ts` | `errors`, `touched`, `dirty`, `wasSet`, **`values`, `initialValues`** (round 7 addition) |
| `hydrate()` | `features/persistence.ts` | `errors`, `touched`, `dirty` — **not** `wasSet`; **`values`, `initialValues`** (round 7 addition) |

`values`/`initialValues` are reassigned only at these same two sites (`reset()`/`hydrate()`) — no additional call sites beyond the six already in this table.

That's 8 call sites total, spanning 3 files, touching between 1 and 4 of the four structures depending on the site — not a uniform "4 structures at every site" as the round-3 text stated. **Every one of these converts to the same clear-and-repopulate-in-place pattern, applied only to the structures that specific site actually reassigns** (per the table above — do not add conversion work for structures a site doesn't touch): clear the `ctx` field of keys not present in the new result (calling `ctx.unindexKey` per removed key), then assign each new/kept key onto the *same* object (calling `ctx.indexKey` per newly-added key) — tracking index changes as the clear/repopulate happens, not via a before/after diff. This removes `reindexErrors` as a separate function (its logic generalizes to whichever structures each site touches, per the table above).

**Conversion hazard flagged in round 5, performance-relevant and correctness-relevant:** `shiftStateIndices`/`rekeyArrayState`/`arraySwap`'s `swapKeys` currently work by building `updated = { ...stateMap }` (a full clone) and reading source values from the *original* `stateMap` throughout, since `updated` is a separate object. Converting to true in-place mutation (clearing/rewriting the *same* object, per the invariant) removes an O(total-keys) clone per array op at each of these three sites — this is a genuine, incidental performance improvement, not a regression risk (it's independent of the `pathIndex` work's candidate-lookup optimization, which only bounded the *scan*, not this clone). But it introduces a real correctness hazard the "clear then repopulate" phrasing above doesn't spell out: a naive in-place conversion that deletes a source key *before* reading its value to write to the rename target will read `undefined` instead of the real value. The conversion must capture every rename's value up front (into a list of `[oldKey, newKey, value]` tuples, exactly as `rekeyArrayState`'s existing code already does at its `affectedKeys`/`renames` step) before performing any deletes — this exact hazard is why `rekeyArrayState`'s current code already separates "compute renames" from "apply renames" into two passes, and the conversion must preserve that two-pass shape for all four (now: for whichever of the up-to-four structures apply) rather than collapsing it into a single delete-and-immediately-rewrite loop.

**`validatedPaths`/`pathSubscribers`/`pathIndex` confirmed (round 4) to never be reassigned anywhere in the file** — only ever mutated via `.add()`/`.delete()`/`.clear()`+repopulate or `.get()`/`.set()`/`.delete()`. The mutation invariant for these three was already satisfied before this spec and needs no conversion work; only `errors`/`touched`/`dirty`/`wasSet` (per the table above) require it.

**This enumeration has now been revised in all three review rounds — treat "8 call sites, 4 structures, 3 files" as a floor, not a ceiling.** The implementation plan's first task must be a genuinely exhaustive grep-based audit (`errors = `, `touched = `, `dirty = `, `wasSet = `, and their `[...]`/`delete [...]` forms, mirroring the discipline used for the `pathIndex` call-site audit) across the *entire* file before any conversion work begins, and must not proceed past that audit task until an independent reviewer confirms the count against a fresh grep of their own — not a re-read of this spec's count. The pattern across all three rounds so far has been "the previous count looked complete until someone actually grepped the whole file fresh," which is exactly the failure mode an audit-then-independently-re-verify gate exists to catch. Given this happened three times in review alone, the implementation plan should treat the audit task's own output as unverified until a *second, independent* pass confirms it — i.e., the audit itself needs the same fresh-subagent-plus-review treatment as any other task, not just a single grep taken on faith.

This is a genuine behavior-preserving refactor of existing logic at every site, not new functionality — the observable result (which keys end up in `errors`, when notifications fire) is unchanged; only the mechanism for keeping `pathIndex` in sync changes shape. But because it now spans both `engine.ts` and `features/array-ops.ts`, it can't be landed as one isolated "convert runValidation" task the way the original draft implied — the implementation plan needs to treat this as one atomic conversion across every site, verified together (a partial conversion — some sites mutate-in-place, others still reassign — would violate the invariant for exactly the sites not yet converted, silently reintroducing the destructure-staleness hazard for those).

**Defense-in-depth lint rule — optional for the six converted fields, mandatory for `lastSubmittedValues`:** a custom biome/lint rule flagging `const { X } = ctx` destructuring patterns for known `ctx` fields, catching any future violation attempt at CI time. For `errors`/`touched`/`dirty`/`wasSet`/`values`/`initialValues`, the mutation invariant eliminates the bug class by construction, so this lint rule is a "belt" alongside the invariant's "suspenders" — worth adding if low-effort, not a blocker if awkward to write correctly. For `lastSubmittedValues` specifically (the one deliberately-excepted field, see above), there is no invariant backstop — the lint rule (or an equivalent code-review checklist item, if the lint rule proves impractical to write) is the *only* protection against a stale-reference bug on that one field, and should not be skipped as "optional polish" the way it can be for the other six.

### Public API surface

```ts
// FormEngineContext<T> — internal only, never exported

interface MinimalFormInstance<T> {
  set(path, val, options?): void;
  get(path): unknown;
  validate(scopePaths?): Promise<boolean>;
  subscribe(fn): () => void;
  subscribeToPath(path, fn): () => void;
  subscribeToPathDynamic(path, fn): () => void;
  reset(newValues?): void;
  resetField(path, options?): void;
  submit(onSubmit): Promise<boolean>;
  handleSubmit(onSubmit, onInvalid?): (e?) => Promise<void>;
  getState(): FormState<T>;
  getPayload(): Partial<T>;
  batch(fn): void;
  isFieldValid(path): boolean | null;
  isFieldDirty(path): boolean;
  isDirty(): boolean;
  setErrors(errors): void;
  clearErrors(): void;
  getFieldMode(path): ValidationMode;
  watch(paths, callback): () => void;
  // Round 5 correction: destroy() moves here from FormInstance. A minimal
  // form still accumulates activeAbortControllers/globalSubscribers/
  // pathSubscribers/pending async-validation timers -- it needs a teardown
  // path exactly as much as a full form does. Its dom-bridge/persistence
  // cleanup branches (mutationObserver?.disconnect(), persistenceUnsubscribe?.())
  // correctly no-op under minimal per the engine-state reclassification above.
  destroy(): void;
  _subscribeToActions(fn): () => void;
  // ... every other method NOT tied to array-ops/DOM-bridge/persistence/computed-fields
}

interface FormInstance<T> extends MinimalFormInstance<T> {
  // Array ops
  arrayAppend<P>(path, item): void;
  arrayInsert<P>(path, index, item): void;
  arrayRemove<P>(path, index): void;
  arrayMove<P>(path, from, to): void;
  arraySwap<P>(path, a, b): void;
  // DOM bridge
  connect(path): (el) => void;
  getConnectedCount(): number;
  focus(path): boolean;
  focusFirstError(): boolean;
  getAriaProps(path, options?): AriaProps;
  // Persistence
  hydrate(): Promise<void>;
  // (computed fields have no distinct public methods today — they affect
  //  `values` reactively; excluding attachComputedFields from minimal means
  //  a minimal-tier form simply has no `computed` config option honored)
}
```

`FormInstance<T> extends MinimalFormInstance<T>` is the key ergonomic property: since it's a strict structural superset, upgrading from `minimal` to full is a **pure widening** — switch the import path, and every method already in use still exists, plus the new ones become available. No other code changes are required. The one edge case: a consumer who explicitly annotated a variable with the narrower `MinimalFormInstance<T>` type would need to update that annotation too — an unusual, deliberate choice, not the normal path (normal usage relies on `createForm`'s inferred return type, which changes automatically with the import).

`FormConfig<T>`'s `computed` option is accepted by both entry points' `createForm` signature for type-compatibility (so switching entry points never causes a config-shape type error), but is silently a no-op under `minimal` (computed fields require `attachComputedFields`, not present). This is flagged in JSDoc on the `computed` field and in the documentation (see below) rather than causing a compile error, since detecting "config option provided but its handler isn't attached" at the type level would require conditional types keyed to which entry point is used — disproportionate complexity for a config option that most `minimal` consumers won't set in the first place.

**`getPayload()`/`submit()` fallback behavior (fix for finding 2, confirmed with user — applies to both tiers, not just `minimal`):** `getPayload()`'s underlying `_getPayload(values, connectionRegistry, connectedPaths, persistedPaths)` currently filters `values` down to only paths present in `connectedPaths` or `persistedPaths`, both populated exclusively by `attachDomBridge`'s `connect()`. Since (per the engine-state-reclassification correction above) these three structures now live in `engine.ts` unconditionally, `_getPayload` gains one additional check: **if `connectedPaths` and `persistedPaths` are both empty, return the full unfiltered `values` object** (deep-cloned, as today) instead of the filtered (and, in that case, always-empty) result. This covers both `minimal` (structurally can never populate these Sets, since `attachDomBridge` never runs) and full-mode consumers who never call `.connect()` on anything. Once at least one path is connected or persisted, filtering behaves exactly as it does today — this fallback only activates for the specific "nothing has ever been connected" case, not a general behavior change to the filtering logic itself. **This is an intentional, user-confirmed behavior change** for existing full-mode consumers in that narrow case (today: `submit()`/`getPayload()` silently return `{}`; after this change: they return real values) — call it out explicitly in the release's CHANGELOG, not just in this spec, since it's observable to existing consumers who never call `.connect()`.

### Compile-time vs. runtime failure mode

A `minimal`-tier consumer calling `.arrayRemove()` fails at **compile time** — `MinimalFormInstance<T>` has no such method, so TypeScript rejects the call before the code ever runs. This is the correct failure mode: an adapter or application code that assumes DOM-bridge/array-op methods exist should never successfully compile against a `minimal` form, not throw a runtime error a user discovers in production.

## Testing

1. **Full existing suite unmodified.** Every test in `packages/core/test/*.test.ts` must pass against the refactored `src/index.ts` with zero test changes — this is the primary regression guard proving the composition refactor preserves 100% of full-package behavior.
2. **`errors`/`touched`/`dirty`/`wasSet`/`values`/`initialValues` mutate-in-place conversion, at every site identified in the scope correction (not just `runValidation`, not just `errors`, and not just the four record structures).** New/adapted tests covering: scoped validation leaving unrelated errors untouched (mirroring the existing `mergeScopedErrors` test coverage), async validation races (abort/epoch handling unaffected by the reassignment→mutation change), `arraySwap`/`shiftStateIndices`/`rekeyArrayState`'s own error/touched/dirty/wasSet-shifting behavior unchanged, `reset()`/`hydrate()`'s clearing behavior unchanged for every structure each actually touches (per the per-site table above), a test proving no cluster ever observes a stale `ctx.values`/`ctx.initialValues` reference across a `reset()`/`hydrate()` call (the specific hazard round 7 found), and a fuzz-style check (in the spirit of the `pathIndex` fuzz test) that every structure's final key set/content and `pathIndex` stay consistent across interleaved validate/set/array-op/reset/hydrate operations — this is the same class of correctness risk the prior release-gate item's `pathIndex` work already built tooling for (`_debugRawState()`, `_debugPathIndex()`), so this conversion should reuse those debug accessors rather than inventing new ones.

## Risks

- **Refactor blast radius**: this touches the entire `createForm` closure body — every one of its ~3000 lines gets relocated into one of five files. Given this release's history (3+ rounds of subtle shared-notify-machinery bugs, plus the 4 real bugs found across the `pathIndex` work), the implementation plan for this spec must apply the same discipline: TDD, fresh-subagent-per-task, independent adversarial review per task, and a final whole-branch review — not treated as a mechanical move-code refactor just because no logic is intended to change.
- **`errors`/`touched`/`dirty`/`wasSet`/`values`/`initialValues` mutate-in-place conversion is a genuine logic change**, not a pure relocation, and is the highest-risk single piece of this spec — it touches validation's error-reporting path, the write path's touched/dirty/wasSet tracking, AND the two fields every cluster reads (`values`/`initialValues`) directly, **at 8 call sites spanning 3 files (`engine.ts`, `features/array-ops.ts`, `features/persistence.ts`)**, per the exact per-site table above — not the single-structure, single-module change the first two drafts scoped, nor the "4 structures uniformly" round-3/4 framing, nor even the "4 record structures only" scope this risk note itself stated through round 6. This count and scope have been revised in every one of seven review rounds — most significantly in round 3 (scope wasn't `errors`-only) and round 7 (scope also wasn't record-structures-only: `values`/`initialValues` are arguably the *most* dangerous omission, since they're read by literally every cluster). It should be its own early task in the implementation plan, landed and fully verified (including against the existing `pathIndex` fuzz-test-style tooling) before the file-splitting work begins, so a regression here isn't conflated with a relocation mistake elsewhere. Per the correction above: a partial conversion (some sites/structures converted, others not) is worse than no conversion, since it would leave the invariant violated at exactly the unconverted sites while giving false confidence elsewhere — the implementation plan must treat this as one atomic, exhaustively-audited task, with the audit itself independently re-verified before conversion work starts (see "Practical effect" above for why a single self-review pass has repeatedly proven insufficient for this specific enumeration, across seven rounds now).
- **`getPayload()`/`submit()` fallback is a genuine, user-confirmed behavior change**, not just an internal refactor detail — existing full-mode consumers who never call `.connect()` will see `submit()`/`getPayload()` start returning real values instead of `{}`. This must be called out in the release CHANGELOG, and the implementation plan should consider whether it warrants its own explicit test asserting the OLD behavior is gone (a regression test in the "this changed on purpose" direction, not just "the new behavior works").
- **Engine extension points (`isComputedField`/`runComputedPass` hooks) are new indirection in the hottest write path** (`setFieldValue`). Two function-pointer calls per write is unlikely to be measurably slower than the direct calls it replaces, but the implementation plan should include a quick sanity check against existing `bench/suites/core/` write-path benchmarks (e.g. `set-get`) to confirm no regression, given this path is the single most frequently executed code in the entire engine.
- **Silent computed-fields no-op under `minimal`**: a consumer who sets `computed` in `FormConfig` while using `@neutro/form/core/minimal` gets no error, just silently non-functional computed fields (see "Public API surface" above for why this isn't type-checked away). The documentation must make this explicit and prominent, not buried — this is the one place in this design where a consumer's config could look correct and behave incorrectly with no warning.
- **Silent persistence no-op under `minimal` (found in round 5, same shape as the computed-fields case above and needs equally prominent documentation, not a lesser footnote)**: a consumer who sets `persistence` in `FormConfig` while using `minimal` gets no error. `hydrate()` doesn't exist on `MinimalFormInstance`, so the adapter is never actually wired up (`persistenceUnsubscribe` stays `null` per the engine-state reclassification above), and `ctx.onReset`'s default no-op means `reset()` never attempts a write either. The config looks accepted (no compile error, same reasoning as `computed`) but does nothing at all — this must get the same documentation prominence as the computed-fields case, not be treated as a lesser variant of it.
- **Adapter compatibility must be verified, not assumed**: the design non-goal states adapters require full `@neutro/form/core`, but this should be confirmed against each adapter's actual source (`packages/adapters/*/src/index.ts`) during implementation — if any adapter happens to only use `MinimalFormInstance`-compatible methods today, that's a fact worth knowing (though not a reason to change this spec's scope).

## Open questions for the implementation plan

- Exact enumeration of every method/field in the current `createForm` closure and which of the five destination files (`engine.ts` or one of the four `features/*.ts`) it belongs to — this spec identifies the clusters by name but the plan needs a complete, verified mapping (similar in spirit to the exhaustive call-site audit the `pathIndex` plan required). Given this spec's own first draft undercounted the `errors` reassignment sites and missed the `getPayload`/computed-fields/notify-bypass couplings on the first pass, this audit needs to be genuinely exhaustive (grep every cross-reference, not just the "obvious" methods) rather than a quick pass.
- Whether the `errors`/`touched`/`dirty`/`wasSet`/`values`/`initialValues` mutate-in-place conversion can reuse `pathIndex`'s existing `_debugRawState()`/`_debugPathIndex()` test infrastructure directly or needs its own equivalent (particularly for `values`/`initialValues`, which aren't `pathIndex`-tracked structures and so aren't covered by the existing debug accessors at all) — decide during planning by reading that infrastructure's actual current shape.
- Whether `ctx.notify`/`ctx.notifyGlobalSubscribers`/`ctx.notifyPathSubscribers`/`ctx.runValidation`/`ctx.dispatchAction`/`ctx.batch` (the engine-primitive functions identified in the scope correction) should be plain function properties on `ctx`, or whether some should be bound/curried differently — decide during planning by reading each call site's actual current signature and closure-capture needs.
- Sequencing: `errors`/`touched`/`dirty`/`wasSet` conversion (all 8-plus sites across all 4 structures, as one fully-verified task, itself preceded by an independently-re-verified exhaustive audit) first, then the engine-state reclassification (`connectionRegistry` et al. becoming engine-level) and the three extension-point hooks (`isComputedField`/`runComputedPass`/`hasComputedFields`), then the `getPayload`/`submit` fallback fix, then the five-way file split (informed by the cross-cluster-call audit that identifies the full `ctx` primitives list), then the two entry points' build/export wiring, then documentation — the plan should make this ordering explicit rather than implicit, since several of these are now prerequisites for the file split rather than independent concerns.
